# 01. ЦЕЛЬ И ВИДИМЫЙ РЕЗУЛЬТАТ

Пользователь дома у клиента открывает существующий проект спальни, выбирает шкаф, выбирает отсек и **в том же отсеке** составляет смешанную конструкцию: снизу три выдвижных ящика, над ними горизонтальная полка/перегородка, выше несколько полок **или** секция со штангой. Отдельно может добавить верхнюю секцию (антресоль внутри шкафа) с контролируемой горизонтальной перегородкой, если это конструктивно допустимо. Каждая зона имеет точные миллиметровые границы, понятный способ редактирования и строгую проверку коллизий. Изменение шкафа и зоны синхронно меняет 3D, фасадный лист, разрез, сборочную схему, физические панели, BOM и статус сметы. Всё сохраняется после перезагрузки.

**Не требуется** реализовать в R02B все когда-либо существующие механизмы, полную рекурсивную свободную геометрию или производственный короб ящика. Требуется закончить один работающий end-to-end сценарий **без фиктивных деталей**.

## Основной пользовательский сценарий S1

1. `Новый объект → Спальня → Мебель → шкаф 1000 × 2400 × 600 мм`.
2. Корпус 16 мм (из **реальной настройки цеха**), два вертикальных отсека R01.
3. В левом отсеке четыре обычные полки (не трогать).
4. В правом отсеке добавить нижний блок из трёх ящиков существующим R02A.
5. Над ним добавить конструктивную горизонтальную перегородку/опорную полку, указывая фактическую высоту в миллиметрах.
6. Над разделителем создать **верхнюю функциональную зону**; разместить там 2–3 полки; изменять их высоты независимо от ящиков.
7. Вместо полок верхней зоны выбрать штангу (после явного удаления/замены содержимого только этой зоны) и менять её высоту; другие зоны не теряются.
8. Выделить верхнюю зону; добавить антресольную зону с разделителем, если геометрия позволяет. Термин "антресоль внутри шкафа" **не должен молча создавать** отдельный верхний мебельный ряд или превращать существующий `mezzModules` в другую модель. Соотношение определить из кода и подписывать точно.
9. В 3D открыть ящик №2, вращать камеру, проверить неподвижность перегородки/штанги/других ящиков.
10. Перейти на фасад, боковой разрез выбранной зоны, панель раскроя, смету. Проверить размеры и принадлежность деталей.
11. Сохранить, обновить страницу, снова выбрать шкаф; все зоны/полки/ящики/штанга/разделители прежние. Простое открытие не пишет в базу.

## Обязательный альтернативный сценарий S2

Один широкий шкаф с правой зоной "нижние ящики + верхняя штанга"; без визуального наложения штанги на ход выдвижения, без ложного выпуска присадки и без удаления полок в другом отсеке. При изменении размера шкафа система либо строго пересчитывает допустимую геометрию, либо показывает численный отказ.

# 02. АРХИТЕКТУРНЫЙ КОНТРАКТ (НЕ НАРУШАТЬ)

## Единый источник истины

Сохранить `MillworkState → Run → Module → fill → bays`. Не создавать `FurnitureState`, `CabinetState`, `DrawerState`, отдельный `InteriorLayoutState`, второй Geometry Engine или самостоятельный Zustand store с другой геометрией. Визуальное состояние (выделение, анимация открывания) может жить в UI/store, но не должно быть вторым хранилищем размеров/разбивки.

**Изменения сохранённой конструкции — только через существующий путь `applyOps`/`set_fill` и проверки.** Единовременные выбранные пользователем параметры (тип зоны, высота, количество полок и др.) — канонические, вычисляемые X/Y/Z, partIds, внешние/внутренние габариты и BOM-количества — функции вычисления.

## Стратегия миграции без миграции

Перед проектированием нового поля выяснить, как сейчас в `FillBay` представлены полки и `drawers`. Предложить **минимальное опциональное расширение** (например, вложенные горизонтальные функциональные зоны с stable IDs и ссылкой на parent bay), но не принимать пример за навязанный API. Альтернативно можно расширить существующие поля при доказанной корректности. Сперва написать короткий data-contract в отчёте к реализации.

Требования:
- Проекты без `bays`: семантика абсолютно прежняя, сериализация и fingerprint не меняются.
- Проекты с R01-бэй без mixed zones: семантика прежняя, не добавлять автоматически разделители при чтении.
- Проекты R02A (`bays[].drawers`) открываются **без сброса**, существующие позиции и `partId` сохраняются. Переход в смешанный режим — **явная операция пользователя**, с понятными последствиями; не переносить данные молча.
- Сохранение и чтение `JSON`/Supabase не теряют настройки.
- Стабильные `bayId`, `zoneId`, `partId` при редактировании, перерисовке и сохранении; только действительно заменённая деталь может получить новый ID.
- Не хранить вычисленные координаты одновременно в zone, module и UI.
- Любое изменение `fill` меняет fingerprint этого модуля; legacy fingerprints неизменны. Использовать канонический путь fingerprint; не делать отдельный hash для нового редактора.
- `opsBayLoss` и подтверждение из R02A.1 сохраняют контроль над всеми новыми горизонтальными зонами; в предупреждениях указывать количество/тип потерянных зон и наполнений.

## Допустимое смешение

Ранее логика R01 запрещала одновременные legacy shelves/rods/drawers при наличии bays. Сохранить запрет legacy-конфликта. **При mixed zones отдельные shelves/rod/drawer разрешены только внутри разных непересекающихся зон одного bay**, с предсказуемой геометрией и валидатором. Не обходить guard путём удаления проверок.

# 04. ТОЧНАЯ ГЕОМЕТРИЯ ГОРИЗОНТАЛЬНЫХ ЗОН

## Координаты

Все физические расчёты в **мм**. Внутренняя система координат — как сейчас у `bayLayout` и `cabinetBoxes`, не вводить второй offset для цоколя. Выяснить, что называется "от дна корпуса", "от пола" и "по фасаду"; расхождения фиксировать тестом. Для одной зоны вычислять:

- `zoneId`, `bayId`, `moduleId`;
- `yFromMm`, `yToMm` в системе текущего ядра;
- `clearWidthMm`, `clearHeightMm`, `usableDepthMm`;
- занятые вертикальные интервалы физических разделителей и наполнения;
- физические панели `partId`, `X/Y/Z`, размеры и ориентацию;
- геометрию фронтов ящиков из существующего `resolveDrawerStack`;
- допустимые объёмы и диагностические ошибки.

**Вычисления целиком в существующем общем geometry pipeline**. `ElevationDrawing`, `SectionDrawing`, `panels.ts`, 3D получают одни и те же координаты. Нельзя вычислять "в 2D 16 мм, а в 3D 18 мм" отдельными формулами.

## Горизонтальный разделитель

- Должен быть **одной физической панелью**, когда реально предусмотрен конструкцией; не дублировать ту же панель ещё раз как обычную полку.
- Толщина определяется текущим правилом материала/корпуса, не хардкодить `16`. Проверить 16 и 18 мм.
- Длина = физический размер **своего** bay с технологическими допусками из текущей конфигурации цеха; глубина от shop allowances и назначения детали. Не переносить произвольно 2 мм / 20 мм, если для **этого типа соединения** нет подходящего правила. Если правило не определено — готовность производства `MISSING_DATA`, а не автоматически правильный раскрой.
- Разделитель занимает материальный вертикальный интервал `[y, y+t]` (или текущая формула ядра). Полки и фасады рядом не могут пересекать этот интервал.
- Контакт плоскостей по нулевому проникновению допустим. Проникновение > tolerance — ошибка. Значение tolerance валидации отличать от технологических допусков.
- В BOM панели привязаны к `moduleId, bayId, zoneId` и имеют стабильный `partId`.

## Зоны с полками

- Полки создаются **только внутри выбранной верхней/нижней зоны**, между её физическими границами.
- Режимы: `even`, `manual`; правильная привязка к System 32 согласно **существующей** настройке и логике; не выдавать произвольный шаг 32 как подтверждённую присадку.
- Высота редактируется числами. Если 290 мм преобразуется в 288 мм по принятому правилу — UI явно сообщает; не перемещать тихо.
- Не позволять полке пересечь разделитель, фасад другого назначения, соседнюю зону, стенку шкафа или другой модуль.
- Позиции других bay при правке не изменяются.

## Зоны с ящиками

- Использовать текущую модель `FillBay.drawers` / `resolveDrawerStack`, её IDs, фронты, стадии производства и независимую анимацию.
- Для ограничения зоны использовать явно определённую высоту и offset, не растягивать ящики до верхней границы модуля.
- Высоты блока/фронтов/зазоры остаются согласованными с действующими shop settings.
- Короб без технических правил остаётся *визуальным объёмом/габаритом*, а не готовой панельной деталировкой. Фасад, если рассчитывается производственно корректно, остаётся реальной деталью.
- Блок 450 мм с тремя ящиками при изменении соседней верхней зоны не должен становиться 600 мм без явного действия.
- Открытие 3D — независимое, без смещения иных элементов; траектория 300 мм если демонстрационная, явная маркировка, нельзя обещать механическую длину выдвижения.

## Зона со штангой

- Отдельная функция зоны `rod` (одна или несколько штанг **только если конструкция это позволяет**), точный position, span, высота.
- Разрешать выбор допустимой штанги из уже подтверждённого каталога; если артикул/диаметр/крепление неизвестны — статус визуального референса, без фальшивых монтажных отверстий и расчётных цен.
- Проверка столкновений **твёрдых тел**: штанга против разделителя/полок/боковин/фасадов. Не выдавать расчёт нагрузки или достаточную высоту для одежды без подтверждённого правила; допускается предупреждение `NOT_VERIFIED`.
- При замене `shelves ↔ rod` показать, какие полки уйдут, и запросить явное подтверждение потери в затронутой зоне. Не удалять полки другого bay.

## Верхняя/антресольная зона

- Сначала точно выяснить семантику существующих `mezzModules` и `upperSegments`. Внутренняя антресоль шкафа — **горизонтально отделённая часть того же Module**, если это соответствует пользовательской операции; не путать с отдельно стоящим верхним модулем.
- Позволить разделить верхнее свободное пространство на два допустимых участка и при необходимости сохранить полки/штангу по понятному правилу; если авторазмещение невозможно, отклонять с численным сообщением.
- Не генерировать фасад для верхней зоны автоматически, если система фасадов не умеет его корректно рассчитывать. Показать, что фронт отдельной зоны — следующий согласуемый scope, и не выдумывать производство.

# 05. МОДЕЛЬ РЕДАКТИРОВАНИЯ И ОПЕРАЦИИ

Минимальный набор:

- `AddHorizontalDivision` — выделить выбранный bay/zone; создать две независимые зоны и **одну** физическую перегородку;
- `MoveHorizontalDivision` — ввести высоту разделителя (в мм); заранее проверить воздействие на полки и ящики;
- `RemoveHorizontalDivision` — обнаружить потери и подтвердить; если удаление невозможно без перестройки содержимого, назвать причину;
- `SetZoneFunction` — empty / shelves / drawers / rod / top-storage; предусмотреть совместимость, не генерировать внезапное наполнение;
- `AddShelf` / `RemoveShelf` / `MoveShelf` / `Distribute` внутри зоны;
- `DrawerCount` / `DrawerBlockHeight` / `IndividualDrawerHeight` — использовать R02A, без копии;
- `SetRodHeight` / `RemoveRod` / `SelectRodReference` при известных/черновых данных;
- `ResizeModuleWidth` / `ResizeBayWidth` / изменение высоты шкафа — сохранить геометрические инварианты, при отказе **не менять исходное состояние**;
- `Undo/Redo` **не реализовывать искусственно в R02B**, если его нет — зафиксировать отдельным этапом, но каждая операция должна быть атомарной;
- `Save / Reload` без преобразований/потерь.

Технический API операций может отличаться: предпочесть `set_fill` с проверенными helper-функциями текущего стека, а не добавление десятков новых ops без необходимости. Учитывать генерацию вариантов: смена вида и типа не может молча удалить mixed zones; защиту R02A.1 расширить с полным количеством физических частей.

## Численные отказы

Сообщения в стиле: «Высота верхней зоны получилась бы 74 мм: доступно 74 мм, необходимо 96 мм, не хватает 22 мм», причём порог `96` может применяться **только** если он реально взят из релевантного действующего правила. Нельзя молча уменьшать число полок, высоту ящичного блока или верхнюю секцию ради принятия операции.

Валидировать: положительные значения, конечные числа, толщина >0, высота зон, sum зон+разделителей = полезная внутренняя высота; отсутствие пересечений физических деталей; допустимость глубины/модуля; уникальность IDs. При ошибке состояние и `savedAt` не меняются.

# 07. ОДНА ГЕОМЕТРИЯ ВО ВСЕХ ПОТРЕБИТЕЛЯХ

Покрыть в рамках R02B:

**Исторические контрольные числа с legacy modules обязаны сохраниться.** Цена *нового* конструктивного разделителя вправе измениться согласно существующим ставкам, но не из-за дубля или неконтролируемой доплаты.
