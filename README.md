# InteriorAI Studio

B2B-конструктор интерьеров в реальном времени для дизайнеров и интерьерных студий.

Дизайнер сидит рядом с клиентом и голосом или текстом даёт команду:
«поставь угловой диван у окна, перед ним мраморный столик, под низ большой ковёр».
Gemini превращает это в точные координаты X/Y/Z и углы поворота, Three.js рендерит
сцену мгновенно. Вместо недели в 3ds Max — 10 секунд при клиенте.

**Ключевое отличие от обычных AI-визуализаторов:** модель выдаёт не картинку, а
пространственное решение — координаты, габариты, углы. Сцену можно крутить на 360°,
замерять и выгружать в смету.

## Пространственное соглашение

```
Единица измерения : МЕТР
Начало координат  : центр комнаты (0, 0, 0), пол Y = 0
X                 : слева направо,          -width/2  … +width/2
Z                 : от задней стены вперёд,  -depth/2  … +depth/2
Y                 : вверх,                   0         … height
position          : НИЖНИЙ ЦЕНТР объекта (bottom-center)
rotation          : в ГРАДУСАХ. rotationY = 0 → объект смотрит в +Z
```

Стены: `north` = z=-depth/2, `south` = z=+depth/2, `west` = x=-width/2, `east` = x=+width/2.

Правила высоты по `placement`: `floor` → 0, `floor_flat` → 0.01, `on_surface` →
высота опорного предмета, `wall` → своя высота, `ceiling` → `room.height`.

Подробности и ловушки — в [CLAUDE.md](CLAUDE.md).

## Как устроена защита от галлюцинаций

Модель не пишет в сцену напрямую. Любое её действие проходит через `applyActions`
в сторе и цепочку `createItem → resolveY → clampToRoom → resolveCollisions`.
Ковёр на высоте 1.5 м, диван за стеной и два кресла в одной точке физически
невозможны — правило высоты навязывается жёстко, объект зажимается по реальной
проекции с учётом поворота, пересечения расталкиваются итеративно.

## Интерфейс

- **Вьюпорт** — орбита мышью, гизмо перемещения и поворота, снимок кадра в PNG.
- **Ассистент** — чат с голосовым вводом (Web Speech API, `kk-KZ / ru-RU / en-US`).
  Под каждым ответом — чипы выполненных действий с координатами; в подсказке чипа
  лежит `reason`: почему объект встал именно сюда.
- **Объекты** — список сцены с координатами, числовые поля X/Y/Z, угол, габариты, цвет.
- **Комната** — габариты, цвета поверхностей, полный каталог.
- **Строка координат** внизу вьюпорта — имя объекта, X / Y / Z, угол, габариты.

Горячие клавиши: `G` перемещение, `R` поворот, `Delete` удалить, `Esc` снять
выделение, `Ctrl+Z` / `Ctrl+Y`.

## Фотореалистичный рендер

3D — это каркас, который держит геометрию. Продаётся фотография.

```
Сцена в 3D (геометрия точная)
   → чистый кадр из вьюпорта (без гизмо, сетки и выделения)
   → кадр уходит в Gemini как GEOMETRY_REFERENCE
   → шесть стилей генерируются параллельно
   → одна комната в шести вариантах, планировка везде идентична
```

Обычные AI-визуализаторы рисуют картинку с нуля, поэтому в каждом варианте
комната уезжает: окно смещается, стена укорачивается, клиент не узнаёт свой дом.
Здесь геометрия зафиксирована кадром — шесть вариантов это шесть стилей **одной
и той же** комнаты. Шторка «3D ↔ Рендер» в полноэкранном просмотре показывает
это клиенту напрямую.

Кнопка **«Визуализация»** снимает два кадра — цветной (LAYOUT_REFERENCE) и
clay-рендер серой геометрией (GEOMETRY_REFERENCE) — и шлёт шесть независимых
запросов. Упавший вариант показывается карточкой с ошибкой, остальные живут дальше.

Стили: скандинавский минимализм, тёплый минимализм, джапанди, современная
классика, лофт, премиум-модерн. Свой седьмой стиль клиент добавляет в
[lib/renderStyles.custom.ts](lib/renderStyles.custom.ts) без правок ядра.

Образцы материалов кладутся в `public/references/{категория}/{имя}.jpg` и
подхватываются автоматически (`npm run refs`, он же в `prebuild`). Без них
рендер идёт по текстовому описанию материалов из пресета стиля.

```env
GEMINI_IMAGE_MODEL=gemini-3.1-flash-image   # необязательно, это значение по умолчанию
```

## Каталог компании, замер и кабинет клиента

Платформа рассчитана на компании: мебельные фабрики, продавцов напольных
покрытий, керамогранита, дверей, ковров, потолков. Клиент в рендере должен
видеть **её артикул**, а не выдуманную моделью мебель.

### Универсальный каталог

Одна таблица `catalog_items` и поле `applies_to`:

| `applies_to` | Смысл | Примеры |
|---|---|---|
| `floor` | покрывает пол | паркет, ламинат, керамогранит |
| `wall` | покрывает стену | обои, панели, плитка |
| `ceiling` | покрывает потолок | натяжной, реечный |
| `zone` | занимает зону | кухонный гарнитур, шкаф-купе |
| `object` | отдельный предмет | диван, ковёр, стол |
| `opening` | встраивается в проём | дверь, окно, портал |

Новая товарная категория заводится через интерфейс и **не требует ни строчки
кода**. Единица измерения (`m2`, `piece`, `running_meter`, `set`) — тоже поле.

Товар загружается из 1С: `/admin/catalog` → «Импорт CSV». Колонки
`article, name, category_key, price, unit`. Парсер переживает BOM, разделитель
`;` и кодировку windows-1251 — именно так выгружает 1С.

Для покрытий сервер собирает **композитный референс**: кроп текстуры без
перспективы плюс полоска усреднённого цвета. Фотография чужой укладки не
годится — модель копирует чужую комнату вместе с её светом и мебелью.

### Фото → комната

`/api/ai/analyze-room` читает фотографию черновой отделки и возвращает состав
помещения: сколько окон, на каких стенах, где дверь, есть ли ниши.

**Модель не измеряет, а описывает.** По фотографии метры определяются с ошибкой
10–20 %, а для кухонного гарнитура промах в 40 см означает, что гарнитур не
встанет — а клиенту уже показали. Поэтому пропорции берутся с фото, абсолютные
размеры — из формы замера. При `confidence < 0.6`, непустых предупреждениях или
непрямоугольной планировке комната молча не строится: нужно ручное
подтверждение.

### Выбор материалов

Панель «Материалы»: категории каталога, карточки с превью, артикулом и ценой.
Назначенное покрытие подставляется в 3D-сцену **мгновенно**, до всякого
рендера — это половина эффекта на встрече. `zone` и `object` остаются
примитивом нужного габарита, подмена на реальный товар идёт в рендере.

В `BINDING TABLE` промпта уходят конкретные артикулы с композитными
референсами, а `GEOMETRY_LOCK` запрещает стилевому пресету их перекрашивать.
Стиль управляет только тем, что не выбрано в каталоге.

### Кабинет клиента

`/p/[token]` — публичная страница без авторизации, с логотипом и акцентным
цветом компании: варианты рендера, спецификация с ценами, шторка «3D ↔ Рендер»
и живая 3D-сцена, которую можно покрутить пальцем. Кнопка «Нравится» пишет
отметку в проект и уходит уведомлением в Telegram — это готовый горячий лид.
«Скачать PDF» использует системный диалог печати: он умеет сохранять в PDF и
не требует тащить кириллический шрифт в бандл.

### Настройка

```bash
# 1. Создать проект на supabase.com
# 2. Применить миграции по порядку, каждую отдельным запуском:
#    SQL Editor → 0001_catalog.sql → 0002_asset_role.sql
#                 → 0003_roles.sql → 0004_accounts.sql → Run
#    (0003 отдельно намеренно: Postgres не даёт использовать только что
#     добавленное значение enum в той же транзакции)
# 3. Заполнить ключи в .env.local (см. .env.local.example)
npm run dev
```

Первый вход: `/login` → ссылка на почту → создание компании → `/admin/catalog`.

Без ключей Supabase студия, чат и рендер по стилям работают как прежде;
каталог, проекты и кабинет клиента показывают понятное сообщение.

## Конфигуратор корпусной мебели

Ядро продукта: инструмент мебельной компании для продажи в первый визит.

```
Замерщик вносит замер  →  платформа предлагает три варианта гарнитура
   →  состав в миллиметрах, чертёж, полная смета
   →  правка текстом («убери пенал») или руками
   →  чертёж, смета и визуализация обновляются мгновенно
   →  клиент подписывает на месте
```

**Ни одно число в смете и чертеже не приходит от модели.** Gemini предлагает
только состав — какие модули и в каком порядке. Ширины, позиции, количество
фасадов, спецификацию материалов и стоимость считает код. Одна раскладка даёт
одну смету при любом числе пересчётов: если цена «плавает», компания подпишет
договор по неверной сумме.

Внутри движка мебели — целые миллиметры. Метры только на экране 3D.

| Вариант | Состав |
|---|---|
| Базовый | минимум модулей, ЛДСП-столешница, фурнитура стандарт |
| Оптимальный | кварц, доводчики, встроенная мойка и варочная |
| Премиум | до потолка с антресолью, Blum, подсветка, интегрированные ручки |

Раскладка у всех трёх одна: клиент сравнивает одну свою кухню в трёх бюджетах,
а не три разные кухни. Решение принимается быстрее.

**Ширина модуля вводится числом**, 150–1200 мм с шагом 1: мебель делают на
заказ, и сама раскладка выдаёт модули вроде 630 мм. Стандартные ширины стоят
рядом чипами. Нестандартная ширина принимается и подписывается спокойно —
«нестандартный модуль, изготавливается по размеру». Ширину техники диктует
прибор, её не изменить. Если запрошенная ширина не влезает, правка не
применяется вовсе и говорит, на сколько ряд вышел бы за стену: съедать
соседние модули ради чужой ширины нельзя.

**Вкладка 3D** — живая сцена, собранная из тех же `Module[]`, что чертёж и
смета. **Вкладка «Рендер»** снимает с неё кадр (beauty + clay) и отправляет
в модель три запроса — по одному на комплектацию:

```
Фото помещения клиента → окна, двери, стены, ракурс
Module[] → сцена → clay-кадр → раскладка модулей и техника
                              → три бюджета одной кухни
```

Основа кадра — **фотография помещения**, снятая замерщиком на обязательном
шаге замера (сжимается до 1600 px прямо в браузере). 3D-комната построена по
замеру, у неё нет ни окон клиента, ни его стен: рендер по ней даёт красивую
чужую кухню. С фотографией заменяются ровно две вещи — черновая отделка на
чистовую и пустая стена на гарнитур; окна и двери остаются на своих местах.
Ракурс кадра гарнитура подбирается под ракурс фотографии. Без снимка всё
работает по-прежнему, но интерфейс говорит прямо: «Без фото помещения клиент
увидит настроение, а не свою квартиру».

Три, а не шесть: клиент сравнивает бюджеты своей кухни, и это втрое дешевле.
Раскладка у всех трёх одна, поэтому кадр снимается один раз — геометрия
на всех трёх картинках совпадает до модуля. Материалы берутся из каталога:
выбранный артикул кухни даёт в BINDING TABLE три строки — фасады, столешница,
фартук. Пока артикул не выбран, интерфейс так и говорит: «материалы каталога
не выбраны», а рендер идёт по описанию комплектации.

**Чертёж** — вид спереди и план. Сквозная размерная цепочка в миллиметрах идёт
под лентой модулей, под чертежом и на плане: сумма отрезков сходится с длиной
ряда, и это видно глазом. Красный флажок на плане, если мойка не совпала с
выводом воды — переделку на объекте видно в квартире, а не на монтаже.

Печать — A4 альбомный, синька в чёрный, размерные линии не обрезаются.

`/demo` открывает готовый проект без входа: приложение никогда не показывает
пустой экран. Демонстрация собирается тем же `workspaceInput`, что и рабочий
объект, — иначе показанное на витрине разошлось бы с продаваемым продуктом.

## Зоны

Кухня, спальня, зал, санузел и прихожая. У каждой своя глубина, свои секции
(штанга, полки, обувница, ниша под ТВ, тумба под раковину), свои статьи сметы
и своё описание кадра для рендера. Шкаф-купе считается по м² полотна, санузел
— по влагостойкому корпусу, и ни в одной зоне не появляется строка, которой
там не бывает.

## Как это выглядит

Тёплая тёмная тема по умолчанию, светлая — переключателем в шапке; выбор
запоминается кукой и применяется на сервере, поэтому страница не мигает.
Один акцентный цвет (латунь) на весь продукт, шкала текста 13/15/17/22/32,
кнопки 44 px и 52 px у главной. Движений ровно три: нажатие кнопки,
появление карточки рендера и подсветка изменившегося числа в смете.

Снимки всех экранов в обеих темах на 1440 и 390 px снимает
`node scripts/check-design.mjs` — он же говорит, где текст мельче 13 px,
где цель касания меньше 44 px и где строка уезжает за край.

## Куда ведёт корень

`/` открывает список объектов вошедшему и страницу входа остальным. Студия
со спатиальным чатом и 3D-сценой осталась в `app/(legacy)/studio` как стенд
движка: продукт — конфигуратор корпусной мебели, и лишний вход в интерфейсе
только путает.

## Один экран — одна задача

Работа идёт последовательностью, а не набором вкладок:

```
Замер → Шаблон → Состав → Материалы → Результат
```

Сверху полоса шагов с отметками пройденного (кликом можно вернуться), внизу
одна главная кнопка и одна вторичная. Смета не занимает места постоянно:
внизу строка «Оптимальный · 1 839 564 ₸ · подробнее», таблица открывается
тапом. Три бюджета показываются на «Результате» крупными карточками, там же
чертёж, план, 3D и рендер — четырьмя кнопками.

**Шаблоны.** Замерщик не собирает кухню из модулей: он берёт типовое решение
и правит длину. Шесть встроенных конфигураций (прямая компактная, прямая
стандартная, прямая с колонной, угловая компактная, угловая с колоннами,
П-образная) плюс свои у компании — они заводятся на `/admin/templates` и
показываются первыми с пометкой «ваш». Неподходящий по длине шаблон выключен
и объясняет почему: «Нужен ряд от 3000 мм». Шаблон задаёт только состав
техники: раскладку по-прежнему считает тот же `buildRun`, поэтому схема на
карточке не может разойтись с чертежом и сметой.

**«До и после».** На шаге «Результат» — сравнение: слева фотография
помещения клиента, справа выбранная комплектация, шторка тянется пальцем.
Пока рендера нет, правая половина честно говорит, что нажать; пока нет
фотографии — предлагает её добавить. Тот же блок стоит в кабинете клиента:
там он доказывает, что окна и двери остались на своих местах. Техническая
3D-сцена ушла в одну из четырёх кнопок вида, наверху её больше нет.

**Плотность.** Палитра синьки осталась, но текст стал 15 px, кнопки 48 px,
поля 56 px, панели читаются перепадом плоскостей, а не рамкой в пиксель.
Проверено на 768 и 390 px: горизонтальной прокрутки нет нигде, кроме ленты
модулей, все цели нажимаются пальцем. Чертёж не тронут — там плотность
оправдана, это технический документ.

## Режим замерщика

Замер и конфигурация — один экран. Замерщик стоит в квартире с планшетом
в одной руке и разговаривает с клиентом; он не заполняет анкету, а записывает
по ходу разговора. Слева ввод по порядку обхода помещения (высота потолка →
стены по кругу → проёмы → коммуникации → фото), справа план, который
дорисовывается вместе с вводом. Как только задана длина стены, на ней
появляется предварительный ряд модулей: видно, что помещается, ещё до конца
обхода.

**Система не выглядит уверенной там, где не знает.** У каждой величины три
состояния:

| состояние | как выглядит |
|---|---|
| замерено | обычное число |
| принято по умолчанию | приглушённый цвет, пунктир, подпись «стандартная высота подоконника — 850 мм» |
| не замерено | так и написано: «не замерено» |

Подставленное число никогда не выглядит как замеренное: на чертеже размер из
допущения идёт пунктиром со звёздочкой, в смете стоит «Итого · предварительно»,
а внизу чертежа и в кабинете клиента — строка «Позиции, требующие уточнения на
объекте: …» или «Все размеры сняты на объекте». Точной смета называется только
тогда, когда все величины сняты.

**Предупреждения — по последствиям.** Красное мешает отправить клиенту (ряд
длиннее стены, гарнитур поперёк двери, мойка дальше 600 мм от вывода воды),
жёлтое не мешает работать (розетка не отмечена, подоконник принят по
умолчанию), информационное не показывается вовсе и уходит в примечания
чертежа. На экране одновременно не больше трёх, остальные — под «ещё N».
Формулировка называет последствие: не «розетка не отмечена», а «монтажник не
будет знать, где её выводить».

Кнопка **«Замер завершён»** показывает сводку: габариты, проёмы, коммуникации,
сколько величин замерено / принято / не замерено, что осталось уточнить —
с кнопкой «Дозамерить». Этот же экран печатается как **замерный лист** на A4
с местом для двух подписей: клиент подписывает его прямо на объекте.

Панель работает **без сети**: состояние пишется на планшет до запроса и
уходит на сервер по возвращении связи. В новостройке интернета часто нет,
а второй выезд на объект стоит денег.

## Аккаунты, объекты и сделка

Вход по ссылке на почту, паролей нет: замерщик открывает приложение стоя,
в чужой квартире, с планшетом в одной руке. Первый вошедший заводит компанию
и становится её владельцем; остальных он приглашает по адресу почты на
`/admin/team` с ролью «Менеджер» или «Замерщик». Приглашение принимается само
в момент первого входа приглашённого.

```
/login  →  /projects  →  «Новый объект»  →  /measure (адрес, контакт, стены)
        →  /project/[id] — конфигуратор с автосохранением
        →  «Отправить клиенту»  →  /p/[token] + ссылка в WhatsApp
```

**Объекты** (`/projects`) — карточки с адресом, зоной, замерщиком, датой,
суммой выбранного варианта и статусом: Замер → Расчёт → Отправлено клиенту →
Согласовано → В производстве. Статус переключается прямо в карточке, список
фильтруется по нему.

**Автосохранение** — через 2 секунды после последнего изменения, с индикатором
«Сохранено» в шапке. Состояние пишется целиком: состав модулей по каждому
варианту, выбранный вариант, снятые галочки сметы и снимок цен на дату расчёта.
Объект открывается ровно таким, каким его закрыли, — пересчёт по изменившемуся
каталогу дал бы другую сумму, и подписанный документ разошёлся бы с тем, что
видел клиент.

**Клиент по ссылке** видит тот же чертёж, тот же состав и ту же сумму: кабинет
собирает варианты по сохранённому снимку цен и ничего не пересчитывает. Кнопка
«Мне подходит» ставит объекту статус «Согласовано» и уходит уведомлением
в Telegram.

**Цены каталога обязательны.** Без ставок конфигуратор говорит «Заполните цены
каталога, чтобы считать смету» и даёт ссылку. Кнопка «Загрузить типовой прайс»
в `/admin/catalog` ставит средние по рынку — она подписана как ориентир, а не
как цены компании, и уже заведённые цены не трогает. Товар попадает в смету
по колонке «Ключ сметы» (`meta.estimateKey`): пока ключ пуст, строка не
считается.

## Проверка

```bash
npm run typecheck      # tsc --noEmit
npm run test:spatial   # пространственное соглашение
npm run test:catalog   # CSV из 1С, спецификация, фото → комната
npm run test:millwork  # раскладка, смета, варианты, коммуникации
npm run test:survey    # состояния величин, отпечаток конфигурации, предупреждения
npm run build
npm run test:capture   # захват кадра в реальном браузере (нужен build)
npm run test:demo      # прогон демонстрации: пять шагов сценария продажи
npm run test:rls       # мультиарендность (нужны ключи Supabase)
npm run test:render    # живой рендер (тратит запросы к модели)
npm run verify         # всё, кроме test:rls и test:render
```

`test:rls` создаёт две организации с двумя пользователями и проверяет, что
участник одной не видит и не может править другую, а анонимный запрос не
отдаёт ничего. Без ключей честно пишет «мультиарендность НЕ проверена».

`test:capture` поднимает production-сервер, гоняет headless Chromium с WebGL и
проверяет: в кадре нет ни одного служебного элемента, clay-проход обесцвечен,
размер вьюпорта восстановился, кадр весит меньше 800 КБ, один намеренно
сломанный вариант не мешает остальным дойти до `done`, а без ключа все шесть
карточек показывают ошибку и интерфейс не падает.

`test:spatial` проверяет: ковёр на Y=0.01, диван на Y=0, подвес на Y=height,
зажим позиции (99, 0, -99) внутрь комнаты, зажим повёрнутого дивана по реальной
проекции, ТВ на тумбе на Y=0.45, расталкивание кресел, и что ковёр не считается
пересечением ни с чем.

## Деплой на Vercel

Импортировать репозиторий, добавить `GEMINI_API_KEY` и `GEMINI_MODEL` в Environment
Variables. Роут `/api/ai/spatial` объявляет `maxDuration = 60` и обрывает запрос к
Gemini на 50 секундах — это потолок Hobby-плана.
