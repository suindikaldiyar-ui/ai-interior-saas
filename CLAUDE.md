# InteriorAI Studio — заметки для агента

Конструктор интерьеров в реальном времени. Дизайнер даёт команду голосом или
текстом, Gemini возвращает **пространственное решение** (координаты, габариты,
углы), Three.js рендерит сцену мгновенно.

## Главное свойство продукта

Модель выдаёт **не картинку, а числа**. Сцену можно крутить на 360°, замерять и
выгружать в смету. Любая правка, которая превращает вывод в изображение или
размывает координаты, ломает продукт. Не делай так.

## Пространственное соглашение

Единственный источник правды — комментарий в начале [types/interior.ts](types/interior.ts).

```
Единица измерения : МЕТР
Начало координат  : центр комнаты (0, 0, 0), пол Y = 0
X                 : слева направо,          -width/2  … +width/2
Z                 : от задней стены вперёд,  -depth/2  … +depth/2
Y                 : вверх,                   0         … height
position          : НИЖНИЙ ЦЕНТР объекта (bottom-center)
rotation          : в ГРАДУСАХ. rotationY = 0 → объект смотрит в +Z
```

Стены: `north` = z=-depth/2, `south` = z=+depth/2, `west` = x=-width/2, `east` = x=+width/2.

### Правила высоты (`placement`)

| placement | Y | Примеры |
|---|---|---|
| `floor` | 0 | диван, стол, шкаф, растение, торшер |
| `floor_flat` | 0.01 | ковёр |
| `on_surface` | высота опорного предмета | ТВ на тумбе, ваза на столе |
| `wall` | своя высота | керамогранитная панель, картина |
| `ceiling` | room.height | подвесной светильник |

Высоты поверхностей — `SURFACE_HEIGHT` в [types/interior.ts](types/interior.ts):
`coffee_table=0.42`, `dining_table=0.75`, `tv_unit=0.45`, `nightstand=0.55`, `side_table=0.55`.

### Единственное исключение из bottom-center

`placement: 'ceiling'`. Подвес крепится к потолку, поэтому его origin — **точка
подвеса** (`y = room.height`), а геометрия уходит **вниз**, в отрицательный
локальный Y. См. `PendantLamp` в [components/FurnitureMesh.tsx](components/FurnitureMesh.tsx).
Габаритный каркас выделения для таких объектов тоже смещён вниз (`boxCenterY`).

Из-за bottom-center **каждый меш мебели строится от нуля своей группы вверх**.
Никаких `position={[0,0,0]}` для боксов — только `[0, h/2, 0]`.

## Фаза 2: 3D как каркас, продаётся фотография

Сцена геометрически точна, но выглядит как серые коробки. Поэтому 3D — это
**каркас, который держит геометрию**, а клиенту показывается фотография:

```
Сцена → чистый кадр из вьюпорта → GEOMETRY_REFERENCE для Gemini
      → шесть стилей параллельно → одна комната в шести вариантах
```

Конкуренты генерируют картинку с нуля, поэтому комната уезжает от варианта к
варианту. Здесь геометрия зафиксирована кадром. **Не сломай это свойство.**

### Захват кадра

`captureMode: true` убирает из сцены гизмо, каркас выделения, кольцо-след,
подсветку при наведении и `Grid`. `ContactShadows` остаётся — это часть картинки,
но гасится в clay-проходе по имени группы `CONTACT_SHADOWS_NAME`.

**Ждать `requestAnimationFrame` после `setCaptureMode(true)` нельзя.** rAF не
связан с коммитом React: захват успевал снять кадр до того, как хелперы уходили
из графа сцены, и гизмо с оранжевым каркасом попадали в рендер. Правильный
сигнал — `useEffect` в `SceneCapture`, он выполняется строго после commit-фазы,
когда R3F уже применил все удаления объектов. См. `committedRef`.

### `applyActions` — единственная дверь для AI

Модель **никогда** не пишет в сцену напрямую. Каждое действие проходит цепочку:

```
createItem → resolveY → clampToRoom → resolveCollisions
```

Если Gemini выдаст ковёр на Y=1.5 или диван за стеной — сцена всё равно останется
корректной. Не добавляй обходных путей мимо `applyActions`.

## Ловушки — не наступай

1. **Селектор Zustand не должен возвращать новый объект** (`s => ({a, b})`) —
   бесконечный ререндер. Один селектор на одно поле.
2. **`RoomCanvas` только через `dynamic(..., { ssr: false })`** — WebGL на сервере нет.
3. **`Environment` — со своими детьми, не `preset`.** `preset="apartment"` тянет
   HDRI из интернета и вешает сцену без сети.
4. **Радиус `RoundedBox` зажимай хелпером `rr()`** — тонкие объекты (ковёр 2 см,
   экран ТВ 6 см) выворачиваются наизнанку.
5. **Не создавай геометрию внутри `args={[new THREE.BoxGeometry(...)]}`** — новый
   объект каждый рендер. Только `useMemo` + проп `geometry`. Декларативный
   `<boxGeometry args={[w,h,d]} />` — норма, R3F пересоздаёт его только при смене args.
6. **Гизмо коммитит в стор на `onMouseUp`**, не на `objectChange` — иначе дребезг
   и мусор в истории undo.
7. **`maxDuration = 60` и таймаут 50 с** — потолок Vercel Hobby.
8. **Версии зафиксированы:** `@react-three/fiber` v8 + `drei` v9. Линия v9/v10 —
   это React 19, с Next 14 падает. Next держи на 14.2.35+.
9. **Все повороты в данных — в градусах**, перевод в радианы только в момент
   рендера через `deg()`.
10. Стены рендерятся `side={THREE.FrontSide}` нормалями внутрь — снаружи они
    исчезают, получается архитектурный разрез. Не меняй на `DoubleSide`.

## Фаза 3: каталог, фото → комната, кабинет клиента

Платформа перестала быть личным инструментом и стала продуктом для компаний.
Клиент в рендере должен видеть **её артикул**, а не выдуманную моделью мебель.

### Универсальная модель каталога

Одна таблица `catalog_items` + поле `applies_to`
(`floor` / `wall` / `ceiling` / `zone` / `object` / `opening`) и поле `unit`.
Новая товарная категория — ковры, двери, кухни, потолки — заводится через
интерфейс и **не требует ни строчки кода**.

**Как только появится вторая специализированная таблица (`kitchens`, `doors`),
платформа перестанет быть универсальной.** Не заводи их.

### Композитный референс

Для покрытий в модель уходит не фотография укладки, а `kind='composite'`:
кроп текстуры без перспективы плюс полоска усреднённого цвета, собирается
на сервере в [lib/composite.ts](lib/composite.ts) при загрузке файла.
Фотография чужой комнаты копируется моделью вместе с её светом и мебелью.

### Пропорции с фото, метры с замера

Зрение НЕ измеряет, а описывает: ошибка по фото 10–20 %, для кухонного
гарнитура это промах в 40 см. `estimatedRatio` — пропорция, абсолютные размеры
приходят из формы замера. См. [lib/roomFromAnalysis.ts](lib/roomFromAnalysis.ts).
`confidence < 0.6`, непустые `warnings` или непрямоугольная планировка требуют
ручного подтверждения — молча строить комнату нельзя.

### selections

`targetKey → catalog_item_id`, где targetKey это `floor`, `wall:north`,
`ceiling`, `zone:kitchen` или id объекта сцены. Хранится **ссылка, а не копия
товара**: компания поменяла цену — проекты подтянут актуальную.

Покрытия (`floor`/`wall`/`ceiling`) подставляются в 3D мгновенно как `map`
материала. Это половина эффекта на встрече с клиентом. `zone`/`object`/`opening`
остаются примитивом-заглушкой, подмена происходит в рендере через референс.

### Ловушки фазы 3

19. **Одна `catalog_items` + `applies_to`.** Никаких таблиц под кухни и двери.
20. **Пропорции из фото, абсолютные размеры из замера. Никогда наоборот.**
21. **Текстуры из Storage — лениво и через кэш** ([lib/textureCache.ts](lib/textureCache.ts)),
    иначе каждое переключение материала уходит в сеть.
22. **`selections` хранит id, а не копию товара.**
23. **RLS проверять запросом от чужого `org_id`** — `npm run test:rls`.
    Мультиарендность без теста это не мультиарендность.
24. **`share_token` — 24 случайных байта**, не последовательный id.
25. **CSV из 1С**: BOM, разделитель `;`, кодировка windows-1251. Всё три случая
    разбираются в [lib/csv.ts](lib/csv.ts) и покрыты `npm run test:catalog`.
26. **`SUPABASE_SERVICE_ROLE_KEY` никогда не префиксовать `NEXT_PUBLIC_`.**
    Он обходит RLS целиком.
27. **Не импортируй supabase-js и three в основной бандл страницы.**
    `CatalogLoader` и `textureCache` подключаются динамически — статический
    импорт раздувал первую загрузку с 115 кБ до 353 кБ.

## Слой 4: конфигуратор корпусной мебели

Ядро продукта. Инструмент мебельной компании для продажи в первый визит:
замерщик приезжает в квартиру, вносит замер, платформа предлагает три
варианта гарнитура, клиент подписывает на месте.

### ГЛАВНОЕ ПРАВИЛО СЛОЯ

**Ни одно число в смете и чертеже не приходит от модели.**

```
Gemini  → предлагает РАСКЛАДКУ (какие модули, в каком порядке)
Код     → валидирует, сажает на стандартные ширины, разрешает коллизии
Код     → считает BOM, метраж, фурнитуру, стоимость
Код     → строит чертёж
```

Одна раскладка обязана давать одну смету при любом числе пересчётов.
Если цена «плавает» — компания подпишет договор по неверной сумме и
потеряет деньги на своём производстве. После этого платформа для неё мертва.

Внутри движка мебели — **целые миллиметры**. Метры только на экране 3D.

### Детерминизм

`buildRun` — чистая функция. Никакого `Math.random`, никаких дат внутри
расчёта, никакой зависимости от порядка ключей объекта. Идентификатор модуля
выводится из позиции и роли, а не из счётчика: при пересчёте тот же модуль
получает тот же id, и выделение на чертеже не слетает.
Проверяется сотней прогонов в `npm run test:millwork`.

### Стандарты не параметризуются

`lib/millwork/modules.ts`: ширины фасадов, `GEOMETRY`, `APPLIANCE_SLOTS`.
Из интерфейса они не меняются — дизайнер не должен иметь возможности
сделать столешницу на высоте 1.1 м.

### Ширина модуля вводится числом

Корпусную мебель делают на заказ: `buildRun` сам раздаёт остаток и создаёт
модули вроде 630 мм — из списка стандартов такое не набрать. Поэтому ширина
это числовое поле 150…1200 мм с шагом 1, а `STANDARD_WIDTHS` — чипы быстрого
выбора. Нестандартная ширина принимается и подписывается спокойно
(«нестандартный модуль»), а не краснеет: краснеет только `kind === 'filler'`,
вынужденная доборная планка.

Ширина техники не редактируется никогда — её диктует прибор.

Инвариант проверяется **до** применения: `widthOverflowMm` считает минимально
возможную сумму (техника, пеналы и углы держат габарит, обычные модули
ужимаются до `MIN_WIDTH`) и, если она уже больше длины ряда, правка
отклоняется целиком с указанием превышения. Съедать соседние модули ради
чужой ширины нельзя — клиент увидел бы не тот состав, который заказывал.

### Рендер комплектации

```
Module[] → KitchenScene сеет сцену в стор → KitchenUnit строит меш
        → captureScene (beauty + clay) → один запрос /api/ai/render
```

**Комплектация одна.** Сначала было шесть стилей, потом три бюджета, теперь
один вариант: клиент начинал сравнивать картинки вместо того, чтобы решать,
а три средних рендера продают хуже одного сильного. Комплектация меняется
переключателями состава (столешница, фурнитура, антресоль), а не выбором
из карточек.

Стратегии `basic` и `premium` живы в [lib/millwork/variants.ts](lib/millwork/variants.ts):
вернуть три бюджета — это флаг `SINGLE_VARIANT`, а не восстановление кода.

### Основа рендера — фотография клиента

```
Фото помещения (IMAGE 1) → окна, двери, стены, ракурс
clay-кадр гарнитура (IMAGE 2) → раскладка модулей и техника
beauty (IMAGE 3), артикулы каталога (IMAGE 4+) → материалы
```

3D-комната построена по замеру: у неё нет ни окон клиента, ни его стен.
Рендер по ней даёт красивую чужую кухню — клиент не узнаёт квартиру, а
узнавание и есть половина продажи. Поэтому снимок помещения снимается на
шаге замера (обязательный шаг, сжатие до 1600 px и JPEG **на клиенте** —
с телефона иначе поедут мегабайты), хранится в Storage,
путь в `projects.source_photo_path`.

Заменяются ровно две вещи: черновая отделка на чистовую и пустая стена на
гарнитур. Проёмы не двигаются и не дорисовываются: в споре о них clay-кадр
проигрывает фотографии — он собран по замеру и может показывать окно там,
где его нет.

Без фотографии всё работает как раньше, но интерфейс говорит прямо:
«Без фото помещения клиент увидит настроение, а не свою квартиру».

Кадр снимается ракурсом `run` ([lib/cameraFraming.ts](lib/cameraFraming.ts)):
в кухне 3.2 × 2.4 м точки, с которой виден весь ряд, попросту нет, поэтому
камера отходит ЗА стену — стены отрисованы нормалями внутрь и снаружи
исчезают. «Геройская» точка вставала вплотную к столешнице, и холодильник
с духовой колонной в кадр не попадали.

Одного clay-кадра модели мало: в пенале она узнаёт «место для духовки» и
дорисовывает прибор туда, где по чертежу глухой фасад. Поэтому в промпт
уходит блок **СОСТАВ ГАРНИТУРА** — список модулей слева направо с ширинами
и содержимым плюс запрет на технику вне списка. Числа здесь идут в модель
как ограничение; смету по-прежнему считает код.

Ракурс clay подбирается под ракурс фотографии («снимать как на фото»:
фронтально, от левого или от правого угла). Если кадры сняты с разных точек,
модель мирит два ракурса и мнёт геометрию.

Стиль подобран под бюджет (`VARIANT_STYLE`), а отличия комплектации уходят
словами в `customNotes` — числа держит кадр, а не текст. Материалы берутся
из `selections`: артикул кухни даёт в BINDING TABLE три строки — фасады,
столешница, фартук. Пока артикул не выбран, интерфейс прямо говорит
«материалы каталога не выбраны»: клиент увидит настроение, а не ваш товар.

### Ловушки слоя 4

28. **Якорь садится не дальше, чем позволяет остаток под ещё не поставленные.**
    Без резерва техника встаёт по желаемым позициям, между ней остаются
    промежутки, и хвост ряда вылезает за стену — хотя по сумме ширин всё
    помещалось. Это ловил `test:millwork` на рядах 1800 и 2400 мм.
29. **Сумма ширин обязана сходиться с длиной ряда до миллиметра —
    в режиме шаблона.** После любой правки `rebalance` перезаполняет
    место. В свободной сборке (`RunRequirements.mode = 'free'`) правило
    другое: ряд имеет право не сходиться, остаток показывается числом,
    и `rebalance` не вызывается вовсе. См. слой 29.
30. **Ставки — из `catalog_items` организации, не из кода.** В сохранённой
    смете лежит снимок цен на дату расчёта: переоценка каталога не должна
    менять подписанный документ.
31. **Модель возвращает операции над списком модулей, а не числа.**
    Ручное и текстовое редактирование работают с одним списком и не конфликтуют.
32. **`KitchenUnit` строит меш из `Module[]`** (`item.meta.runModules`), а не
    из собственной разбивки — иначе 3D и чертёж покажут разную мебель.
33. **Верхний ряд разрывается на участке окна.** Шкафы поперёк окна — грубая
    ошибка, которую клиент замечает мгновенно.
34. **`module` — зарезервированное имя в Next.** В коде раскладки переменная
    называется `unit`, иначе сборка падает на `no-assign-module-variable`.
35. **Красный флажок при расхождении с коммуникацией — это функция, а не шум.**
    Мойка в 900 мм от вывода воды — переделка на объекте; увидеть её надо
    в квартире, а не на монтаже.
36. **Ширина модуля — число, а не список.** Стандарты остаются подсказкой.
    Проверка «влезает ли» идёт ДО применения (`widthOverflowMm`), иначе
    `rebalance` тихо ужмёт соседей и покажет клиенту не тот состав.
37. **Сцена конфигуратора сеется через стор, а не мимо него.** Там же живут
    захват кадра и рендер; вторая сцена рядом с первой разъедется с чертежом.
38. **`modulesFromRun` обязана пробрасывать `kind` и высоту.** Пенал,
    потерявший `kind`, превращается в 3D в нижний модуль, духовка уезжает
    под столешницу — и рендер показывает клиенту не ту кухню, что чертёж.
    Ловилось только глазами: тесты видели «7 модулей и там, и там».
39. **Фотография помещения главнее clay-кадра.** Окна и двери берутся
    только с неё; верхний ряд описывается участками (`runUppers`), иначе
    модель достраивает сплошной ряд шкафов через всю стену.
40. **Фото сжимается на клиенте.** 4–12 МБ с телефона не должны уезжать
    ни в Storage, ни в запрос к модели.
41. **`KitchenScene` подключается только `dynamic(ssr:false)`.** Статический
    импорт затащил бы three.js в бандл конфигуратора, который обязан
    открываться быстро на планшете.

### Ловушки фазы 2

11. **Ждать коммит React, а не rAF.** См. раздел о захвате выше — это тот самый
    баг, из-за которого гизмо уезжало в рендер.
12. **JPEG, не PNG.** PNG на 1536×1024 в base64 — 3–5 МБ и гарантированный 413.
    Качество 0.92 даёт 60–130 КБ.
13. **Размеры рендерера восстанавливай в `finally`.** Иначе упавший захват
    оставит вьюпорт 1536×1024 и вёрстка поедет.
14. **Шесть вариантов — шесть отдельных вызовов роута.** Внутри одного запроса
    они не уместятся в 60 с Vercel Hobby.
15. **`inlineData` и `inline_data`** — разные версии API отдают ключ по-разному,
    разбирай обе формы.
16. **Ракурс по умолчанию одинаков для всех вариантов**, иначе сравнивать нечего.
17. **`lib/captureRegistry.ts` не должен импортировать three.** Иначе страница
    статически тянет three.js в основной бандл, и `dynamic(ssr:false)` у
    `RoomCanvas` перестаёт что-либо экономить (проверено: 20 кБ → 232 кБ).
18. **Один набор вариантов в памяти.** `startRenderBatch` заменяет предыдущий
    целиком: шесть base64-картинок — это десятки мегабайт во вкладке.

## Ключ Gemini

Передавать **заголовком `x-goog-api-key`**, а не параметром `?key=` в URL:
новый формат ключей через URL не проходит. Вся обвязка — `lib/gemini.ts`,
там же `parseImageResponse` с обеими формами ключа (`inlineData` и
`inline_data`): переезд на другой эндпоинт стоит правки одного файла.

Модели: текст и зрение — `gemini-3.6-flash`, изображение — `gemini-3.1-flash-image`.

## Слой 5: из демонстрации в рабочий продукт

Вход только по ссылке на почту. Паролей нет намеренно: замерщик стоит в чужой
квартире с планшетом в одной руке — вводить туда пароль неудобно, а
восстанавливать забытый некогда. Первый вошедший заводит компанию и становится
её владельцем, остальных он приглашает по адресу почты.

### Ловушки слоя 5

42. **Состояние конфигуратора хранится целиком, а не «параметрами для
    пересчёта».** Объект обязан открыться ровно таким, каким его закрыли:
    пересчёт по изменившемуся каталогу дал бы другую сумму, и подписанный
    документ разошёлся бы с показанным клиенту.
43. **Новые значения `enum` — отдельной миграцией.** Postgres не даёт
    использовать только что добавленное значение в той же транзакции:
    `default 'surveyor'` падает с «unsafe use of new value». Поэтому
    `0003_roles.sql` коммитится раньше `0004_accounts.sql`.
44. **Приглашение принимается при первом входе, сервисным ключом.** У
    приглашённого ещё нет членства, а значит и прав ни на одну строку
    организации. Проверка одна и её достаточно — совпадение подтверждённой
    почты с адресом приглашения.
45. **Товар не существует без категории.** `catalog_items.category_id` —
    NOT NULL, поэтому «Загрузить типовой прайс» СНАЧАЛА заводит недостающие
    категории (`ensureCategories`), и только потом вставляет товары. Список
    зон однажды уехал вперёд категорий — четыре ключа (`wardrobe`,
    `hallway`, `living`, `bath`) были в позициях и не были в категориях, —
    и загрузка на пустом каталоге падала целиком. Расхождение ловит
    `orphanTypicalRates` и `npm run test:catalog`.
46. **Существующие категории не трогаем.** Соблазн сделать `upsert` одной
    строкой переписывает компании её собственные название, единицу и
    `applies_to` по совпадению ключа. Заводим только то, чего нет.
47. **Смета без ставок каталога не считается.** Конфигуратор говорит
    «Заполните цены каталога» и даёт ссылку. Кнопка «Загрузить типовой прайс»
    ставит средние по рынку и **подписана как ориентир**, а не как цены
    компании; уже заведённые цены она не трогает.
48. **Демонстрация и рабочий объект идут через один `workspaceInput`.** Две
    похожие функции разъезжаются, и демо начинает показывать не тот продукт,
    который продают.
49. **Автосохранение — через паузу после последнего изменения**, а не на
    каждый клик. Индикатор в шапке обязателен: замерщик не должен гадать,
    сохранилось ли.

## Слой 6: режим замерщика на объекте

Замер и конфигурация — ОДИН экран. Замерщик стоит в чужой квартире с планшетом
в одной руке и разговаривает с клиентом: он не заполняет анкету, он ведёт
разговор и записывает по ходу. Слева ввод, справа план, который дорисовывается
вместе с вводом; как только задана длина стены ряда, на ней появляется
предварительный ряд модулей.

### Система не выглядит уверенной там, где не знает

```ts
type Known<T> =
  | { state: 'measured'; value: T }
  | { state: 'assumed'; value: T; basis: string }
  | { state: 'unknown' };
```

Замерщик показывает этот экран клиенту, и всё, что на нём написано, клиент
примет за факт. Поэтому пустое поле — это «не замерено», а не ноль;
подставленное число помечается `assumed`, идёт приглушённым цветом с пунктиром
и объясняет, откуда взялось; на чертеже размер из допущения идёт пунктиром со
звёздочкой — это отраслевая норма и читается без пояснений.

Неизвестное превращается в число ровно в одном месте — `resolveSurvey`
([types/survey.ts](types/survey.ts)), и превращается в **допущение**, а не
в замер. Точной смета называется, только когда все величины `measured`;
`affectsQuantity` управляет формулировкой («сумма изменится» против «размеры
требуют подтверждения»), а не статусом.

### Предупреждения по последствиям

`lib/millwork/warnings.ts` делит их на три класса:

| класс | цвет | что делает |
|---|---|---|
| `blocking` | красный | мешает отправить клиенту: ряд длиннее стены, гарнитур поперёк двери, мойка дальше 600 мм от вывода воды |
| `clarify` | жёлтый | не мешает работать: розетка не отмечена, вентканал не отмечен, подоконник принят по умолчанию |
| `info` | — | на экране не показывается вовсе, уходит в примечания чертежа |

На экране одновременно не больше двух, остальные — под «ещё N». Формулировка
называет последствие, а не факт: не «розетка не отмечена», а «монтажник не
будет знать, где её выводить».

### Отпечаток конфигурации

`configurationFingerprint` ([lib/millwork/fingerprint.ts](lib/millwork/fingerprint.ts))
считается от последовательности `{kind, widthMm, appliance, frontCount}` и
лежит в `Run` и в `Estimate`; сцена кладёт его в `meta.fingerprint`, а рендер
сверяет перед отправкой. Расхождение — исключение, а не предупреждение.

Сверять по числу модулей мало: ровно так прошёл баг с потерянным `kind`, когда
пенал приезжал в 3D нижним модулем, а «7 модулей и там, и там» сходилось.

### Ловушки слоя 6

48. **Ни одно неизвестное не заменяется удобным числом молча.** Пустое поле —
    «не замерено», подстановка — только через `resolveSurvey` и только
    с пометкой `assumed` и объяснением.
49. **`assumed` отличается от `measured` визуально везде:** экран, чертёж,
    замерный лист, смета, кабинет клиента. Одинаковый вид — это обман.
50. **Смета с допущениями подписана «предварительная».** Точная — только
    когда всё замерено.
51. **Не больше двух предупреждений на экране одновременно.** Десяток строк
    превращается в фон, который не читает никто.
52. **Совпадение чертежа, сметы и рендера проверяется отпечатком, а не числом
    модулей.**
53. **Панель замера работает без сети.** Состояние пишется в `localStorage`
    до запроса, отправка повторяется по событию `online`: в новостройке
    интернета часто нет, а второй выезд на объект стоит денег.
54. **Два `patch()` подряд собираются из одного снимка состояния** — второй
    затирает первый. Ловилось тем, что добавленный проём исчезал сразу после
    добавления; правки замера идут ОДНИМ вызовом `onChange`.

## Слой 7: один экран — одна задача

Шесть вкладок, лента модулей, панель сметы, двадцать предупреждений и
командная строка одновременно — экран, который невозможно объяснить замерщику
за пять минут. Вместо них последовательность:

```
Замер → Шаблон → Состав → Материалы → Результат
```

Сверху полоса шагов с отметками пройденного, внизу — одна главная кнопка
«Дальше» и одна вторичная «Назад». Итог сметы свёрнут в строку
(«Оптимальный · 1 839 564 ₸ · подробнее»), таблица открывается тапом и
закрывается тапом мимо. Три варианта показываются только на «Результате»
крупными карточками; чертёж, план, 3D и рендер — четырьмя кнопками там же.

### Шаблоны — главное упрощение

Замерщик не собирает гарнитур из модулей: в девяти случаях из десяти он
берёт типовое решение и правит длину. [lib/millwork/templates.ts](lib/millwork/templates.ts) —
шесть встроенных конфигураций плюс свои у компании (`orgs.run_templates`,
экран `/admin/templates`, показываются первыми с пометкой «ваш»).

Шаблон задаёт СОСТАВ ТЕХНИКИ и сторону колонн. Своей раскладки у него нет —
модули по-прежнему считает `buildRun` по длине из замера, иначе схема на
карточке разошлась бы с чертежом и сметой. Неподходящий по длине шаблон
выключен и объясняет почему: «Нужен ряд от 3000 мм».

### Плотность

Базовый текст 15 px, межстрочный 1.55, шкала 13 / 15 / 17 / 22 / 32.
Радиусы 14 px у панелей и 10 px у кнопок и полей, отступ в панелях 24 px,
между блоками 20 px, высота кнопки 44 px и 52 px у главной, поля 52 px.
Панели читаются перепадом плоскостей (`--surface` на `--bg`), а не линией
в один пиксель. Утилитарные классы `.mw-btn`, `.mw-field`, `.mw-panel`
лежат в `@layer components` — иначе `display` из `.mw-btn` перебивает
утилиту `hidden`, и кнопка остаётся видимой там, где её прячут.

**Чертёж под это правило не подпадает**: там мелкий шрифт уместен, это
технический документ.

### «До и после» вместо технической сцены

На шаге «Результат» вверху стояла маленькая 3D-сцена. Клиенту она не давала
ничего: это служебный вид для захвата кадра. Её место занял блок сравнения
([components/millwork/BeforeAfter.tsx](components/millwork/BeforeAfter.tsx)) —
слева фотография помещения, справа выбранная комплектация, между ними шторка
на Pointer Events. Тот же блок стоит в кабинете клиента и работает там
главным доказательством: окна и двери на месте, поехала только отделка.

Сцена при этом остаётся смонтированной — она уезжает за экран
(`fixed left-[-3000px]`), иначе кадр снимать будет нечем. `display: none`
здесь не годится: канвас нулевого размера перестаёт рисоваться.

Картинка выбранной комплектации уходит в Storage при отправке клиенту
(`/api/projects/render` → таблица `renders`): до этого рендеры жили только
в памяти вкладки, и по ссылке клиент видел чертёж без своей кухни.

## Слой 10: настоящий эскиз и детализировка

Компании начинают разговор с чертежа, а не с картинки. Модуль-прямоугольник
с одной шириной — это визуализатор: внутри мебели нет ни полок, ни штанги,
ни ящиков. И дороже всего в мебельной компании стоит не рисунок, а **час
технолога**: на каждый заказ уходит час-два, чтобы расписать детали.

### Наполнение модуля

[lib/millwork/fill.ts](lib/millwork/fill.ts) — `ModuleFill`: полки, вертикальная
перегородка, штанги, высоты фронтов ящиков, сторона петель. Считается из типа
модуля и секции детерминированно и складывается в `Module.fill` прямо в
`buildRun` — чертёж, смета и детализировка обязаны видеть одну мебель.

**Система 32.** Присадочные отверстия идут шагом 32 мм, и полка садится
только на них: полки на «высоте 412 мм» не существует. Любое положение
проходит через `snapTo32`. Мебельщик замечает это первым — если полка встаёт
куда угодно, инструмент писал человек не из отрасли.

Наполнение входит в `configurationFingerprint`: подвинутая полка меняет
отпечаток, и рендер с чертежом не разъедутся.

### Эскиз в двух видах

«С фасадами» — вид для клиента: контуры, двери, ширины, размерная цепочка,
и у каждой одиночной двери треугольник направления открывания (одна метка —
и цех не ошибётся стороной петель). «Внутри» — разрез: полки с высотами от
пола, перегородки, штанги, ящики отдельными прямоугольниками; фасады не
рисуются, они закрывают ровно то, ради чего этот вид смотрят.

Правка — перетаскиванием, замерщик не вводит числа: полка тянется вверх-вниз
и садится по системе 32, двойной клик добавляет и убирает её, граница между
ящиками тянется с сохранением суммы высот, клик по треугольнику меняет
сторону петель. Правила производительности те же, что у шторки сравнения:
`pointermove` живёт только между `pointerdown` и `pointerup`, позиция пишется
прямо в DOM, `setState` случается один раз — на отпускании.

### Детализировка — главная ценность

[lib/millwork/panels.ts](lib/millwork/panels.ts) считает карту деталей:
боковины, дно, крыша, полки, задняя стенка, фасады и фронты ящиков — с
размерами, количеством, кромкой по торцам и направлением текстуры. Схема
сборки — вкладное дно и крыша между боковинами.

Экран «Детализировка» стоит рядом с чертежом и планом, печатается со штампом
и выгружается кнопкой **«Выгрузить для раскроя»** —
[lib/millwork/csv-export.ts](lib/millwork/csv-export.ts), `;` в разделителе и
windows-1251 по умолчанию: так файл примут программы раскроя, которыми
пользуются компании. UTF-8 переключателем, с BOM для Excel.

### Настройки цеха

Толщины и зазоры у каждой компании свои, и захардкоженные числа сделали бы
детализировку неверной для половины клиентов — а неверная детализировка хуже
её отсутствия: по ней распилят плиту. `/admin/production` хранит их в
`orgs.production`; система 32 в настройки не выведена, это стандарт.

    присадочного отверстия не существует.
83. **Сумма высот фронтов ящиков равна высоте модуля до миллиметра.**
    Иначе фасады не закроют корпус.
84. **Наполнение входит в отпечаток конфигурации.** Подвинутая полка —
    это другая мебель, и смета с рендером обязаны об этом знать.

    Нарисованная после них, она перехватывает нажатия, и полка перестаёт

## Слой 16: библиотека планировок ЖК

Застройщики сдают дома сериями: в одном ЖК сотни одинаковых квартир.
Отсюда три вещи, ради которых слой и построен:

1. **Один замер работает на сотни квартир.** Замерщик один раз меряет
   квартиру этого типа — замер годится для всех одинаковых в этом ЖК.
2. **Клиенту говорят фразу, после которой он слушает:** «на вашу квартиру
   у нас уже есть готовый проект».
3. **У компании появляется актив.** Двадцать обмеренных планировок — это
   то, чего нет у конкурента, и принадлежит оно организации.

### Два состояния планировки

Планировка заводится **до** замера и уже в этом виде работает.

| Состояние | Что известно | Что работает |
|---|---|---|
| **Заведена** | ЖК, код, комнаты, площади из объявления, схема | публичная страница, заявка; вместо проектов — «готовим» |
| **Обмерена** | плюс замер стен, проёмов, коммуникаций | размеры подставляются, появляются готовые проекты и цены |

`isMeasured` **считается**, а не хранится флагом: флаг забудут переключить,
и продукт начнёт обещать проекты, которых нет. То же правило, что
у `zoneReadiness`.

**Площадь комнаты — это не замер.** Кухня 11.85 м² бывает и 3200 × 3700,
и 2900 × 4100, а смету считает длина ряда. Поэтому у необмеренной
планировки нет ни одного размера и ни одной цены.

### Подставленные размеры — допущения, а не замер

`surveyFromMeasurement` переводит библиотечный замер в замер объекта, и
КАЖДАЯ величина приходит со статусом `assumed` — вместе с `basis`, который
называет дату, квартиру и допуск: «размеры из библиотеки, замер 12.03.2026
на кв. 42, допуск ±30 мм». Смета по ним предварительная, шаги замера не
отмечены пройденными. Это прямое продолжение слоя 6: система не делает
вид, что знает то, чего не знает.

### Публичные страницы

`/zk`, `/zk/[complex]` и `/zk/[complex]/[plan]` открыты без пароля и без входа — на них
ведёт реклама, одна планировка = одно объявление. Читаются СЕРВИСНЫМ
ключом и только по нужным полям, как кабинет клиента: политика
«select using (is_public)» отдала бы анониму строку целиком, вместе
с org_id и снимком цен.

Внизу страницы честная строка: где и когда сняты размеры и какой допуск.

135. **Публикация в админке — это состояние, а не действие.** Кнопка

    этого планировка лежала `is_public = false` при экране, который
    выглядел опубликованным. Два положения с `aria-pressed` и строка

136. **Планировка видна на `/zk`, только если опубликованы И она, И её ЖК.**
    Это и написано на экране — обеими сторонами, а не догадкой.
137. **`test:rls` пропускает раздел библиотеки, пока миграция 0008 не
    применена.** Красный прогон по несуществующей таблице прячет
    настоящие поломки.

### Размеры со схемы: третье состояние планировки

Схема застройщика — **масштабный чертёж**, а площади комнат в объявлении
известны до сотой. Значит масштаб выводится из них: обвели комнату
известной площади — получили миллиметры в пикселе, а из них длину любой
стены. Отсюда предварительный проект и предварительная цена **в тот же
день**, когда планировку завели, — до всякого выезда.

```
Заведена  →  Размеры со схемы  →  Обмерена
   ↓                ↓                  ↓
страница      +чертёж и цена     точные размеры
и заявка      допуск ±100 мм     допуск ±30 мм
```

`isMeasured` и `hasSchemeSizes` — разные состояния, и смешивать их нельзя:
`derivedWalls` лежат ОТДЕЛЬНО от `zones` именно поэтому. Обводка даёт
2–3 % погрешности, на стене 3200 мм это ±100 мм — обещать здесь тридцать
означает соврать.

**Настоящий замер всегда сильнее.** `sizeSourceFor` и `zoneRunLengthMm`
сначала смотрят в замер и только потом в схему; появился замер — допуск
возвращается к тридцати, а схема молчит. Ничего при этом не удаляется:
приоритет, а не стирание.

Автопроект (`lib/millwork/autoProject.ts`) считает ТЕМ ЖЕ кодом, что и
замерщик: `suggestTemplate` → `buildRun` → `buildEstimate`. Вторая ветка
расчёта развела бы предварительную цену с итоговой не из-за размеров,
а из-за двух калькуляторов.

### Состав показывает только свою зону

Шаг «Состав» долго оставался кухонным: в шкафу-купе предлагались мойка,
холодильник и посудомойка. Замерщик видит кнопки, которых там быть не
может, — и перестаёт доверять экрану целиком, а он показывает этот экран
клиенту.

Источник один — профиль зоны: `zoneAppliances`, `allowsSection`,
`zoneOptions` в [lib/millwork/zones.ts](lib/millwork/zones.ts). Через него
проходят ВСЕ пути: чипы состава, выпадающий список модуля, `applyOps`
и разбор ответа модели. Четыре независимых списка разъехались бы
на первой же правке.

| Зона | Чем набирается состав |
|---|---|
| Кухня | приборы: холодильник, духовка, СВЧ, варочная, вытяжка, мойка, посудомойка |
| Спальня | секции: штанги, полки, ящики, открытая, антресоль, витрина |
| Прихожая | крючки, обувница, скамья, зеркало, полки, антресоль |
| Зал | ниша под ТВ, подвесные модули, ящики, полки |
| Санузел | тумба под раковину, пенал, зеркальный шкаф, ящики |

Отказ объясняет мир, а не отказывает: «В спальне такого не бывает:
посудомойка 45». Ради этой фразы у зоны есть предложный падеж
(`locative`) — «в зоне «спальня» посудомойка не бывает» читается как
ошибка программы.

### Расход материалов — цифра компании

Под автопроектом в админке: ЛДСП, фасады, ХДФ, кромка, число деталей,
рядом «Детализировка» и «Выгрузить CSV». Считается из той же
детализировки, что уходит в цех, — второй расчёт разошёлся бы с раскроем.

**На публичной странице расхода нет и быть не должно.** Клиенту он не
нужен, а конкуренту очень: по нему видны схема сборки, толщины и нормы
кромки. Наружу идут состав одной строкой и цена.

### Визуализация автопроекта

У планировки ЖК **нет фотографии помещения**: квартира не сдана или сдана
без отделки, снимка клиента не существует. Значит в кадре гарнитур
настоящий — размеры, состав, техника по проекту, — а комната придумана
моделью. Под картинкой это написано словами:

> «Гарнитур — по размерам со схемы. Комната на визуализации условная:
> точную покажем после замера вашей квартиры.»

Без этой строки клиент ищет своё окно и не находит; один такой разговор
дороже красивой картинки.

### Ловушки состава, расхода и визуализации

145. **Состав берётся из профиля зоны, а не из константы экрана.**
    Списков должно быть ОДИН, иначе они разъезжаются.
146. **Чужое отклоняется на всех путях сразу:** чипы, список модуля,

148. **Переключатель, который ничего не меняет, — та же ложь, что чужая
    кнопка.** `upperToCeiling` в шкафу-купе не читается вовсе: высоту там
    задаёт профиль зоны, поэтому переключателя там нет.
149. **Расход материалов виден компании и не виден клиенту.**
150. **Расход считается из детализировки, а не отдельной формулой.**
151. **У планировки ЖК нет фотографии.** В кадре настоящий только
    гарнитур, и это написано под картинкой.
152. **Один рендер на проект.** Перерисовать можно, копить нельзя:

### Ловушки размеров со схемы

138. **`derivedWalls` живут отдельно от `zones`.** `zones` означает
    «обмерена замерщиком»; слитые вместе, они заставят продукт обещать
    точность, которой у обводки нет.
139. **Допуск схемы — 100 мм, а не 30.** И он виден и клиенту, и замерщику.
140. **Цена по схеме всегда со словом «предварительно» РЯДОМ с суммой.**
    Клиент запомнит первую названную цифру, и разница на замере будет
    стоить компании доверия.
141. **Проверка глазами стоит сразу после обводки.** Габариты в
    миллиметрах и расхождение с объявлением: «3180 × 3720» человек
    сверяет мгновенно, и это дешевле неверного проекта.
142. **Без масштаба автопроект не собирается вовсе**, как и без ставок
    каталога: цена без длины ряда — выдуманное число, а смета без ставок —
    нули с виду настоящей цены.
143. **На зону ровно один автопроект.** Выбор из трёх выдуманных вариантов
    хуже одного честного. Ручной проект замерщика вытесняет автоматический.
144. **Новый набор полей не должен ломать экран до миграции.** PostgREST
    роняет ЗАПРОС ЦЕЛИКОМ на несуществующей колонке: первый такой ответ
    переключает чтение на прежний набор (`schemaNeedsMigration`), и
    админка говорит, какую миграцию применить.

## Пароль на сайт до запуска

`SITE_PASSWORD` в переменных окружения закрывает сайт одним общим паролем.
Это НЕ авторизация — она живёт в Supabase и решает, кто что может; пароль
решает другое: пускать ли на сайт вообще, пока продукт не показан клиентам.

```
middleware → checkGate → нет пароля в окружении  → пускаем всех
                       → путь открыт              → пускаем
                       → кука совпала             → пускаем
                       → страница                 → 307 на /gate?next=…
                       → /api/*                   → 401 JSON
```

Открыты без пароля ровно три пути: `/gate` (сама дверь), `/p/[token]`
(кабинет клиента — ссылку отправляют клиенту, пароль там неуместен) и
`/api/projects/like` — единственный запрос, который эта страница делает.

В куке лежит **не пароль, а SHA-256 от него**: пароль общий на всю
компанию, и утекать из куки, истории браузера или лога прокси ему незачем.
Кука `httpOnly`, на 30 дней. Форма отправляется server action'ом, а не
`fetch`: первый экран продукта обязан работать и без скриптов.

### Ловушки двери

118. **Дверь стоит ПЕРВОЙ в middleware.** Обновлять сессию Supabase тому,
    кого мы не пускаем, незачем.
119. **API отвечает 401, а не редиректом.** `fetch` за редиректом уходит на
    HTML-страницу и падает на разборе JSON — в интерфейсе это выглядит
    как поломка сервера, а не как «введите пароль».
120. **Пустой `SITE_PASSWORD` = двери нет.** Локальная разработка и сборка
    не должны о ней знать.
121. **Приёмки поднимают сервер с пустым `SITE_PASSWORD`.** Иначе проверка,
    запущенная там, где пароль задан, упирается в `/gate` и падает
    с непонятным «страница не та».
122. **`next` не теряется ни на одном шаге**, включая неверный пароль:
    иначе человек, пришедший по ссылке на объект, после входа попадает
    на главную и ищет объект заново.

## Слой 36: 3D вернулась САПР-видом

Сцену убрали в слое 32 не зря, но и не за то: тормозила не она, а
СКРЫТАЯ сцена, рисовавшая 588 кадров в минуту мебели, которую никто не
видел. Причина устранена (`frameloop="never"` у скрытой), и видимая
вернулась — переключателем рядом со схемой.

```
[ 3D ] [ Схема ] [ План ]            ← вид
Спереди · Слева · Справа · Сверху · Свободный · Вернуть вид
```

**Не фотореализм.** Референс — вывод мебельного САПР: плотные плоские
цвета фасадов, чёткие рёбра между деталями, один направленный свет плюс
общий. Ни бликов, ни отражений, ни постобработки: красный фасад просто
красный. Фотореалистичную картинку делает Gemini, и делает отдельно —
здесь отвечают на другой вопрос, «как это устроено».

### Измерено, а не «быстро»

| | прямой ряд 3800 | угловая | П-образная |
|---|---|---|---|
| вызовов отрисовки | **10** | **22** | **28** |
| мешей в сцене | 9 | 21 | 27 |
| треугольников | 1070 | 1490 | — |
| кадров в покое | **0 за 10 с** | — | — |
| кадров за минуту работы | **708** (55 действий) | — | — |

Ноль в покое — это и есть `frameloop="demand"`: мебель стоит, пока её не
тронули. 708 за минуту активной работы — это перерисовки на нажатия,
открывание и вращение, а не фоновая трата. Меряет
`node scripts/check-cad-frames.mjs`; в `verify` он не входит — минута
прогона на каждую проверку стоит дороже, чем сообщает.

### Рёбра — один буфер

`EdgesGeometry` на коробку дала бы на угловой кухне под двести объектов.
Здесь вершины всех рядов сложены в ОДИН буфер и пересобираются только при
смене состава.

Габариты коробок ряда считает `runBoxes` — одна функция на сцену, рёбра и
всё остальное. Раньше раскладка модулей по высоте и глубине жила внутри
`Cabinet3D`, и всё, что хотело те же числа, считало их заново.

### Угол в сцене

Оба ряда в одной сцене под прямым углом. Каждый ряд по-прежнему собран
`buildRun` вдоль своей стены от нуля — здесь только поворот вокруг угла и
смещение на то, что угол занял: глубина ряда плюс панель либо 900 мм у
углового модуля. **Те же числа, что урезали полезную длину**, иначе ряды
в сцене разъедутся с тем, что посчитала смета.

Ряды берутся из `wallRuns` — сохранённых стен: открыл объект, и угол на
месте вместе с материалами каждой стены.

Камеру ставит ПЕРВЫЙ ряд: два ракурса на один канвас — это две проекции,
спорящие за одну матрицу.

### Состояние сцены проверяется числами, а не снимком

`toDataURL` на WebGL-канвасе без `preserveDrawingBuffer` отдаёт очищенный
буфер: два «одинаковых» кадра не доказывают ничего. Приёмка сравнивает
`__mwCadState()` — материалы фасадов, число рядов и позу камеры.

Счётчик кадров у видимой сцены СВОЙ (`__mwCadFrames`): общий затирается
скрытой сценой, которая регистрирует его последней, и мерили бы не то.

### Цвет фасада считает ОДНА формула

`parts.ts` брал «артикул выбран — его цвет, иначе цвет сцены», а схема
считала `frontSwatch` — «иначе типовой цвет ЭТОЙ БАЗЫ». Выбранный без
артикула акрил выходил на схеме тёмным, а в сцене бежевым: восьмой случай
одного и того же класса — две формулы одной величины. Теперь `frontColor`
делегирует `frontSwatch`, и цвет один на схему и на сцену.

### Открыть всё, и внутри настоящее наполнение

Механизм открывания жил давно (`InteractiveDoor`, `useSlide`,
`openablePartIds`), а нажать на него было негде. Кнопки стоят в самой
сцене; список открываемого считает та же функция по тем же `fill`.

Полки внутри — это `fill.shelves`, те же числа, что уедут в цех:
`carcassBoxes` и `panels` читают ОДИН массив, и приёмка сверяет каждую
высоту, а не их количество (на разрезе мы уже ловили условные доли
`[0.33, 0.66]` вместо настоящих полок).

### Размерные цепи над сценой

Второй раз рисовать цепочку нечем — поверх канваса ложится ТОТ ЖЕ
`ElevationDrawing` (ловушка 170). Сцена отдаёт наверх не «zoom», а
готовую ортопроекцию: `CadScene` пробрасывает `onFraming` от ПЕРВОГО ряда.
На перспективе проекции нет вовсе, и слой уходит из разметки: размер по
горизонтали на повёрнутой мебели измеряет не ту длину.

### Ловушки слоя 36

299. **САПР-вид, а не фотореализм.** Блик на фасаде заставляет клиента
    выбирать цвет по блику, а привезут ему плиту.
300. **Рёбра — один буфер на сцену.** `EdgesGeometry` на коробку это
    сотни объектов.
301. **Габариты ряда считает `runBoxes`.** Вторая формула тех же чисел
    разъезжается — этот класс ошибки ловился шесть раз.
302. **Камеру ставит один ряд.** У угловой кухни рядов два, а камера
    одна.
303. **Поворот ряда в сцене берёт ТЕ ЖЕ числа, что урезали его длину.**
    Иначе сцена показывает не ту мебель, которую посчитала смета.
304. **Снимок WebGL-канваса не годится для сравнения.** Без
    `preserveDrawingBuffer` буфер очищен; сравнивать надо состояние.
305. **У видимой сцены свой счётчик кадров.** Общий затирается скрытой.
306. **Промах мимо мебели не снимает выделение.** Пропадающая панель
    читается как сбой.
307. **Цвет фасада — одна формула на сцену и на схему.** Своя формула в
    сцене красила акрил бежевым там, где схема рисовала тёмный.
308. **Полки в сцене — это `fill.shelves`.** Условная разбивка внутри
    открытого шкафа показывает клиенту мебель, которой не будет.
309. **Размерные цепи живут только там, где есть ортопроекция.** На
    перспективе слой убирается целиком, а не гасится: цепь без проекции
    рисует неверную длину.

## Слой 44: ригель на потолке

Клиент показал квартиру, где по потолку идёт балка. Шкафы под ней в полную
высоту не встают, а система считала потолок ровным: ряд упирался в выступ,
и узнавали об этом на монтаже — когда мебель уже распилена и привезена.

### Ригель — объект стены, только сверху

```
Opening { kind: 'beam', fromCornerMm, widthMm, heightMm }
                                                 ↑ СВЕС, а не высота от пола
```

Он заводится там же, где окно, и теми же тремя числами. Своего списка у
него нет намеренно: замер, сохранение объекта, композиция и чертёж уже
возят проёмы, и второй путь для той же величины разошёлся бы с первым.

**`sillMm` у ригеля не читается вовсе.** Низ считается из высоты потолка
(`beamBottomMm`), и держать рядом копию этой отметки значит завести
величину, которая устареет от первой же правки потолка. Замерщик тоже
меряет свес: до потолка он рулеткой не достаёт, а свес балки видит —
поэтому и поле в замере называется «Опускается от потолка».

### Высоту урезает ОДНА функция

`ceilingOverSpanMm(from, to, beams, ceiling)` отвечает на единственный
вопрос: какая высота доступна над этим участком ряда. Под двумя балками
сразу берётся самая низкая — мебель обязана пройти под обеими.

Ограничитель применяется в `moduleCarcassHeightMm` ОДИН раз и ко всем
веткам сразу: у шкафа, пенала, антресоли и секции шкафа-купе высота
считается по-разному, а упираются они в один и тот же выступ. Разложи
проверку по веткам — и первая же новая ветка высоты пройдёт сквозь балку.

Ригели едут НА РЯДУ (`Run.beams`) по той же причине, что и антресоль:
высоту считает одна функция, и видит она только `unit` и `run`. Чертёж и
сцена тоже видят ряд, а не замер.

### Разрыв ряда — тот же механизм, что на окне

Под выступом шкаф просто ниже. Но если свес съел столько, что осталось
меньше полезного корпуса (`GEOMETRY.upper.minCarcassH` = 300 мм), ставить
его там нельзя: полка не встанет, а фасад с петлями будет стоить как у
нормального. Тогда ряд разрывается — ровно как на окне, и считает это та
же `freeSpans`, что разрывает его под окном и над колоннами.

```
свес  120 мм → шкаф 1130 вместо 1250
свес  300 мм → шкаф  950
свес  900 мм → шкаф  350
свес 1000 мм → шкафа нет: осталось 250, ряд разорван
```

**Антресоль съедается первой.** Она идёт верхней полосой, у самого
потолка: её низ оказывается ВЫШЕ низа балки, и никакая высота её туда не
впишет. Поэтому под ригелем её просто нет — и в шкафу-купе, и на кухне,
где она пересобирается в `applyOps`.

Кладовка над холодильником меряет потолок НАД СОБОЙ, а не потолок зоны:
под балкой её может не остаться вовсе.

### Отпечаток

Ряд под выступом — ДРУГАЯ мебель: шкафы там ниже, и в раскрое это другие
детали. Считать это через высоты модулей нельзя — высот в отпечатке нет
вовсе, и добавить их значило бы сдвинуть отпечатки всех сохранённых рядов
разом. Поэтому в отпечаток входят сами ригели, а пустой список не
пишется (ловушка 246): у рядов без них отпечаток прежний до символа.

### Инвариант, а не предупреждение

`assertUnderCeiling` бросает исключение, если верх модуля оказался выше
доступного потолка. Габарит берётся ТОТ ЖЕ, что у проверки непересечения
модулей, а высота — та же `ceilingOverSpanMm`, по которой считался
корпус: вторая формула означала бы проверку не той мебели, которую
собрали.

Это тот же класс правил, что «два модуля в одном объёме»: шкаф, который
по расчёту заходит в балку на сорок миллиметров, на объекте не встанет, а
в цех уедет распиленным.

### На чертеже и в сцене

На фасаде — штриховкой и с подписью свеса («Ригель 300»), а не заливкой:
лист печатают чёрно-белым. В сцене — объёмом в группе КОМНАТЫ, а не
мебели: попади он в габарит гарнитура, и камера начала бы кадрировать
балку, а счётчик мешей — считать её мебелью.

Без этого разная высота фасадов читается ошибкой построения, и первый же
вопрос на приёмке — «а это что у вас тут не сошлось».

### Предупреждение называет последствие

> «Под выступом шкаф ниже на 70 мм — верх ряда там не сойдётся с
> остальными.»

Насколько ниже — считается ТОЙ ЖЕ функцией высоты, что строит раскрой.
Своя арифметика «потолок минус свес» разошлась бы с ней на первом же ряде
до потолка.

Причина обязана быть В РИГЕЛЕ: под колонной холодильника верхнего ряда
нет и без всякой балки, и сказать там «ряд разрывается из-за выступа»
значит соврать замерщику про то, что он видит.

### Демонстрация

В демо-кухне появился короб вентиляции: 2400…3400 мм, свес 600. Стоит он
НАД ВЕРХНИМ РЯДОМ, а не над колоннами: над колонной любой выступ съедает
кладовку над холодильником целиком, и демонстрация показывала бы не
«шкаф ниже», а «модуля нет» — а клиент спрашивает именно про высоту.

Сумма демо-ряда при этом поехала: **1 650 499 ₸ → 1 644 970 ₸**
(−5 529). Это не наценка и не скидка — два верхних шкафа стали ниже на
70 мм, и материала на них ушло меньше.

### Названия видов проёма — одна таблица

Их было ТРИ копии: панель замера, замерный лист и предупреждения. Новый
вид проёма приходится вписывать в каждую, и первая же забытая копия
показывает замерщику сырой ключ вместо слова. Теперь `OPENING_KIND_TITLE`
одна на продукт.

### Ловушки слоя 44

371. **Ригель — это `Opening`, а не свой список.** Замер, сохранение,
    композиция и чертёж уже возят проёмы; второй путь разойдётся с первым.
372. **У ригеля `heightMm` — это СВЕС.** Замерщик до потолка не достаёт;
    `sillMm` у него не читается вовсе, низ считает `beamBottomMm`.
373. **Доступную высоту над участком считает одна функция.** Высота
    модуля, разрыв ряда, чертёж, сцена и инвариант обязаны получить один
    ответ.
374. **Ограничитель применяется ко ВСЕМ веткам высоты сразу.** Разложи
    его по веткам — и первая новая ветка пройдёт сквозь балку.
375. **Ригели живут на `Run`.** Высоту считает функция, видящая только
    `unit` и `run`; из замера её не дотянуть.
376. **Разрыв ряда под балкой — тот же механизм, что под окном**
    (`freeSpans`). Второй разошёлся бы с первым на первой правке.
377. **Антресоль под ригелем не существует.** Её низ выше низа балки, и
    никакая высота её туда не впишет — модуля там просто нет.
378. **Ригели входят в отпечаток, а пустой список — нет** (ловушка 246).
379. **Мебель, упирающаяся в выступ, — исключение, а не предупреждение.**
    Она не встанет на объекте, а в цех уедет распиленной.
380. **Ригель в сцене принадлежит КОМНАТЕ.** В группе мебели он попал бы
    и в габарит для камеры, и в счётчик мешей гарнитура.
381. **Наполнение считается с ригелями.** Оболочка без них даёт полки по
    неурезанной высоте: раскладка и пересчёт после правки расходились на
    одном и том же модуле, и ловилось это только отпечатком.
382. **Названия видов проёма — одна таблица на продукт.** Три копии
    молча разъезжаются на первом же новом виде.

## Слой 43: производство — припуски цеха, бутылочница, типы техники

Четыре вещи от мебельщика, и три из них про одно: продукт знал о мебели
больше, чем показывал, а о цехе — меньше, чем нужно.

### Фронт у модуля один: створки ИЛИ ящики

«Ящики под варочной не открываются». Модуль под варочной панелью
числился нишей: на чертеже два фронта, в раскрое два фронта, а в сцене
глухая панель, за которую не взяться. Прибор занимает нишу СВЕРХУ, под
ним обычные ящики (слой 34), и выдвигаются они так же, как у соседей.

Вопрос «есть ли тут ящики» задаётся данным, а не типу модуля: `drawers =
unit.column ? 0 : fill.drawerHeights.length`. Условия «нет прибора» и
«прибор не виден» одинаково не годятся — варочная ВИДНА, она лежит
сверху, а ящики под ней есть.

Рядом вскрылись два соседних расхождения, и оба того же класса:

| | было | стало |
|---|---|---|
| закрытый ящик по Z | рисовался на 270 мм ПЕРЕД фасадом | короб в корпусе, фронт на `thickness/2` |
| `doorCount` | `Math.max(1, …)` — створка поверх ящиков и на открытой секции | ноль там, где фронт не створка |
| «Открыть всё» | свой список: «нет прибора» + `frontType === 'door'` | `openablePartIds` считает ровно то, что рисует сцена |

Створка поверх ящиков в раскрое не существует (`panels.ts` смотрит
`frontType`) — то есть сцена показывала мебель, которой цех не сделает.
В демо ящичных и открытых модулей нет, поэтому этого не видел никто:
ровно так же пряталась их геометрия по Z.

`openablePartIds` переехал из `Cabinet3D` в
[lib/millwork/cabinetBoxes.ts](lib/millwork/cabinetBoxes.ts) — туда, где
считаются коробки. Это одно и то же знание: что нарисовано подвижным.

**Известное расхождение, и оно названо.** У встроенного холодильника в
раскрое ДВЕ створки друг над другом (дверь камеры и дверь морозильника,
`BUILT_IN_FRIDGE_FRONTS`), а сцена рисует одно полотно во всю высоту:
створки в ней раскладываются только В РЯД, вертикальной раскладки у неё
нет вовсе. Детали и петли в смете при этом верные — расходится картинка.

### Бутылочница

Остаток 150–200 мм закрывался узкой дверцей, а потом — карго, которого
такой ширины не бывает: механизм не влезает. Там ставят **бутылочницу** —
полное выдвижение, две-три корзины, своя фурнитура и свои деньги
(`bottle_pullout` 38 000 ₸ против `cargo_300` 56 000 ₸).

Она не только получается остатком, но и ставится руками: в каталоге
модулей она предлагается СВОЕЙ ширины даже в широкий промежуток —
бутылочницы на 900 мм не бывает.

### Припуски — настройка цеха

«Модуль 900 — столешница минус 40, что-то ещё минус 60». В коде
захардкоженными лежали три числа, все в `panels.ts`:

| припуск | было в коде | что это |
|---|---|---|
| `shelfSideMm` | `SHELF_SIDE_GAP_MM = 2` | полка уже проёма между боковинами |
| `shelfDepthMm` | `SHELF_DEPTH_BACK_MM = 20` | полка мельче глубины корпуса |
| `dividerDepthMm` | та же константа | перегородка мельче глубины |
| `backInsetMm` | `BACK_INSET_MM = 8` | вкладная задняя стенка меньше габарита |

Толщины, зазор фасада и кромка настройкой были уже (слой 10) — они тоже
припуски, просто заведены раньше. Теперь рядом с ними лежит
`ProductionSettings.allowances`, экран `/admin/production`, поля в
миллиметрах. Число принимается любое от 0 до 200: у цеха свои нормы, и
подрезать их «правильными» значениями — это тот же захардкоженный
раскрой, от которого настройка уводит.

**Столешнице «минус 40» задать негде, и это честно сказано здесь, а не
обойдено молча.** Столешница не деталь раскроя: она идёт в смету
погонными метрами (`countertop_*`), деталей у неё нет. Появится
раскрой столешницы — припуск станет ещё одним полем; выдумывать его в
настройках раньше, чем он на что-то влияет, значит завести
переключатель, который ничего не меняет (ловушка 148).

### Типы техники

Мебельщик заказывает не «варочную», а газовую или электрическую; вытяжка
бывает встроенной, наклонной и купольной. Пока тип был один на прибор,
габариты приходилось вводить руками каждый раз — а «каждый раз» означает
«иногда забыли».

```
варочная     электрическая · газовая
духовка      встроенная · отдельностоящая
вытяжка      встроенная · наклонная · купольная 900
СВЧ          встроенная · настольная
```

Тип — это НАБОР УМОЛЧАНИЙ, а не новый прибор: `ApplianceKind` остаётся
прежним, и ни зоны, ни шаблоны, ни промпт о нём не знают. Порядок силы:
**замеренное > типовое > общее умолчание**, и первый тип списка совпадает
с прежним отраслевым стандартом — иначе новый слой молча пересчитал бы
всем сохранённым кухням ширины приборов.

**Умолчание в данные не пишется** (ловушка 246). Записанное, оно сдвинуло
бы отпечатки ВСЕХ сохранённых кухонь разом и потянуло бы за собой
раскрой: паспортная глубина духовки 560 плюс 20 мм просвета отодвигают
пенал, и в смете появляются метры, которых не было. Измерено на демо-ряду:
**1 650 499 ₸ → 1 651 667 ₸ при том, что человек ничего не выбирал.**
В модуль едет только ВЫБРАННОЕ исполнение — `chosenApplianceType`.

Тип доезжает до модуля ГАБАРИТАМИ, а не идентификатором: раскрой, смета и
3D читают миллиметры, и второго словаря типов у них нет. Отсюда и первое
следствие, которое видно глазами: купольная вытяжка 900 мм над варочной
600 — модуль вытяжки берёт СВОЮ ширину, а верхний ряд под неё
разрывается. Раньше он брал ширину варочной, и выбор купольной не менял
ни раскладку, ни смету — тип был подписью.

### Ловушки слоя 43

358. **Ящики есть у всех, у кого есть фронты ящиков.** Спрашивается
    `fill.drawerHeights`, а не тип модуля: под варочной они тоже есть.
359. **Фронт у модуля один: створки ИЛИ ящики.** `Math.max(1, doorCount)`
    вешал створку на фронты ящиков и на открытую секцию — в раскрое этой
    створки нет, то есть сцена показывала мебель, которой цех не сделает.
360. **Открывается ровно то, что нарисовано.** `openablePartIds` живёт
    рядом с `cabinetBoxes` и повторяет её условия; свой список расходится
    в обе стороны и молча.
361. **Ящик стоит В корпусе, а не перед ним.** Закрытый фронт — на
    `thickness/2`, короб — от `-innerDepth/2`. Ошибка по Z не видна в
    демо: ящичных модулей там нет.
362. **Узкое место 150–200 мм — бутылочница, а не карго.** Механизм карго
    туда не влезает, и назвать одно другим значит подписать клиента не на
    ту фурнитуру.
363. **Модуль предлагается СВОЕЙ ширины.** Каталог в широком промежутке
    даёт бутылочницу на 200, а не на 900.
364. **Припуски деталей — настройка организации.** Две компании с разными
    припусками обязаны получать разный раскрой; это и проверяется.
365. **Припуск принимается числом, а не выбором из двух.** Границы — 0…200
    мм и мусор; «правильных» значений у чужого цеха не бывает.
366. **Тип прибора — набор умолчаний, а не новый `ApplianceKind`.**
    Иначе о нём пришлось бы узнать зонам, шаблонам и промпту.
367. **Замеренное сильнее типового.** Тип — то, что обычно бывает; замер —
    то, что стоит у клиента. Молча вернуть типовое поверх замера — самая
    дорогая ошибка из возможных.
368. **Умолчание типа совпадает с прежним стандартом.** Иначе слой
    пересчитал бы ширины приборов всем сохранённым кухням.
369. **Тип доезжает до модуля габаритами.** Второй словарь типов в
    раскрое и в сцене разъедется с первым.
370. **Умолчание типа в модуль не пишется** (ловушка 246). Записанное,
    оно двигает отпечатки и раскрой всех сохранённых кухонь: замерено
    +1 168 ₸ на демо-ряду, которого никто не трогал. В данные едет
    только ВЫБРАННОЕ — `chosenApplianceType`.

## Слой 42: прибор принадлежит кухне, а не ряду

В угловой кухне холодильник появлялся дважды — по одному на каждой стене,
и удалить его можно было только вместе с тем, что стоит на главной.

### Почему проверка была зелёной

`npm run test:millwork` проверял «мойка одна на кухню» и «приборы между
рядами не дублируются» — и оба раза мерил `buildComposition`. Эта функция
раздаёт приборы правильно: мойка на длинную стену, пеналы на короткую.

А рабочий экран собирал стену А **своими средствами**:

```
segments = layout.segments.map((segment, i) =>
  i === 0 ? active.run          // ← ПОЛНЫЙ набор приборов
          : editedWalls[i] ?? segment.run,   // ← доля из раздачи
);
```

Стена А строилась из полных требований, остальные — из распределённых.
Расходилась не композиция и не ряд, а ШОВ между ними, и проверка его не
видела: она смотрела на данные до шва.

Мерить надо там, куда смотрит человек. Новая проверка ходит по стенам в
интерфейсе и считает подписи модулей на схеме — как считает их глаз.

### Приборы принадлежат композиции

```
RunRequirements.applianceWalls   прибор → номер стены
RunSegment.appliances            приборы ЭТОЙ стены
```

Раздача осталась одна — `splitAppliances` внутри композиции; рабочее
место больше не считает её второй раз, а берёт из `segments[i].appliances`.
Попытка посчитать самому длилась ровно один заход: параллельная формула
дала другую полезную длину, и с прямой стены пропала варочная.

**Выбор человека сильнее правила.** Рабочий треугольник — умолчание;
сказал замерщик «холодильник на стену Б» — слушаем его.

| действие | что это |
|---|---|
| перенос на другую стену | ОДНА правка состава: `applianceWalls` |
| удаление | прибор уходит со всей кухни, а не с одной стены |
| габариты прибора | едут вместе с ним (`applianceSizes` в составе) |

### Панель модуля работала только на стене А

Тот же шов: `selectedUnit` искался в `active.run`. Модуль стены Б
выделялся на схеме, но панель под ним оставалась пустой — материал,
открывание, ручка и перенос были недоступны на всех стенах, кроме
главной.

### Духовка и СВЧ меняются местами

Кнопка была; проверки не было. Теперь проверено:

* порядок меняется и **меняет отпечаток** (4cff5a92 → c06119b0): присадка
  на другой высоте;
* **смету не меняет** — и это правда, а не дефект: деталей столько же и
  тех же размеров, меняются только высоты опор;
* правило пары ниш (1500 мм) держится при любом порядке;
* правило «низ духовки не выше 600 мм» при выборе «духовка сверху»
  выполниться не может — под ней микроволновка. Запрещать нельзя, так
  тоже собирают; теперь об этом говорит жёлтая строка с числом: «Низ
  духовки на 996 мм — выше пояса».

### Ловушки слоя 42

351. **Прибор принадлежит КУХНЕ.** У него есть стена, и она одна.
352. **Раздача приборов живёт в композиции.** Посчитать её второй раз в
    рабочем месте — значит получить другую полезную длину и потерять
    прибор.
353. **Перенос на другую стену — одна правка.** Удаление плюс добавление
    теряет настройки прибора по дороге.
354. **Удаление прибора убирает его со всех стен.** Иначе это переезд, о
    котором никто не просил.
355. **Выделенный модуль ищется в ВЫБРАННОЙ стене.** `active.run` — это
    всегда первая.
356. **Проверка «прибор один» обязана смотреть на экран.** На данных до
    шва она зелёная при дубле на экране.
357. **Перестановка приборов в колонне не меняет смету.** Деталей
    столько же; отпечаток при этом меняться обязан.

## Слой 41: мебель собралась

Шесть дефектов со скриншота, и у четырёх из них оказалась одна причина.

### Одиннадцатый случай: отметка низа верхнего ряда

Где стоит модуль по высоте, знали ТРИ места: коробки (`runBoxes`), сцена
(`Cabinet3D`) и инвариант непересечения. Числа совпадали, пока верхний
ряд был один, и разошлись на антресоли: `upperBottomFor` знает, что она
стоит на крыше колонны холодильника (2400 мм), а сцена и коробки рисовали
её по отметке навески — 1450 мм, ВНУТРИ холодильника.

На экране это выглядело двумя жалобами сразу:

* «маленькая дверца посередине холодильника» — это фасад антресоли;
* «антресоль не видна в 3D» — она была, но внутри колонны.

Теперь раскладка одна — `runPlaces`, и спрашивают её все.

### Фасады проверяются закрытыми

Проверялось ОТКРЫТОЕ положение: куда уходит створка. А на скриншоте
разъехались закрытые — а это как раз то, что видит клиент.

Меряется каждый модуль: центр фасада лежит на передней плоскости своего
корпуса (отклонение 0 при девяти фасадах), края внутри корпуса, а у всех
створок одного модуля общий верх и общий низ.

### Ручки: три типа помодульно

```
Скоба · Профиль · Без ручки
```

Было одной опцией на весь ряд (`integratedHandles`), а мебельщик выбирает
на каждом модуле. Лежит выбор в том же `fill`, что и направление
открывания: скоба, профиль и нажатие — фурнитура фасада, и хранить её
порознь значит однажды нарисовать скобу там, где в смете механизм.

| ручка | в смете | в сцене |
|---|---|---|
| скоба | штуками на фасад | накладная перемычка |
| профиль | погонными метрами кромки | планка по верхней кромке |
| без ручки | `push_to_open`, штуками | на фасаде НЕТ ничего |

«Без ручки» — это не отсутствие фурнитуры, а механизм: 4 200 ₸ за фасад.
Три типа дают три разные суммы: 1 650 499 · 1 652 362 · 1 653 739 ₸.

Умолчание не пишется в отпечаток (ловушка 246): ряды, собранные до этого
выбора, не едут.

### Вращение вернулось — с пределами, которые держат

Мебельщик просит крутить мебель, и правильно просит. Свободное вращение
однажды уже сломало вид; теперь оно держится на двух вещах:

1. **Камера ортогональная.** У неё масштаб не зависит от расстояния,
   поэтому «мебель целиком в кадре» — свойство ЗУМА, а не угла: предел
   подобран один раз и верен на всех 360°.
2. **Предел зума считается от ДИАГОНАЛИ габарита** — при повороте на 45°
   в кадр ложится именно она.

```
поворот   360° вокруг вертикали, без ограничений
наклон    0.05 … π/2−0.02: ни под пол, ни вверх ногами
зум       от fitZoom/2 до fitZoom, где fitZoom — «влезает при любом угле»
```

Проверено крайними значениями: полный оборот шагом 30°, наклон в оба
предела, зум в оба предела — **16 положений, ни одного вылета**, причём
требование строже прежнего: габарит обязан быть ВНУТРИ кадра, а не
пересекаться с ним.

### Духовка опущена

Низ ниши духовки — не выше 600 мм от пола (было 800). Отметка считается
ОТ ПОЛА и переводится в отметку от дна корпуса: цоколь входит в высоту, и
забыть его — значит поднять пару приборов на сто миллиметров. Проверено:
580 мм, пара приборов 1024 мм при пределе 1500.

### Ловушки слоя 41

344. **Отметку низа модуля знает одна функция** (`runPlaces`). Три копии
    совпадали, пока верхний ряд был один.
345. **Фасад проверяется ЗАКРЫТЫМ.** Клиент смотрит на закрытую мебель,
    а проверялось открывание.
346. **Створки одного модуля имеют общий верх и низ.** Разные — это
    развалившаяся мебель, и видно это только глазами или числом.
347. **Ручка — выбор модуля, а не опция ряда.** И «без ручки» — это
    механизм, а не пустота.
348. **Вращение ограничивает ЗУМ, а не угол.** У ортокамеры масштаб от
    угла не зависит, и предел, подобранный по диагонали габарита, верен
    на всех 360°.
349. **«Целиком в кадре» — это габарит ВНУТРИ, а не пересечение.**
    Пересечение зелёное и тогда, когда видно четверть мебели.
350. **Отметка прибора от пола переводится в отметку от дна.** Цоколь
    входит в высоту корпуса, и забытый он поднимает прибор на 100 мм.

## Слой 40: сцена как у мебельного САПР

Три отличия от Базис-Мебельщика, из-за которых наша сцена выглядела хуже,
и поправка к правилу колонны.

### Мебель стоит в комнате

Пол и стены — не украшение: ряд ПРИМЫКАЕТ к ним, и потому читается
стоящим. Висящая в пустоте мебель кажется развалившейся, потому что глазу
не за что зацепиться.

Стены ставятся ПО РЯДАМ, а не по форме из настроек: у каждого ряда своя
стена за спиной, и прямая кухня получает одну, угловая две, П-образная
три — сама собой, тем же `rowPlacement`, который ставит мебель. Проверено
числом: полов 1, стен 3 у П-образной, и **ни одна не режет мебель**
(`__mwCadRoom().intersects === 0`).

Ни окон, ни дверей, ни мебели комнаты: это фон, а не визуализация.
Показывает её рендер — по фотографии клиента.

### Свободного вращения нет

На скриншотах мебель «разваливалась»: ряды разлетались, панели висели.
Геометрия была верной — ломалась КАМЕРА.

**Почему проверка этого не видела.** `__mwCadFit` меряла, пересекается ли
габарит мебели с кадром, и отвечала на вопрос «мебель в кадре», а не
«мебель читается». Камера внутри шкафа, под полом, в метре от фасада —
всё это даёт пересечение и зелёную строку. Читаемость — это угол и
расстояние, а при свободном вращении их гарантировать нечем.

Убрана причина, а не проверка. Пять ракурсов, все фиксированные:

```
Спереди · Слева · Справа · Сверху · Общий вид
```

Общий вид — **ортогональная изометрия** 30°/30°, те же числа, по которым
строится печатная аксонометрия. Камера не вращается и не панорамируется,
остаётся зум в узких пределах (0.9…2.2 габарита).

**И это убрало целый класс беды.** Пока общий вид был перспективным, на
экране жили ДВЕ камеры. Возвращаясь с плана на общий вид, сцена
оставалась на ортокамере ПЛАНА с её масштабом — мебель на экране
разъезжалась (замерено: габарит выходил за кадр в два раза). Одна камера
на пять ракурсов — и спорить стало нечему.

Кадр целится в **центр габарита мебели**, а не комнаты: `sceneBounds`
отдаёт и центр, и размеры, по ним же считаются пределы зума. Проверка
теперь меряет то, что стало правдой: поза камеры не меняется от
протаскивания и правой кнопки, а каждый из пяти ракурсов держит габарит
ВНУТРИ кадра (не «пересекается», а внутри).

### Цвета в демонстрации

У демо нет организации, а палитра читается из каталога организации:
каталог был пуст, и выбор цвета честно писал «цветов не заведено» — на
встрече это читается как отсутствие функции.

`DEMO_CATALOG` — та же типовая палитра, что уходит компании в первый
день: 20 позиций, все с пометкой «типовая», все пять баз фасадов.
Второго списка цветов в продукте нет.

### Правило колонны: сумма, а не отметка

Клиент имел в виду ГАБАРИТ ПАРЫ: высота ниши духовки плюс высота ниши
микроволновки не больше 1500 мм. В прошлый раз я прочитал это как «верх
духовки от пола» — число получалось другое и ловило другие модули.
Обычная пара укладывается в 1024 мм; духовка 1100 мм даёт 1536 мм и
жёлтую строку с числом. Раскладка применяется.

### Ловушки слоя 40

337. **Стены ставятся по РЯДАМ.** Форма композиции меняется, стены
    следуют за ней сами — второй формулы «где стена» нет.
338. **Комната — фон, а не визуализация.** Ни окон, ни дверей: их
    показывает рендер по фотографии клиента.
339. **Свободного вращения нет.** Камера, которую можно увести внутрь
    шкафа, ломает вид, а проверка «в кадре» этого не видит.
340. **Одна камера на все ракурсы.** Две камеры спорят за активную, и
    возврат на общий вид оставлял ортокамеру чужого вида.
341. **Кадр целится в центр МЕБЕЛИ.** Центр комнаты совпадает с ним
    только у прямой кухни, и то случайно.
342. **«Показывает целиком» — это габарит ВНУТРИ кадра.** Пересечение с
    кадром зелёное и тогда, когда видно четверть мебели.
343. **У демонстрации свой каталог, но не свой список цветов.** Палитра
    одна — типовая, и помечена типовой.

## Слой 39: сцена перестала быть каркасом

«Видно рёбра, задние стенки прозрачные, мебель не читается как мебель» —
и у этого впечатления оказалась ровно одна измеримая причина.

### Проволочный двойник в двух метрах

Ряд и его рёбра ставились ДВУМЯ РАЗНЫМИ формулами:

```
меши   Cabinet3D:  x = −roomWidth/2,  z = −roomDepth/2 + depth
рёбра  CadScene:   placement первого ряда отсутствует → 0, 0
```

Измерено на демо-кухне: **1.90 м по X и 0.94 м по Z**. Рядом с гарнитуром
висел проволочный двойник — его и видно на скриншоте. Это девятый случай
того же класса, и самый заметный глазами.

Теперь место ряда считает `rowPlacement` — одна функция на меши, рёбра,
габарит сцены и пределы камеры. Ряд лежит от −L/2 до +L/2, фасады на
z = 0, корпус уходит в −z: та же система координат, в которой слой
размеров кладёт цепи на мебель. Расхождение после правки — **0 м**, и
проверяется оно числом (`__mwCadLook().edgeDrift`).

### Два режима, и оба честные

```
[ Фасады ]  готовая мебель: сплошные фасады, непрозрачные корпуса,
            рёбра только по внешнему контуру деталей
[ Каркас ]  разрез: фасады сняты, корпус просвечивает, видны полки,
            ящики и штанги
```

Признак ОДИН — тот же `cutaway`, по которому сцена снимает фасады.
Второй флаг про то же самое однажды дал бы сцену, где фасады сняты, а
рёбра думают, что они на месте.

| | Фасады | Каркас |
|---|---|---|
| прозрачных материалов у мебели | **0** | 2 |
| точек в буфере рёбер | 2016 | 2232 |

Ноль прозрачных — это и есть «сквозь мебель не видно ни стены, ни
соседнего модуля», и меряется он материалами, а не глазами.

**Внутренние детали помечены в данных** (`BoxDraw.inside`): полки,
перегородки и короба ящиков. По этому признаку сцена решает, вести ли по
ним рёбра. Плюс `polygonOffset` на гранях: без него линия, лежащая ровно
на плоскости, наполовину проваливается внутрь, половина проступает сквозь
соседнюю грань — и сплошная мебель снова выглядит сеткой.

### 3D занимает весь экран

Нажал «3D» — панель уезжает, сцена занимает **98 %** ширины; кнопка
«Показать панель» возвращает её (70 %). Панель при этом не
размонтируется, а прячется: выбранный модуль и открытые карточки обязаны
пережить переключение вида.

Кнопка живёт в полосе сцены, а не своей строкой над ней: строкой она
отнимала у сцены полсотни пикселей — ровно тех, из-за которых мебель
уезжала под подвал.

### Все три формы — один код

Прямая, угловая и П-образная собираются одной `runBoxes` и одним
`rowPlacement`; отличается только место ряда. Проверено числом: каждая
следующая стена добавляет РОВНО столько же материалов, сколько
предыдущая (8 → 15 → 22), рёбра у всех лежат на мебели (0 м), прозрачной
мебели нет ни у одной.

### Холодильник: две разные мебели

Встроенный закрыт фасадом того же материала, что соседи; отдельностоящий
виден прибором. Различие лежит в данных (`builtIn`) и доезжает до всех:

```
раскрой   Фасад встройки 1144×596  ·  у отдельностоящего его нет вовсе
смета     1 650 499 ₸  против  1 599 504 ₸
сцена     фасадов 8 → 9, приборов 4 → 3
```

Меши тут считать бесполезно: мебель рисуется пачками ПО МАТЕРИАЛУ, и
исчезнувший фасад пачку не убирает — разница видна в коробках.

### Ловушки слоя 39

330. **Место ряда считает одна функция.** Меши по комнате и рёбра по
    нулю — это проволочный двойник в двух метрах от мебели.
331. **В режиме «Фасады» прозрачных материалов у мебели НОЛЬ.** Это
    число, а не впечатление.
332. **Рёбра — только по внешнему контуру.** Линии по полкам сквозь
    закрытый фасад и превращают мебель в чертёж.
333. **Грани смещены `polygonOffset`.** Линия, лежащая на плоскости,
    без смещения спорит с ней в каждом пикселе.
334. **Режим показа — один признак (`cutaway`).** Второй разошёлся бы с
    первым.
335. **Панель в 3D прячется, а не размонтируется.** Выбранный модуль
    обязан пережить переключение вида.
336. **Разница встройки видна в КОРОБКАХ, а не в мешах.** Пачки по
    материалу не меняются от одной детали.

## Слой 38: правила мебельщика и рабочий экран

Два правила от клиента-мебельщика и пять дефектов экрана, который он
видит каждый день.

### Над холодильником — антресоль, а не потолок

Фактическая высота холодильника всегда меньше паспортной, и над ним
оставляют кладовку. Пенал до потолка не делают: туда не дотянуться, а
место пропадает.

```
FRIDGE_MEZZANINE_MIN_MM = 300     колонна кончается на 300 мм ниже
                                  и эти 300 мм становятся МОДУЛЕМ
```

Это не пустота: у неё корпус, фасад, полка, задняя стенка — шесть
строк в раскрое и свои деньги в смете. Холодильник выше того, что
оставляет правило, отклоняется числом: «Холодильник 2450 мм: над ним
останется 140 мм — антресоль не встанет, нужна высота от 300».

**Антресолей теперь две, и различаются они ОПОРОЙ.** Заказанная стоит на
верхнем ряду (`run.mezzanine`, высоту выбирает заказчик); обязательная —
на крыше колонны, и высота у неё следует из остатка. Опора считается
геометрией (`mezzanineBaseOf`), а не признаком на модуле.

**По дороге нашлось, что антресоль стирала верхний ряд.** На кухне
отметка навески фиксирована (1450), и низ антресоли считался той же
формулой, что низ ряда, — выходило «низ антресоли = низ ряда», а высота
ряда «до антресоли», то есть НОЛЬ. Заказанная антресоль молча превращала
верхние шкафы в детали нулевого размера. Приёмка этого не видела: она
спрашивала про антресоль, а не про шкафы под ней.

### Духовка не выше пояса

Верх ниши духовки — не выше 1500 мм от пола: горячий противень оттуда не
вынуть. Жёлтое, не блокирующее: раскладка применяется, замерщик главнее
алгоритма.

Клиент сформулировал правило как «верх ВЕРХНЕЙ ниши», но последствие в
нём названо про духовку. Проверено на раскладке: микроволновка над
духовкой встаёт на 1828 мм — так её и собирают все, и предупреждать об
этом значило бы кричать на каждой кухне. Меряем духовку: при обычной
колонне её верх 1412 мм, при духовке 900 мм — 1732 мм и жёлтая строка.

### Ракурс показывает одну стену

П-образная в виде «Спереди» разворачивалась в плоскую ленту: три
перпендикулярные стены выстраивались в строку. Развёртки трёх стен в
одной проекции не существует — на чертеже это отдельные виды
(ловушка 292).

| ракурс | что видно |
|---|---|
| Спереди · Слева · Справа | ОДНА стена — выбранная переключателем |
| Сверху | все стены: это план |
| Свободный | все стены |

### Чертёжный слой — по кнопке

Размерные линии поверх 3D читаются плохо: видно и мебель, и чертёж
сразу. Кнопка «Размеры» рядом с остальными действиями, **по умолчанию
выключена**; на перспективе слой не показывается вовсе — там
горизонтальный размер меряет не ту длину.

### Из сцены нельзя выпасть

Все четыре предела считаются от ГАБАРИТА МЕБЕЛИ (`sceneBounds`), а не от
комнаты: у угловой кухни центр комнаты — не центр мебели, и поворот
уносил её за край.

```
поворот   полярный угол 0.12 … π/2−0.02   ни под пол, ни вверх ногами
зум       0.8 … 4 радиуса                 мебель не станет точкой
панорама  цель не дальше 0.5 радиуса      мебель не уедет за кадр
```

Проверяется крайними значениями: поворот на 360° по обеим осям, зум в
оба предела, панорама во все стороны — 22 положения, и после каждого
габарит мебели обязан пересекаться с кадром (`__mwCadFit`).

### Панель собрана по смыслу

```
[ 3D · Схема · План ]   [ Открыть всё · Закрыть всё · Размеры ]
                                     ┌──────────────────────────┐
                                     │ сцена      [Во весь экран]│
                                     │                           │
                                     │ [Спереди · Слева · …]     │
                                     └──────────────────────────┘
```

Ракурсы и «во весь экран» — управление СЦЕНОЙ, и живут они на ней.
Причина не в красоте: тринадцать кнопок в одной полосе переносились на
планшете в три ряда и съедали 140 px высоты.

**Измерено на 1180 × 820:** панель 92 → 46 px, подвал 137 → 81 px (сумма
и кнопки в одну строку), сцена **352 → 520 px, 43 % → 63 % высоты
экрана**.

### Пустая сцена не врёт

До сборки сцена рисовала столешницу, фартук и цоколь — мебель, которой
нет. Теперь пустой ряд не рисует НИЧЕГО (`cabinet.meshes = 0`) и говорит
словами: «Мебели пока нет. Выберите готовое решение или соберите ряд
сами».

Цоколь нашёлся последним и только счётом: столешницу с фартуком видно
глазами, а планка поперёк пустой стены читается как часть интерфейса.

### Ловушки слоя 38

319. **Над холодильником всегда остаётся не меньше 300 мм**, и это
    МОДУЛЬ, а не пустота: у пустоты нет деталей в раскрое.
320. **Антресоль над рядом и антресоль над колонной — разные опоры.**
    Считай их одинаково, и кладовка над холодильником отнимет полметра
    у шкафов на другом конце кухни.
321. **Низ антресоли на кухне — это верх ряда, а не отметка навески.**
    Отметка там фиксирована, и одна формула на двоих обнуляла ряд.
322. **Правило про духовку меряет духовку.** Буквальное «верх верхней
    ниши» срабатывает на каждой стандартной колонне — а предупреждение,
    которое горит всегда, не читает никто.
323. **Фронтальный ракурс показывает одну стену.** Три перпендикулярные
    стены в одной проекции — это лента, а не вид.
324. **Чертёжный слой поверх 3D — по кнопке и по умолчанию выключен.**
325. **Пределы камеры считаются от габарита МЕБЕЛИ.** От комнаты — это
    центр, вокруг которого мебели может не быть вовсе.
326. **«Мебель в кадре» проверяется проекцией габарита**, а не глазами,
    и прогоняется крайними значениями.
327. **Управление сценой живёт на сцене.** В общей полосе оно съедает у
    неё же высоту.
328. **Высота сцены считается от того, что занято, а не долей экрана.**
    Полосы стали тоньше — вычитать надо меньше.
329. **Пустой ряд не рисует случайную геометрию.** Столешница над
    несобранной мебелью читается как «что-то недогрузилось».

## Слой 37: направление открывания — данные, а не ряд

Восьмой случай одного класса ошибки, и самый дорогой: смета выводила
фурнитуру из РЯДА. «Верхний — значит подъёмник, нижний — значит петли».

Из данных это не следует никак. Большинство верхних шкафов делают
распашными, а газлифт стоит в разы дороже петли — и мебельщик видит такое
первым, потому что это его расход.

```
ModuleFill.hinge  влево · вправо · вверх (подъёмник) · вниз (откидной)
                  · две створки · без фасада
```

Поле то же самое: направлений стало пять вместо двух сторон петель, но
второго места под механизм не появилось. Подъёмник, откидной и сторона
присадки — ответы на ОДИН вопрос, и храни их порознь, однажды получишь
фасад, который на чертеже распашной, а в смете на газлифте.

### Одно поле — три места

| кто | что берёт |
|---|---|
| 3D | вокруг чего вращать полотно и где ручка |
| чертёж | диагональ на петельную сторону или дуга механизма |
| раскрой и смета | петли, подъёмник, откидной механизм, ручки |

Считает направление `openingOf` ([lib/millwork/opening.ts](lib/millwork/opening.ts)),
фурнитуру — `openingHardware` там же. Ряд, в котором модуль оказался, на
фурнитуру не влияет вовсе.

### Как поехали деньги

Демо-кухня, ставки типового прайса:

```
было (верхний ряд молча на газлифтах)   1 697 101 ₸
стало (умолчание — петли)               1 629 709 ₸   −67 392 (−4.0 %)

  подъёмники          3 шт. → 0          23 400 ₸ → 0
  столешница          3.8 м → 2.6 м      68 400 ₸ → 46 800 ₸
  плинтус столешницы  3.8 м → 2.6 м       9 500 ₸ →  6 500 ₸
  фартук              3.8 м → 2.6 м      53 200 ₸ → 36 400 ₸
  опоры              20 шт. → 28 шт.      6 000 ₸ →  8 400 ₸
```

Выбранный подъёмник при этом СТОИТ денег и виден строкой: три верхних
фасада на подъёмниках дают 1 649 149 ₸ — на 19 440 ₸ дороже петель, и
петель в смете становится 14 → 8. Раньше он был бесплатным в том смысле,
что его никто не выбирал: он стоял всегда.

### Что ещё считалось из вида модуля

Искали рядом — как в прошлые пять раз, и нашли:

| было | стало |
|---|---|
| опоры под `base`, `corner_base`, `filler` | под всем, что `standsOnFloor` — пенал тоже стоит на полу |
| столешница по всему, что не верхний ряд | по тому, что её НЕСЁТ (`bearsCountertop`): колонна кончается выше |
| карго считалось на петлях | `pullOut` — оно выдвигается на направляющих |
| вариант «Подъёмник» приносил `lift_aventos` И `lift_mechanism` | механизм один, и считает его направление |

`bearsCountertop` спрашивает высоту, а не вид: модуль несёт столешницу,
если стоит на полу и кончается ниже отметки навески верхнего ряда. На то,
что выше, положить её нельзя.

### Умолчание называет себя умолчанием

Не выбрано — считаем распашным на петлях и **говорим это словами**: строка
под суммой в смете и подпись под кнопками выбора. Провенанс лежит в
`fill.openingChosen` и в отпечаток НЕ входит: числа от него не меняются,
он нужен ровно для того, чтобы не молчать и чтобы не переспрашивать после
выбора.

Слова стоят рядом с СУММОЙ, а не на экране замера: там место принадлежит
тому, что происходит на объекте, и не больше двух строк — невнесённая
розетка важнее.

### Правила и отказы

Подъёмник и откидной — только верхний ряд и антресоль. Отказ объясняет
мир: «У нижнего шкафа фасад пойдёт вверх и упрётся в столешницу, а
открытым перекроет рабочее место». Неподходящее в интерфейсе не
показывается вовсе — серая кнопка это вопрос «почему нельзя», а задавать
его при клиенте некому.

Механизм ставится на ОДИН фасад: две створки объединяются, и это сказано
словами, а не сделано молча.

### Фасад открывался В КОРПУС

Поймано числом при переносе оси из компонента в движок: корпус нарисован
от нуля вглубь, комната со стороны +z, а поворот распашной створки шёл на
+90° — то есть полотно уходило СКВОЗЬ шкаф. Глазами это видно, только
если открыть створку, а кнопки «Открыть всё» появились днём раньше
(слой 36). Проверка считает центр открытого полотна: он обязан оказаться
перед фасадом, а не за ним.

### Ловушки слоя 37

310. **Фурнитура считается из ВЫБРАННОГО направления, а не из ряда.**
    «Верхний — значит подъёмник» это догадка, и стоит она денег в каждом
    заказе.
311. **Направление живёт в `fill.hinge` — в одном поле.** Второе поле под
    механизм развело бы чертёж со сметой.
312. **Умолчание названо словами и стоит рядом с суммой.** Молча
    подставленное читается как выбранное.
313. **Провенанс (`openingChosen`) в отпечаток не входит.** Он не меняет
    ни одного числа: подъёмник от петли отличается полем `hinge`.
314. **Выбранное направление пересчёт не трогает.** Сторона петель вправе
    переехать вместе с модулем, выбор человека — нет.
315. **Механизм — только верхний ряд и антресоль**, и отказ называет
    последствие.
316. **Карго не открывается, оно выдвигается.** Петель у него нет.
317. **Открытый фасад уходит НАРУЖУ.** Знак поворота проверяется числом:
    центр полотна перед фасадом, а не за ним.
318. **Рисунок открывания сверяется у КАЖДОГО модуля.** «Хотя бы у
    одного» пропускает ровно ту ошибку, ради которой написана проверка:
    данные и лист расходятся не везде, а в одном месте.

## Слой 35: угол собирается руками

«В чертеже только прямой» — сказал мебельщик, который делает угловые
постоянно. `buildComposition` умел собрать угол ПО ШАБЛОНУ, но рабочее
место знало ровно один ряд: второй не правился, а свободная сборка
отказывала вовсе.

```
Форма   Прямая · Угловая · П-образная
Стены   [Стена А 3800] [Стена Б 1740]      ← переключаются
Угол    Фальш-панель 100 мм · Угловой модуль 900
```

**`Run` остался одним прямым рядом** (слой 17). Угол — это два таких
ряда, П — три; правки идут через тот же `applyOps`, и второго пути
записи не появляется. Активный ряд — тот, чья стена выбрана; соседняя
видна на схеме контуром, иначе не понять, где угол.

### Свободная сборка угла

Отказ снят. Пустые стены — законное начало и для угла: место в углу
урезано С САМОГО НАЧАЛА (второй ряд короче на глубину первого либо на
900 при угловом модуле), а модули человек ставит сам. Первый же
поставленный модуль иначе налез бы на соседний ряд.

### Смета — сумма рядов, а не второй расчёт

`mergeEstimates` складывает сметы по КЛЮЧУ статьи — по тому же, по
которому смета группируется в пять групп. Разовые статьи объекта
(доставка, монтаж, замер) не удваиваются: их платят за объект, а не за
стену. Второй калькулятор угловой кухни разошёлся бы с первым на первой
же правке ставок, и клиенту показали бы одну сумму, а в цех уехала бы
другая.

### Решение угла — это деньги и доступ

| Решение | Второй ряд теряет | Что в смете |
|---|---|---|
| Фальш-панель 100 мм | глубину ряда + 100 | панель, петли 175°, зазор 12 мм |
| Угловой модуль 900×900 | ровно 900 | корпус с каруселью, дороже |

Измерено на демо-стенах: 1 972 923 ₸ против 2 135 148 ₸, и отпечаток
композиции разный — решение угла входит в него (ловушка 155).

### Лист показывает ОБА ряда

Развёртка каждой стены — СВОИМ видом со своими размерами: стены
перпендикулярны, и общая размерная цепочка по ним ничего не значит.
План при этом один — на нём угол и виден. Масштаб общий на лист
(ловушка 197): разный масштаб у двух половин одной кухни читается как
ошибка построения.

Половина кухни на листе — это половина заказа в цеху.

### Глубина проверяется против комнаты

Предел 700 мм — про МЕБЕЛЬ: глубже прибор не встраивают. Человеку важно
другое, и теперь оно сказано последствием: «После этого между рядом и
противоположной стеной останется 440 мм: не разойтись вдвоём и не
открыть ящик напротив».

### Композиция переживает закрытие объекта

Соседние стены жили только в памяти вкладки: замерщик собирал угловую
кухню, показывал клиенту, закрывал объект — и второй ряд пропадал молча.
Это потеря работы, а не неудобство.

`MillworkState` хранит теперь всё: `shape`, `cornerSolution` и `wallRuns`
(ряды соседних стен по индексу). Рабочая стена остаётся в `runs` — на ней
держится всё, что было до углов.

**Совместимость решена ЧТЕНИЕМ, а не переписыванием строк.** Новые поля
необязательные: у прямых кухонь, сохранённых раньше, их просто нет, и
отсутствие читается как «прямая». Миграции базы не нужно вовсе — а
значит, и нечему упасть на половине.

Круг проверяется через `JSON.parse(JSON.stringify(...))`, а не через
`structuredClone`: клон сохранил бы то, чего JSON не знает — `undefined`,
`Map`, числовые ключи, — и круговая проверка «проходила» бы на состоянии,
которое в базу не доедет.

### Отпечаток объекта — от композиции

Главное правило продукта: чертёж, смета, раскрой и рендер сверяются ОДНИМ
числом. Пока угловая кухня несла отпечаток стены А, правка на стене Б его
не меняла — смета и лист могли разъехаться молча.

Теперь у композиции отпечаток композиции (`compositionFingerprint`, он же
учитывает решение угла), а у прямой кухни — по-прежнему отпечаток ряда:
один ряд, одно число, и отпечатки сохранённых объектов не едут.

### Ловушки слоя 35

288. **Угол — два `Run`, а не новый тип ряда.** Вторая ветка раскладки
    разойдётся с первой на первой правке.
289. **Смета композиции — сумма смет рядов по ключу статьи.** Разовые
    статьи объекта не удваиваются.
290. **Место в углу урезано ДО первого модуля**, в том числе на пустых
    стенах: иначе первый поставленный модуль налезет на соседний ряд.
291. **Идентификатор выводится из позиции, поэтому перезаполненный
    модуль получает тот же id.** Проверка «состав изменился» по одним
    идентификаторам ничего не докажет — в шаблоне `rebalance` ставит на
    то же место такой же модуль.
292. **Каждая стена — своя развёртка на листе.** Общая размерная цепочка
    по перпендикулярным стенам не значит ничего.
293. **Проход считается от КОМНАТЫ, а не от габарита мебели.**
294. **Соседние стены сохраняются наравне с рабочей.** Состояние в
    памяти вкладки — это потерянная работа замерщика.
295. **Новые поля состояния необязательные.** Совместимость читается,
    а не мигрируется: миграция может упасть на половине, а отсутствие
    поля — нет.
296. **Круг сохранения проверяется через JSON, а не через
    `structuredClone`.** Клон сохраняет то, чего база не увидит.
297. **Отпечаток угловой кухни — от композиции.** Иначе правка второй
    стены не меняет числа, которым сверяются чертёж и смета.
298. **Демонстрация не сохраняет ничего:** она монтируется без
    `projectId`. Круг «закрыл — открыл» проверяется на состоянии, а не
    на ней.

## Слой 34: размер лежит на приборе, а не на модуле

Четыре вещи, которые мебельщик называет первыми, и все четыре упирались
в одно: продукт считал модуль неделимым.

### Габариты — по прибору

`applianceSize` лежал НА МОДУЛЕ, и в колонне духовка с микроволновкой
получали одну высоту на двоих: микроволновке доставалась духовочная ниша,
и в пенале оставалось двадцать сантиметров пустоты.

`Module.applianceSizes` — набор по прибору, и `columnNiches` спрашивает
каждый свой:

```
паспорт          духовка 608 · микроволновка 416
введено 720/380  духовка 736 · микроволновка 416
```

Операция `set_appliance_size` требует `appliance`: «размер модуля» в
колонне не значит ничего. Чужой прибор в модуль не пишется — отказ
называет, что его здесь нет.

**Соседи ужимаются не молча.** В раскладке по шаблону ряд сходится со
стеной до миллиметра, поэтому расширение прибора всегда за чей-то счёт:
«Холодильник: 900 мм вместо 600. Соседние модули ужались на 300 мм».
Не влезло вовсе — отказ с превышением в миллиметрах.

### Глубина работает

Поле существовало, входило в отпечаток и не делало НИЧЕГО: глубину
корпуса задавал профиль зоны. Теперь `moduleDepthMm` берёт максимум из
стандарта и «глубина прибора + просвет 20 мм»: холодильник 640 отодвигает
модуль с 560 до 660, и это сказано числом. Глубже 700 мм прибор в
корпусный ряд не встраивают — отказ называет выступ.

### Антресоль — позиция, а не свойство

Была признаком верхнего ряда: ни снять отдельно, ни выбрать материал.
Теперь `Run.mezzanine` — своя высота (300–900 мм), свои модули в раскрое
и смете, свой материал через тот же `set_front`.

Живёт она НА РЯДУ, а не в требованиях: верхний ряд пересобирается из
нижнего на каждой правке, и антресоль обязана пережить пересборку вместе
со своим материалом.

**Верхний ряд уступает ей место.** Кухонная ветка `moduleCarcassHeightMm`
считала высоту одной формулой и про антресоль не знала: поставленная
сверху, она занимала ТОТ ЖЕ объём, что шкафы под ней, — инвариант
непересечения поймал это исключением на первом же прогоне.

### Фронты под варочной

Чертёж рисовал два ящика, промпт называл два, а в раскрой уходила ОДНА
глухая панель на всю высоту. Число фронтов задаёт вариант места
(`hob_base` — два), высоты раскладывает `defaultFill`, и дальше их видят
все: раскрой, чертёж, промпт и 3D. Сумма фронтов сходится с высотой
модуля: 140 + 580 = 720.

### Палитра цветов — товар компании, а не список в коде

Клиент работает с МДФ и просит цвет. Цвета лежали в коде: восемь
шестнадцатеричных чисел в готовых дизайнах — и это цвета НАШИ. У компании
свой поставщик, свой прайс и свои декоры; показать клиенту «графит
#3A3D40», которого она не продаёт, значит принять заказ, который она не
выполнит.

**Отдельной таблицы под палитру нет** (ловушка 19): цвет — это ТОВАР и
живёт в `catalog_items` с остальными. Отличают его два поля `meta`:

```
meta.frontBase   из чего фасад: ldsp · mdf_film · mdf_enamel · acrylic · veneer_solid
meta.color       #rrggbb — тот же ключ, что читает surfaces.ts
meta.typical     позиция типовой поставки, а не своя
```

Картинка образца — файл `texture`/`swatch` товара в Storage, тот же, что
подставляется в 3D. Второго источника нет: разошлись бы карточка и схема.

Типовая палитра (RAL и ходовые декоры) заводится тем же
`seedTypicalCatalog`, что и типовой прайс, и подписана так же ориентиром:
«Часть цветов — типовая палитра. Замените на свои в каталоге».

**Артикул входит в отпечаток.** `FrontSpec.itemId` был заведён и нигде не
заполнялся; теперь выбор цвета пишет его, и `frontKey` его учитывает:
«дуб сонома» и «дуб крафт» совпадают по шестнадцатеричному цвету, а в
заказе это разные плиты и разные деньги.

### Ловушки палитры

284. **Палитра — позиции каталога, а не список в коде.** Второй источник
    цветов обещал бы клиенту декор, которого у компании нет.
285. **Цветом считается только позиция с базой И цветом.** Ставка сметы
    в палитру не попадает.
286. **Типовая палитра помечена ориентиром.** Молча выданная чужая
    палитра — это обещание цвета, которого у компании нет.
287. **Артикул входит в ключ материала.** Два декора одного цвета — это
    разные товары, и отпечаток обязан их различать.

### Ловушки слоя 34

278. **Размер лежит на ПРИБОРЕ.** В колонне их два, и «размер модуля»
    там не значит ничего.
279. **Ужатие соседей называется числом.** Молча ужатый ряд — это не тот
    состав, который заказывал клиент.
280. **Введённая глубина обязана двигать корпус.** Поле, которое лежит в
    данных и ничего не делает, хуже отсутствующего.
281. **Антресоль живёт на ряду.** В требованиях она не пережила бы
    пересборку верхнего ряда.
282. **Верхний ряд кончается там, где начинается антресоль.** Кухонная
    ветка высоты про неё не знала, и они занимали один объём.
283. **Число фронтов у приборного модуля — из варианта места**, а высоты
    из `fill`: второй расклад развёл бы раскрой с чертежом.

## Слой 33: модуль с техникой — тоже мебель

Модуль с прибором числился «нишей» и не получал НИЧЕГО: ни фасадной
детали в раскрое, ни материала. Отсюда три жалобы подряд — выбрал шпон, а
верхний пенал остался серым; рядом с холодильником модуль другого цвета;
нижний ряд не красится. Причина одна: безусловный выход `if (isAppliance)
return panels` и такое же исключение в `set_front`.

Физически это неверно. Прибор занимает нишу, но у модуля остаётся корпус
(он и так считался) и остаётся фасад:

| модуль | что закрывает фасад |
|---|---|
| мойка | створка под чашей, за ней сифон |
| варочная | ящики под панелью |
| посудомойка | фасад заподлицо у полностью встроенной |
| колонна | фасады НАД нишей и ПОД ней |
| вытяжка | декоративный фасад шкафа |
| холодильник встроенный | створки во всю высоту |
| **отдельностоящий прибор** | **ничего: фасада нет вовсе** |

Признак один на весь продукт — `hasFacade` в
[lib/millwork/applianceFront.ts](lib/millwork/applianceFront.ts). Участки
считает `facadeSpans` по тем же нишам, что `columnNiches`: второй
формулой их считать нельзя, разойдясь — раскрой начнёт пилить фасад
поверх духовки.

**Как поехали суммы.** Смета считает из раскроя, поэтому исправление
раскроя само сдвинуло деньги:

```
фасады   2.8 м² → 5.41 м²     72 800 ₸ → 140 660 ₸
распил  19.6 м² → 22.21 м²    35 280 ₸ →  39 978 ₸
итого                      1 610 403 ₸ → 1 696 528 ₸   (+86 125, +5.3 %)
```

486 сверок сметы с раскроем сошлись на новых числах — они и должны были
сойтись: обе стороны читают один список деталей.

### «До потолка» отменяла комплектация

Замок `lockedOptions` ставился ТОЛЬКО когда человек трогал переключатель
руками. Опция, пришедшая из шаблона или умолчаний, молча возвращалась
стратегией: `optimal` ставит `upperToCeiling: false`, и переключатель
показывал «до потолка», а между шкафами и потолком оставалось **530 мм**.

Это ловушка 108 ещё раз. Теперь высота верхнего ряда заперта ВСЕГДА:
значение в `options` — это ответ, кто бы его ни дал.

### Размеры прибора вводятся

`APPLIANCE_SLOTS` держит отраслевой стандарт — с него начинается
разговор. Но холодильник бывает 550, 600, 700 и 900 у side-by-side.
`Module.applianceSize` — то, что измерил человек; ниша пересчитывается от
введённой высоты (`nicheHeightMm`), а ЗАЗОРЫ вокруг прибора остаются
наши: их считает код. Габарит входит в отпечаток — прибор 700 вместо 600
это другая ниша, другой раскрой и другие деньги.

Отказ идёт тем же правилом, что и ширина обычного модуля: в шаблоне
соседи ужимаются, в свободной сборке — нет, и превышение названо в
миллиметрах.

### Встроенный прибор читается шкафом

Холодильник за фасадом заподлицо снаружи выглядит пеналом: створка того
же материала, что у соседей. Буква в кружке говорила обратное, и клиент
видел серую вставку там, где стоит обычная на вид мебель. Знак остаётся
только у ОТДЕЛЬНОСТОЯЩЕГО — он виден целиком, и фасада у него нет.

### Вторая ветка «прибор ли это» была в ИНТЕРФЕЙСЕ

Раскрой и смета фасад у приборных модулей увидели сразу, а схема — нет.
Причина не в отрисовке: панель материала не показывалась для модуля с
техникой ВООБЩЕ (`selectedUnit && !selectedUnit.appliance` в Workspace,
`if (unit.appliance) return null` в `FrontMaterialPicker`). Нажать было
некуда — модуль оставался прежнего цвета, а соседи красились.

Копий правила нашлось четыре: гейт панели, сам компонент выбора,
карточки образцов и рисунок филёнки в чертеже. Все сведены к `hasFacade`.

### «До потолка» поднимает и пеналы

`standardHeightMm('tall')` возвращала фиксированную высоту и опцию не
читала: при потолке 3000 пенал холодильника кончался на 2400, над ним
600 мм пустоты. Проверка была зелёной, потому что мерила ТОЛЬКО верхний
ряд — а он честно доходил до верха.

В отрасли бывают оба решения: пенал во всю высоту и пенал плюс
антресоль. Сделано первое — одно число вместо отдельного модуля сверху.
**Второе остаётся дальнейшей работой** и нужно там, где боковина выше
листа ЛДСП (2750 мм): при потолке 3000 корпус пенала 2900 мм из одного
листа не выкроить, а длины листа продукт сегодня не моделирует вовсе.

Чертёж считал высоту пенала СВОЕЙ веткой — `standardHeightMm('tall')` без
опций ряда — и рисовал бы прежнее, что бы ни считала раскладка. Теперь
и он спрашивает `moduleCarcassHeightMm`.

### Ловушки слоя 33

267. **Приборный модуль — это мебель.** У него есть корпус и фасад;
    «ниша» — это место прибора внутри модуля, а не отсутствие модуля.
268. **Участки фасада считает `facadeSpans` по `columnNiches`.** Вторая

270. **Опции, видимые человеку, заперты всегда.** Стратегии незачем

271. **Габарит прибора вводится, зазоры считает код.**
272. **Ниша не меньше прибора.** Округление всегда вверх.
273. **Встройка и отдельностоящий рисуются по-разному.** Различие уже

275. **«До потолка» поднимает ВСЁ, а не верхний ряд.** Кухня до потолка

277. **Проверка «до потолка» меряет самый высокий элемент ряда.**
    Пока она смотрела только верхний ряд, она была зелёной на

## Слой 32: рабочий экран стал плоским

Три.js ушёл из интерфейса. Клиент выбирает глазами, но для этого не нужен
WebGL: вид спереди и план рассказывают о мебели всё, что решается на
встрече, — состав, ширины, что за фасадом и из чего он сделан.

```
Замер → Решение → Конфигуратор → Результат
                  ┌──────────────┬───────────┐
                  │ схема 70 %   │ ФОТО      │
                  │ спереди·план │ варианты  │
                  │ вектор,      │ образцы   │
                  │ материалом   │ материал  │
                  │              │ состав    │
                  ├──────────────┴───────────┤
                  │  сумма · Назад · Дальше  │
                  └──────────────────────────┘
```

Схема рисуется ТЕМ ЖЕ кодом, что чертёжный лист (`ElevationDrawing`,
`PlanDrawing`). Второй отрисовки не существует намеренно — она разошлась
бы с листом на первой правке, и клиент выбрал бы по схеме одно, а
подписал другое. Отличие ровно одно: `showMaterial`.

### Сцена жива, но не рисует

`KitchenScene` осталась смонтированной за экраном (`x = −3000`): она
снимает clay-кадр, а без кадра нет ни сравнения «до и после», ни
генерации — то есть нет главной продающей функции.

**`frameloop="demand"` для невидимой сцены оказался недостаточным.**
Измерено: 588 кадров за минуту обычной работы — сцена перерисовывалась
на каждую правку состава, хотя её никто не видит. Поставлено
`frameloop="never"`: 0 кадров за ту же минуту. Захват не пострадал —
`captureScene` вызывает `gl.render` сам.

### Материал виден на схеме

Заливка фасада — не абстрактная плашка, а материал: цвет плюс рисунок
(волокно шпона, крошка ЛДСП, блик глянца, ровная эмаль). Филёнка рисуется
рамой и вставкой, как в раскрое.

**Откуда картинка.** Ровно два источника, и оба принадлежат компании:
файл `texture`/`swatch` её каталога в Storage — либо процедурный рисунок
по базе материала, выведенный из чисел. Третьего нет: чужие фотографии в
репозитории — это образцы чужих поставщиков, и компания показывала бы
клиенту плиту, которой не продаёт.

### Выноски: проверка мерила не то

Проверка «полки выносок не садятся друг на друга» сравнивала Y-координаты
полок с допуском **1 мм модельного пространства** — при 1:25 это 0.04 мм
бумаги. Она проходила на подписях, лежащих друг на друге: про высоту
строки и её ширину не знала ничего.

Починены обе стороны:

* зазор задаёт вызывающий, пересчитывая кегль в миллиметры модели;
* переполненная сторона отдаёт лишние выноски соседней — вместимость
  поля это факт, а не предпочтение;
* излом линии стоит на границе рисунка: поле подписей принадлежит
  подписям, и диагональ туда не заходит;
* поле расширено до самой длинной подписи (236 единиц при поле 235 —
  хвост строки вылезал на чертёж);
* приёмка меряет НАСТОЯЩИЕ прямоугольники текста в браузере и сами
  отрезки линий, а не их габариты: по габаритам диагональ накрывает
  пол-листа, и первая версия проверки насчитала 35 несуществующих
  пересечений.

## Слой 31: один рабочий экран

«Состав», «Материалы» и «Результат» были тремя шагами, и замерщик не
видел, что меняется, пока не перейдёт дальше. Клиент при этом сидит рядом
и ждёт. Теперь работа идёт на ОДНОМ экране:

```
Замер  →  Решение  →  Конфигуратор  →  Результат
                      ┌──────────────┬───────────┐
                      │   3D-сцена   │  панель   │
                      │    70 %      │  варианты │
                      │   ширины     │  материал │
                      │              │  состав   │
                      │              │  дизайны  │
                      ├──────────────┴───────────┤
                      │  сумма · Назад · Дальше  │
                      └──────────────────────────┘
```

Нажал на модуль в сцене — справа его варианты с миниатюрой и разницей в
цене, ниже материал фасада. Выбрал — сцена поменялась на месте, сумма
внизу пересчиталась. Никаких переходов.

**Чертёж на «Результате» остался намеренно.** Лист, план и раскрой — это
документы для цеха, а не то, что показывают клиенту.

### Сцена одна, и она не пересоздаётся

`sceneSlot` — ОДИН элемент: в конфигураторе он стоит слева и виден, на
«Результате» уезжает за экран, но остаётся смонтированным, потому что
именно он снимает clay-кадр (ловушка 61). Один и тот же элемент означает,
что правка состава или материала не пересоздаёт канвас — и поворот сцены
переживает любую правку.

**Высота сцены считается от свободного места, а не долей вьюпорта.**
`68vh` при экране 900 px давал 612 px при доступных 601: сцена уезжала
под подвал ровно на те одиннадцать пикселей, из-за которых её приходится
прокручивать. Вычитаем полосы шапки и подвала, а не подбираем долю.

### Затухание камеры доводится до конца

`enableDamping` двигает камеру после отпускания мыши — но только в тех
кадрах, которые кто-то нарисовал. При `frameloop="demand"` кадров после
отпускания нет, инерция замирает на полпути и дальше доезжает **по шагу
на каждую правку состава**. Со стороны это выглядит как «правка сбросила
поворот»: клиент рассматривает мебель под своим углом, замерщик меняет
фасад — камера уползает.

`DampingSettler` в [components/RoomCanvas.tsx](components/RoomCanvas.tsx)
просит следующий кадр, пока затухание живо, — ровно как техническая сцена.

Проверять это точным равенством позы НЕЛЬЗЯ: в headless сцена рисует
1–2 кадра в секунду (ловушка 97), и затухание доезжает десятки секунд
вместо полусекунды. Приёмка сверяет то, что действительно ломается:
камера не ВОЗВРАЩАЕТСЯ в исходную рамку.

### Ловушки слоя 31

253. **Сцена — один элемент на все шаги.** Второй экземпляр рядом с
    первым это второй канвас, второй контекст WebGL и потерянный поворот.
254. **Высота сцены — от свободного места.** Доля вьюпорта не знает про
    шапку и подвал.
255. **Затухание камеры доводится кадрами.** Иначе оно доезжает на
    правках и читается как сброс поворота.
256. **Поза камеры в headless не сверяется побайтово.** Проверяется, что
    камера не вернулась домой.
257. **Один выбор — одно место на экране.** Панель материала стояла и в
    ленте состава, и под сценой: приёмка находила десять кнопок вместо
    пяти, а человек — две разные настройки одного и того же.

## Слой 30: материал фасада

Клиент выбирает материал глазами. До этого слоя у фасада были только цвет
и `meta.finish` из артикула — одна поверхность на весь гарнитур, и та
из каталога. Мебельщик же говорит тремя независимыми словами:

```
base       ldsp · mdf_film · mdf_enamel · acrylic · veneer_solid
construct  solid · framed · radius
finish     gloss · matte · textured
```

`Module.front` — материал КАЖДОГО модуля. Верх и низ могут отличаться, и
половина готовых дизайнов этим и пользуется. Пусто — фасад по умолчанию
(ЛДСП, цельный, мат): ряды, собранные до этого слоя, ничего не теряют, и
отпечаток у них не меняется — `frontPart` умолчание не пишет.

### Правила технологии — не декорация

Продать фасад, которого цех не сделает, хуже, чем не продать ничего.
Правила живут одним списком в [lib/millwork/frontMaterial.ts](lib/millwork/frontMaterial.ts);
разложенные по интерфейсу, раскрою и промпту, они разойдутся на первом же
новом материале.

| Правило | Почему | Что делает конфигуратор |
|---|---|---|
| ЛДСП только цельная | пилится прямыми | радиуса и филёнки нет в списке вовсе |
| Радиус только МДФ и шпон | остальное трескается на гибе | отказ называет, из чего он бывает |
| Эмаль и плёнка без кромки | сплошной слой и загиб на торцы | у фасада НЕТ строки кромки в раскрое |
| Филёнка — две детали | рама и вставка режутся отдельно | две строки раскроя вместо одной |

**Смета видит это сама.** Она считает количества из раскроя
(`panelMaterials`), поэтому исчезнувшая строка кромки забирает с собой и
метры, и деньги: 52.91 м → 34.77 м, 23 810 ₸ → 15 647 ₸. Второго места,
где это надо было бы поправить, не существует.

Отказ объясняет МИР, а не запрещает: «ЛДСП пилится только прямыми» —
эту фразу замерщик перескажет клиенту слово в слово, «недопустимая
комбинация» пересказать нельзя. И отказ ничего не роняет: человек всего
лишь нажал на материал.

### Материал виден в сцене сразу

Выбрал модуль → выбрал материал → фасад перекрасился. Без пересчёта
всего и без ухода на другой шаг: тот же `FrontMaterialPicker` стоит и в
ленте состава, и под сценой — компонент ОДИН, иначе два места разойдутся.

Фасады рисуются пачками ПО МАТЕРИАЛУ (`PartBox.frontKey`): пачек столько,
сколько разных фасадов в ряду, а не сколько модулей. Материал под ключом
создаётся один раз и дальше только меняется — пересоздание это
перекомпиляция шейдера ровно в тот момент, когда клиент перебирает
варианты.

Различаются глазами четыре вещи: цвет каталога, глянец против мата
(0.06 против 0.78 — не «0.4 против 0.5»), филёнка рамой и вставкой
в разных плоскостях, стекло витрины.

### Готовые дизайны

Мебельщик не собирает материал по атрибутам — он показывает решения,
которые уже делал, и называет их словами. Восемь пресетов связывают
фасад низа, фасад верха, столешницу и ручки; один тап кладёт всё на ряд
теми же операциями, что и поштучная правка. Поэтому ручная правка
СИЛЬНЕЕ: она применяется позже и переписывает то, что положил дизайн.

Пресеты ссылаются на позиции каталога ЭТОЙ организации. Нет позиции —
дизайн недоступен и говорит, какой именно не хватает; похожая не
подставляется молча, иначе клиент подпишет смету на товар, которого
компания не продаёт.

### Ловушки слоя 30

243. **Правила технологии — в одном месте.** Разложенные по интерфейсу,
    раскрою и промпту, они разойдутся на первом же новом материале.
244. **Кромка снимается в РАСКРОЕ, а не в смете.** Смета считает из
    раскроя; правка в двух местах — это тот самый класс ошибки, который
    слой 24 закрывал пять раз подряд.
245. **Филёнка — две детали и в раскрое, и в сцене, и в промпте.** Одна
    панель означала бы гладкий фасад на производстве.
246. **Умолчание не пишется в отпечаток.** Иначе изменились бы отпечатки
    всех рядов, собранных до этого слоя.
247. **Фасад встройки идёт материалом ряда.** Холодильник закрыт
    настоящей створкой: одна ЛДСП среди эмали видна сразу, а в раскрое
    ещё и с кромкой, которой у остальных нет.
248. **Материалы фасадов создаются по ключу и не пересоздаются.** Пачек
    столько, сколько разных фасадов, а не сколько модулей.
249. **Выделение переживает перебор материалов.** Снятое выделение
    убирает панель после первого же нажатия — дальше нажимать не на что.
250. **Смена материала перерисовывает кадр явно.** `frameloop="demand"`:
    без `invalidate()` материал сменится в памяти, а на экране останется
    прежний, и никакой расчёт этого не заметит.
251. **Дизайн, для которого нет позиции в каталоге, недоступен и называет
    её.** Похожая не подставляется.
252. **Ручная правка сильнее дизайна.** Дизайн — это те же операции,
    поэтому правка просто применяется после.

## Слой 29: свободный конструктор

Ряд собирался только из шаблона. На вопрос мебельщика «а мой дизайн
сделать сможешь?» ответить было нечем: девять случаев из десяти закрывает
готовое решение, а десятый упирался в то, что другого пути нет вовсе.
Теперь путей два, и шаблон остаётся быстрым стартом, а не единственным
входом.

```
RunRequirements.mode = 'template'  раскладку считает buildRun, ряд сходится со стеной
                     = 'free'      ряд собирает человек, ряд имеет право не сходиться
```

### Пустая стена — законное состояние

`buildRun` в свободном режиме возвращает `emptyRun`: тот же `Run`, ноль
модулей, `residualMm` во всю стену и свой устойчивый отпечаток. Чертёж,
смета, раскрой и 3D работают с ним без единой оговорки, смета ровно ноль.

Ноль в смете и пустая лента читаются как «не загрузилось», поэтому пустой
ряд объясняет себя словами: «Стена 3800 мм пустая: мебели нет, и смета
поэтому нулевая». То же правило, что у зон «в разработке», — система не
делает вид, что сломалась там, где она просто ещё не начата.

**Столешница, цоколь и фартук считаются по СОБРАННОМУ ряду, а не по
стене.** Раньше их метраж брался из `run.lengthMm`, и пустая стена стоила
141 588 ₸ — столешница на мебель, которой нет. В раскладке по шаблону обе
величины равны, поэтому подмена не была видна.

### Свободная сборка идёт через applyOps

Собственного пути записи у неё нет: «+ Модуль», ширины, прибор из состава
и «Удалить» — это `add_module`, `set_width`, `remove_module`, те же
операции, которыми правится ряд из шаблона. Отсюда главное следствие:
**один состав даёт один отпечаток, как бы его ни собрали** — вручную и
шаблоном получается один и тот же `configurationFingerprint`. Проверяется
приёмкой; расхождение ловилось дважды — у поставленного руками
холодильника не было `builtIn`, а сторона петель замерзала на моменте
добавления вместо того, чтобы считаться от позиции.

### У модуля есть МЕСТО, а не только порядок

В раскладке по шаблону `offsetMm` — величина выведенная: модули идут
подряд, и позиция каждого это сумма ширин предыдущих. В свободной сборке
наоборот: человек ставит модуль туда, куда хочет, и между модулями
законно появляется пустое место. Удалённый посреди ряда модуль оставляет
дырку ТАМ, ГДЕ СТОЯЛ, — ряд не схлопывается.

Инвариантный слой к этому был готов: `assertRunFits` уже сверял
`offsetMm + widthMm` с началом следующего модуля и с длиной стены, а
`moduleOverlaps` считает габариты по тем же числам. Repack делал только
`reindex`; в свободном режиме вместо него `placeFree` — он сортирует по
позиции и выводит идентификатор, но ничего не двигает.

Отсюда важное различие в интерфейсе: **свободное место и самый широкий
промежуток — разные величины**. «Свободно 900 мм» может означать три щели
по 300, и предлагать по общей сумме значит обещать модуль, которому
некуда встать.

### Перетаскивание: соседи не двигаются

Мебельщик собирает ряд так, как привык: ставит и двигает. Модуль тянется
вдоль ряда шагом 50 мм — тем же, что у ширины, — и на чертеже, и в сцене.
Занятое место **отказывает числом**: «Здесь стоит «Дверца»: перекрытие
450 мм. Ближайшее свободное место — 1050 мм». Раздвигать соседей нельзя:
это ровно то, от чего защищает отказ от `rebalance`.

Куда модуль встанет, видно ДО отпускания: подсветка едет под пальцем и
краснеет над занятым местом. В сцене рамка двигается прямо в графе
(`frameloop="demand"` — состояние React на каждом движении перерисовывало
бы всю мебель), а операция применяется ОДИН раз, на отпускании: по дороге
модуль проходит сквозь занятые места, и промежуточные положения были бы
чередой отказов при совершенно нормальном жесте.

### «+» ставит готовый модуль

Не пустое место заданной ширины, которому потом выбирают начинку вторым
жестом, а сразу «Карго 400» или «Витрина 600»: `add_module` несёт
`variant`. Список — тот же `MODULE_VARIANTS`, отфильтрованный по зоне и по
СВОБОДНОМУ ПРОМЕЖУТКУ. Ниши под приборы (`impliesAppliance`) оттуда
исключены: поставленные без прибора, они дают модуль, который выглядит
нишей, но в смете прибора не несёт.

### Место после удаления не перезаполняется

`rebalance` дозаполняет недостачу и снимает излишек с соседей. Для
шаблона это правильно, для свободной сборки — отъём контроля: удалил
модуль — на его месте немедленно вырос другой; потянул ширину — соседи
молча ужались, и клиент увидел не тот состав, который заказывал. Поэтому
в свободном режиме вместо него `reindex`.

Ряд, который не сходится, — это **не ошибка, а «ещё не собрано»**:
остаток стоит числом и нейтральным цветом. Красным он остаётся только
в режиме шаблона, где недостача действительно означает недостачу.

Отказы называют миллиметры и ничего не ломают: модулю не хватило стены —
«Не хватает 400 мм: свободно 200 мм, а модуль 600 мм», и ряд остаётся
прежним. Ронять `assertRunFits` исключением на нажатие «добавить» нельзя.

## Слой 28: выбор картинкой и совпадение с визуализацией

### Лента превью вместо списка названий

Мебельщик держит варианты в голове КАРТИНКАМИ, и клиент выбирает глазами.
«Карго» и «ящик с дверцей» — два слова, между которыми клиент не выбирает;
два рисунка — выбирает мгновенно.

Каждая карточка ([VariantStrip.tsx](components/millwork/VariantStrip.tsx)) —
настоящий мини-чертёж модуля с этим вариантом, нарисованный тем же
`FrontGlyph`, что и большой чертёж. Заготовленная иконка разошлась бы
с чертежом на первой правке, а новый вариант требовал бы художника; здесь
он появляется сам.

Под схемой — РАЗНИЦА в цене, считанная настоящим пересчётом. Выбор
перестраивает чертёж на месте, выделение остаётся, лента не закрывается:
замерщик перебирает варианты подряд, пока клиент смотрит.
Замер: от касания до перерисованного чертежа **83 мс**.

Вариантов стало столько, чтобы в каждом месте было из чего выбрать: две
дверцы, четыре ящика, витрина с подсветкой, ниша под микроволновку, колонна
«духовка + СВЧ», холодильник, высокая витрина. Ограничение витрины в 900 мм
снято: это предел на СТВОРКУ, а на модуле 1200 мм ставят две по 600.

### Модуль ловит палец всей площадью

Контур модуля нарисован `fill="none"`, и такая фигура ловит указатель
только по линии обводки (ловушка 101). Прозрачный прямоугольник стоял
только у переносимой техники — по остальным модулям попасть можно было
лишь в миллиметровую рамку, и лента не открывалась вовсе. Теперь он есть
у каждого модуля.

### Визуализация видит то же, что чертёж

Блок «СОСТАВ ГАРНИТУРА» называл приборы и ширины, но не говорил, ЧТО У
МОДУЛЯ ЗА ФАСАДОМ. Пустоту модель заполняет по-своему — рисует всё
сплошными дверцами, и ящики с витриной пропадают с картинки.

[lib/millwork/promptFronts.ts](lib/millwork/promptFronts.ts) описывает
каждый модуль строкой «0–600 холодильник встроенный, закрыт фасадом
заподлицо» — по обоим рядам, слева направо. Числа берутся из `Run`, руками
не пишется ничего. Витрина названа витриной, подсветка — включённой,
ящики — числом фронтов.

Жёсткие правила («ящики и дверцы различаются», «открытые секции и витрины
остаются открытыми», «состав не дополняется») стоят в `GEOMETRY_LOCK` ДО
описания стиля: стиль модель читает как пожелание, а `GEOMETRY_LOCK` —
как ограничение.

`assertCompositionMatches` сверяет перед отправкой: число описанных модулей
обязано совпасть с рядом, и ящики не должны потеряться. Расхождение —
исключение на сборке запроса, а не сюрприз на картинке: рендер стоит денег,
а неверная картинка стоит доверия.

**Вариант доезжает до промпта через мету сцены** (`runModules[].variant` и
`runUppers[].units`). Верхний ряд раньше уходил только участками
«0–1200, 3 шт.» — витрина, сушилка и подъёмник живут именно там, и модель
о них не знала.

### Ловушки слоя 28

220. **Карточка варианта — мини-чертёж тем же кодом.** Иконка разойдётся
    с чертежом на первой правке.
221. **Под карточкой разница в цене, а не сумма.**
222. **Лента не закрывается после выбора**, а выделение остаётся:
    варианты перебирают подряд при клиенте.
223. **У модуля есть прозрачная зона захвата.** `fill="none"` ловит
    указатель только по обводке.
224. **Предел ширины у витрины — на створку, а не на модуль.**
225. **Промпт описывает ОБА ряда помодульно, с фронтами.** Без этого
    модель рисует сплошные дверцы.
226. **Правила про ящики и витрины идут в `GEOMETRY_LOCK` до стиля.**

228. **Вариант обязан попадать в мету сцены.** Верхний ряд участками —

## Слой 27: вариант виден на чертеже

Витрина с подсветкой на чертеже выглядела обычным шкафом, карго — обычной
дверцей, модуль под мойку — тоже. Это не единичный промах: рисунок вариантов
не был проверен ни одной приёмкой, потому что проверять было нечего —
чертёж рисовал прямоугольники, а не варианты.

### Что видно на фасаде — это данные

[lib/millwork/frontGlyph.ts](lib/millwork/frontGlyph.ts) отвечает одним
списком: створка, шов, ящики по числу фронтов, стекло, рама, полки сквозь
стекло, волна подсветки, стрелка карго, решётка сушилки, дуга подъёмника,
пунктирный вырез чаши, полоса варочной, воздуховод вытяжки.
[FrontGlyph.tsx](components/millwork/FrontGlyph.tsx) только рисует.

Разведи эти две вещи по разным местам — и приёмка перестанет ловить
варианты, которые выглядят одинаково. Именно так витрина и оказалась
шкафом.

**Стекло витрины — незакрашенное поле с рамой и бликом**, а не заливка:
сплошная плашка на чёрно-белой печати схлопывается, и витрина снова
становится шкафом.

### Приёмка ловит одинаковые рисунки

`verify-millwork` строит модуль для КАЖДОГО варианта из `MODULE_VARIANTS` и
сверяет подписи рисунка. Два варианта с одинаковым набором элементов —
это дефект, и он падает.

Сравнение идёт **внутри ряда**: клиент выбирает из того, что бывает в этом
месте. Открытая полка наверху и открытая секция внизу — одна и та же мебель
на разной высоте, выдумывать им разный рисунок значит врать.

Проверяется и режим «Внутри»: фасады сняты, но наполнение остаётся — у
витрины полки, у карго корзины, у сушилки решётка. Иначе разрез не
отличает варианты, а отличаются они именно начинкой.

### Прибор решает за себя

`currentVariant` выводил вариант только из явного выбора, поэтому модуль
под мойкой считался обычной дверцей — и рисовался ею. Теперь мойка и
варочная определяют вариант сами: у подмоечного нет дна и есть вырез,
у модуля под варочной верхний ящик укорочен. Это факт прибора, а не
предпочтение.

Ставки сметы от этого не поехали: `variantEstimateKeys` по-прежнему читает
ЯВНЫЙ выбор — снимок цен в подписанных сметах не должен меняться от
уточнения рисунка.

### Ловушки слоя 27

214. **Что рисовать — данные, а не разметка.** Рисунок варианта живёт
    в `frontGlyph`, компонент только рисует; иначе одинаковые варианты
    никто не поймает.
215. **Стекло — незакрашенное поле с рамой.** Заливка схлопывается на
    печати.
216. **Варианты сравниваются внутри ряда.** Разные ряды — разные места,
    и одинаковый рисунок там честен.
217. **Режим «Внутри» показывает начинку варианта**, а не голый корпус.
218. **Мойка и варочная задают вариант сами.** Ждать явного выбора значит
    рисовать не ту мебель.
219. **Уточнение рисунка не трогает ставки сметы.** `variantEstimateKeys`
    читает явный выбор.

## Слой 26: лист, который принимает проектировщик

Слой 25 собрал виды на один лист. Этот доводит лист до состояния, в котором
его принимает не только цех, но и проектировщик: аксонометрия, выноски с
материалами, отраслевые обозначения, примечания и штамп.

### Аксонометрия рисуется в SVG, а не снимается со сцены

Чертёж печатают: вектор на бумаге читается, снимок канваса рассыпается. Плюс
детерминизм — тот же ряд даёт тот же рисунок на любой машине, без GPU и без
ожидания кадра. Изометрия простая (30° / 30°, без перспективы), коробки — те
же, что дают `cabinetBoxes`.

Три состояния: закрытый, с наполнением, голый корпус. Материалы различаются
ШТРИХОВКОЙ, а не цветом: лист печатают чёрно-белым, и цвет там пропадёт.
Грани непрозрачные — сквозь полупрозрачные заливки виден весь ряд насквозь,
и объём превращается в рентген.

**Масштаб у аксонометрии свой.** Метрические виды держат один масштаб на
всех — по ним мерят. Тянуть из-за объёмного вида фасад с планом в 1:50
значит испортить ровно то, ради чего лист печатают.

### Выноски: линия, излом, полка, текст

Название берётся из каталога компании ЦЕЛИКОМ, вместе с артикулом. Артикул
не выбран — идёт общее описание и слова «артикул не согласован»: по чертежу
без этого нельзя ни заказать материал, ни проверить, что привезли именно
его. На конце линии ТОЧКА, а не стрелка — так принято в мебельных чертежах.

Полки разводятся РАВНОМЕРНО по высоте листа в порядке высоты точек.
Раскладка «от точки и ниже с шагом» упиралась в пол: последние три выноски
садились на одну высоту и подписи наезжали друг на друга. Ловится проверкой
пересечений прямоугольников в браузере, а не глазами.

### Отраслевые обозначения

Треугольник направления открывания заменён ДИАГОНАЛЯМИ, сходящимися на
петельной стороне: понятный треугольник был выдуман нами, а диагонали
мебельщик читает не глядя. Плюс дуга подъёмника, линия ящика со стрелкой
вперёд, точка «Tip-on», волна подсветки, стрелка направления волокон.

На плане — условные знаки коммуникаций и ЛЕГЕНДА в углу листа: буква «В» в
кружке это ребус (вода, вентиляция или выключатель), а знак с расшифровкой
читается один раз.

### Примечания и штамп

Девять пунктов на КАЖДОМ листе. Это не формальность: «размеры уточняются
после чистовой отделки стен» — та строка, которая решает спор о том, кто
платит за переделку, когда штукатур увёл стену на два сантиметра.
Позиции с допущениями называются поимённо.

Штамп: разработал, проверил (пустая строка под подпись), заказчик, объект,
изделие с номером позиции, дата, масштаб, лист. Логотип и телефон — из
настроек организации.

**Позиции сквозные по объекту** (`МИ-поз.1`, `МИ-поз.2`): две кухни в одной
квартире бывают, а два «поз.1» — это спор бригад при разгрузке. В штампе
стоит ИЗДЕЛИЕ («Кухонный гарнитур»), а не помещение: по этой строке на
производстве понимают, что приехало.

    на чёрно-белом принтере в цеху.

## Слой 25: чертёжный лист, а не один вид

Проектировщик работает с ЛИСТОМ: фасад, разрезы и план перед глазами разом,
потому что вопросы живут между ними — «пройдёт ли столешница мимо
подоконника», «что там за фасадом». У нас был один вид за раз, вкладками:
цех такой лист прочитает, а проектировщик не примет.

```
┌──────────────────────────────────────────────────────┐
│ Фасад ряда 1:25   Разрез боковой   Разрез с наполн.  │
│                                                      │
│ План 1:25                                            │
├──────────────────────────────────────────────────────┤
│ Примечания                                    Штамп  │
└──────────────────────────────────────────────────────┘
```

### Масштаб настоящий, а не «примерно такой»

Раньше чертёж растягивался по ширине экрана: снять с него размер линейкой
было нельзя. Теперь ширина вида задана в МИЛЛИМЕТРАХ БУМАГИ, и при 1:25
тысяча миллиметров мебели занимает ровно сорок миллиметров листа —
проверено измерением в режиме печати (`node scripts/check-sheet.mjs`).

**Масштаб один на весь лист.** Глаз перестраивается однажды, и размеры
сравниваются между видами напрямую. `fitComposition` перебирает
стандартный ряд 1:10 · 1:20 · 1:25 · 1:30 · 1:50 и берёт самый крупный,
при котором компоновка складывается в ОДНУ страницу. Промежуточных вроде
1:23 не бывает: по ним нельзя мерить.

### Виды становятся в строку, пока хватает ширины

Фасад 148 мм и два разреза по 44 мм помещаются рядом на поле A3 — лист
используется целиком. Не хватило высоты — следующий лист со своим номером
и тем же штампом. Ужимать чертёж, чтобы «влезло», нельзя: масштаб
перестанет быть масштабом.

### На экране лист вписан, на бумаге натуральный

Поле A3 — 400 мм, полтора экрана планшета. Лист уменьшается ЦЕЛИКОМ одним
преобразованием (масштаб внутри от этого не врёт, он остаётся отношением),
а печать преобразование снимает. Пикселей в миллиметре меряет линейка на
100 мм в самой разметке: константа 3.78 врёт на половине машин.

Формат выбирается по составу: A3 по умолчанию, A4 для короткого ряда —
печатать двухметровую тумбу на A3 значит тратить бумагу компании.

### Боковой разрез

Новый вид ([SectionDrawing.tsx](components/millwork/SectionDrawing.tsx)):
глубина корпуса, высота столешницы, свес, утопленный цоколь, отметка низа
верхнего ряда. Рисуется В МИЛЛИМЕТРАХ — `viewBox` совпадает с натурой,
поэтому масштаб получается делением, а не подгонкой. Числа те же
`GEOMETRY`, что держат раскладку.

Вкладки «План» больше нет: план лежит на том же листе. Отдельный экран под
один вид заставлял держать в голове то, что должно быть перед глазами.

## Слой 21: сцена, которая тянет планшет

Ряд из тринадцати модулей — это под сотню коробок: боковины, дно, крыша,
задняя стенка, полки, фасады, ручки. Каждая была своим мешем, и сцена
стоила **99 мешей и 103 вызова отрисовки** — при том, что мебель стоит
на месте и не двигается вовсе.

```
                было      стало
меши гарнитура    99         7
вызовы отрисовки 103 (сцена) 7 (гарнитур) · 51 (сцена)
материалы          7         6
```

### Неподвижное описывается числами

[lib/millwork/cabinetBoxes.ts](lib/millwork/cabinetBoxes.ts) — чистая
функция: модуль → список коробок с материалом и, если деталь подвижная,
с идентификатором. Корпус, закрытые фасады, ручки, техника.
[InstancedBoxes.tsx](components/millwork/cabinet3d/InstancedBoxes.tsx)
рисует каждый материал одним `InstancedMesh`: четыре вызова на весь ряд.

Матрицы пересобираются только при смене состава — раскладка меняется по
нажатию, а не каждый кадр.

### Едет — значит своим мешем

Открытая дверца и выехавший ящик из общей пачки уходят: у них своя дуга.
Возвращаются они не по «открыто/закрыто», а по факту остановки
(`onSettle` в [useSlide.ts](components/millwork/cabinet3d/useSlide.ts)) —
иначе створка на полпути исчезала бы из одного места и появлялась
закрытой в другом.

### Зона касания не рисуется

Коллайдеры на 44 px — невидимые меши, но прозрачный материал всё равно
уходил в отрисовку: тринадцать модулей давали больше тридцати вызовов на
то, чего не видно. `visible={false}` их гасит, а луч указателя их
по-прежнему находит — проверено кликом по мебели в браузере.

### Свет и тени

Карты теней сняты: второй проход по каждому мешу стоит на планшете
половины кадра, а мебель стоит на полу от КОНТАКТНОЙ тени — она одна и
рисуется однажды. Окружение — пресет `apartment` из drei, но под границей
ошибок и `Suspense`: HDRI он тянет из сети, и без интернета сцена виснет
(ловушка 3). Не загрузился — остаётся своё окружение, и замерщик в
новостройке без связи этого не заметит.

`dpr={[1, 1.75]}`: ретина-планшет умножает площадь отрисовки вчетверо, а
разницы между 1.75 и 2 на мебели не видно. `frameloop="demand"` остаётся
и на видимой сцене: мебель стоит, пока её не тронули.

178. **Деталь возвращается в общую пачку по остановке, а не по флагу
    «закрыто».** Иначе она исчезает на полпути.
179. **Зоны касания не рисуются.** Прозрачный меш — это вызов отрисовки.
180. **Число экземпляров задаётся при создании буфера.** Меняется состав —
    меш пересоздаётся через `key`, иначе буфер остаётся прежней длины.
181. **`computeBoundingSphere` после смены матриц.** Без него мебель
    пропадает при отсечении по камере, стоя в кадре.
182. **Пресет окружения — только под границей ошибок.** Сеть отвалится —
    сцена не должна гаснуть.
183. **Кадры в секунду в headless не мерятся** (ловушка 97). Честное

    `__mwCabinetCalls` меряет ИМЕННО гарнитур, пряча остальную сцену на

## Слой 22: материал меняется мгновенно

Клиент на встрече перебирает фасады подряд: белый, дуб, графит,
фрезерованный. Между нажатием и картинкой не должно быть ничего.

Материалы создаются ОДИН РАЗ и дальше только меняются: `color.set()`,
`roughness`, `map`. Новый материал на каждое нажатие — это перекомпиляция
шейдера и заметная задержка на планшете.

Что берётся из артикула ([lib/millwork/surfaces.ts](lib/millwork/surfaces.ts)):

| Свойство | Откуда | Что делает |
|---|---|---|
| цвет | `meta.color`, шестнадцатеричный | присваивается материалу |
| фактура | `meta.finish` | глянец 0.12, мат 0.62, софт-тач 0.85 — это `roughness` |
| текстура | файл `texture` или `swatch` | `map` из Storage через кэш |
| раскладка | `tiling.moduleSize` | число повторов текстуры |

**Фрезеровка — это рельеф, а не цвет.** Карта нормалей с вертикальными
бороздками рисуется на канвасе прямо на месте
([milledNormal.ts](components/millwork/cabinet3d/milledNormal.ts)): файл
пришлось бы тянуть из сети, а сцена обязана работать в квартире без
интернета.

Фартук — отдельная поверхность и отдельный меш ВНЕ гарнитура: это
отделка стены, и в смете он идёт своей строкой.

### Ловушки слоя 22

184. **Материалы не пересоздаются.** Меняются цвет, шероховатость и карта.
185. **Мусор в `meta` не красит мебель в чёрное.** Цвет принимается только
    как `#rrggbb`, фактура — только из известного списка; иначе остаётся
    цвет по умолчанию.
186. **Текстура ставится на клоне.** Кэш отдаёт одну текстуру на URL, а
    повторов у поверхностей разное число.
187. **Фартук — стена, а не мебель.** Он вне группы гарнитура: иначе
    отделка стены попадёт в габарит мебели и в её вызовы отрисовки.

## Слой 23: правка там, где смотрят

Замерщик показывает клиенту 3D, а не чертёж, и правит он там же.

**Выделение общее.** Клик по мебели в сцене выделяет модуль — тот же
`selectedId`, что подсвечивает модуль на чертеже. Идентификатор модуля
достаётся из идентификатора детали (`<модуль>:door:0`).

**Вариант выбирается под сценой.** Тот же список, что на чертеже
(`variantsForModule`), и та же разница в цене — считанная настоящим
пересчётом, а не прикидкой по прайсу: клиент видит и цифру у варианта,
и итог внизу экрана.

**Ширина тянется, а не вводится.** Ручка на правом краю выделенного
модуля, шаг 50 мм: пальцем миллиметр не поставить, а цех считает
пятёрками. У техники ручки нет вовсе — её ширину диктует прибор.

**Что отклоняется, а что предупреждает.** Ряд длиннее стены — правка не
применяется, дефицит назван в миллиметрах: `rebalance` иначе тихо ужмёт
соседей, и клиент увидит не тот состав. А вот карго шириной 500 мм —
жёлтая строка, но ширина остаётся: это выбор заказчика, и отменять его
за него нельзя.

### Ловушки слоя 23

188. **Выделение в сцене и на чертеже — одно.** Два независимых выделения
    на одной мебели читаются как две разные мебели.
189. **Шаг ширины 50 мм.** Миллиметр пальцем — ложное ощущение контроля.
190. **Ширина техники не тянется.**
191. **Перетаскивание не полагается на `setPointerCapture`** (ловушка 62):
    состояние живёт в `useRef`, слушатели — на окне.
192. **Ряд длиннее стены — отказ; неподходящая начинка — предупреждение.**

## Слой 24: смета в пять строк

Полная смета — тридцать позиций: кромка ПВХ, эксцентрики, опоры, распил.
Клиенту они не говорят ничего, зато создают чувство, что его считают по
мелочам и где-то там спрятана наценка.

```
Корпус и фасады · Столешница и фартук · Фурнитура · Техника · Доставка и монтаж
```

Группы ([lib/millwork/estimateGroups.ts](lib/millwork/estimateGroups.ts))
ничего не считают заново — они складывают строки сметы, поэтому сумма
пяти цифр равна итогу до тенге. Снятая галочка выпадает и из группы, и
из итога. Подробный вид со ставками — по кнопке «Подробно», он же идёт
в печать.

Группа определяется по КЛЮЧУ статьи, а не по названию: название меняют,
ключ живёт в сохранённых сметах. Пустая группа не показывается вовсе —
«Техника: 0 ₸» в шкафу-купе читается как забытая позиция.

### Ловушки слоя 24

193. **Группы складывают, а не считают.** Второй расчёт разошёлся бы
    с итогом, и обе цифры видны клиенту одновременно.
194. **Группа определяется по ключу статьи.**
195. **Пустых групп на экране нет.**

## Слой 20: чертёж — это ракурс, а не отдельный экран

Чертёж, план и объём были тремя разными вещами: SVG, второй SVG и сцена.
Клиент, глядя на чертёж, не понимал, что 3D — та же мебель, и спрашивал
«а это точно моя кухня?». Теперь это ОДНА модель, снятая с трёх точек, и
переключение между ними — движение камеры: чертёж на глазах
разворачивается в комнату.

```
Как чертёж   ортокамера строго спереди + размерная цепочка поверх кадра
Сверху       ортокамера отвесно вниз
Три четверти перспектива, мебель крутится мышью
```

### Две камеры, а не одна

`OrthographicCamera` и `PerspectiveCamera` друг в друга не превращаются:
у них разные матрицы проекции. Поэтому рядом с перспективной живёт
ортогональная ([SceneCamera.tsx](components/millwork/cabinet3d/SceneCamera.tsx)),
и переключается АКТИВНАЯ.

Перелёт всегда снимает перспективная камера — в движении она выглядит
естественно, — а ортогональная включается в самом конце, когда камера уже
стоит. Именно там её точность и нужна: на ней держится слой размеров.
`prefers-reduced-motion` ставит камеру сразу.

### Размеры — тот же чертёж, положенный на кадр

Второй раз рисовать размерные цепочки нечем: разошедшийся размер хуже
отсутствующего. Поэтому поверх сцены ложится ТОТ ЖЕ `ElevationDrawing`
с флагом `overlay` — без контура помещения и с приглушёнными контурами
модулей ([DimensionLayer.tsx](components/millwork/DimensionLayer.tsx)).

Совпадение точное, потому что ортопроекция линейна: сцена отдаёт наверх
не «zoom», а готовую проекцию — пикселей в метре и экранную точку мировых
координат (0, 0, 0). Проверено числом: расхождение 0 px по всем трём
краям (`node scripts/check-unified-view.mjs`).

Проекция снимается В КАДРЕ, а не в эффекте: в эффекте матрица камеры ещё
не пересчитана рендерером, а прямоугольник канваса берётся до того, как
раскладка встанет окончательно.

### Ортокамеру приходится держать

OrbitControls подхватывают активную камеру и ставят её по своему состоянию
на каждом кадре — ДАЖЕ ВЫКЛЮЧЕННЫЕ. Ортокамеру они поднимали на четверть
метра и наклоняли на полтора градуса: вид «как чертёж» переставал быть
фасадом, а цепочка расходилась с мебелью на три пикселя. Полтора градуса
глазами неотличимы от фасада — ловится только числом, поэтому поза
ортокамеры восстанавливается каждый кадр перед замером.

Крутить чертёж и план мышью нельзя вовсе: сдвинутая камера увела бы размеры
от мебели. Крутится только «Три четверти».

### Подписи не повторяют вкладки

Вкладки результата уже называются «Чертёж», «План» и «3D». Кнопки ракурса
внутри сцены называют ТОЧКУ СЪЁМКИ — «Как чертёж», «Сверху», «Три
четверти»: два одинаковых слова на одном экране читаются как две разные
вещи, которые почему-то называются одинаково.

### Ловушки слоя 20

170. **Размерная цепочка не рисуется второй раз.** Поверх кадра ложится
    тот же `ElevationDrawing`, что уходит в печать.
171. **Сцена отдаёт проекцию, а не zoom.** Считать положение цепочки
    арифметикой «половина канваса плюс масштаб» нельзя: R3F меряет канвас
    своим наблюдателем и на кадр отстаёт.
172. **Проекция снимается в кадре, а не в эффекте.** В эффекте матрица
    камеры стара, а раскладка ещё не встала.
173. **Позу ортокамеры держим каждый кадр.** OrbitControls двигают
    активную камеру и выключенными.
174. **Ортогональные виды не крутятся мышью.**
175. **Перелёт анимирует перспективная камера, орто включается по
    прибытии.** Промежуточные кадры ортокамерой выглядят вывернутыми.
176. **Плавность перехода в headless не меряется.** GPU там нет, и любой
    перелёт укладывается в один кадр (ловушка 97): проверка смотрит
    ФАКТ переезда, а не число промежуточных положений.

## Слой 19: галерея готовых решений рядом с чертежом

Шаблон выбирался один раз на втором шаге и исчезал: посмотреть другое
решение значило вернуться назад и потерять правки. А на встрече всё
наоборот — клиент смотрит на чертёж и спрашивает «а по-другому можно?».
В этот момент замерщик должен нажать один раз.

Галерея стоит **рядом с чертежом**, на шаге результата. Решений на зону
до десятка — столько же, сколько в голове у мебельщика.

### Макет карточки — тот же чертёж, только маленький

`ElevationDrawing` с `compact`: без размерных цепочек, высотных отметок
и подписей, viewBox обрезан по мебели. **Нарисованных картинок нет
намеренно** — они разошлись бы с настоящим чертежом на первой же правке
раскладки, а новое решение требовало бы работы художника. Здесь оно
появляется само.

Каждая карточка собирается тем же `buildRun` на текущей длине стены:
десяток вызовов чистой функции — доли миллисекунды.

### Что показывает карточка

Название, цена и **разница с текущим**: «1 730 345 ₸ · −259 214». На
встрече клиент решает по разнице, а не по абсолютной сумме. Решение,
которое не собирается на этой стене, не показывается вовсе: карточка,
которая не соберётся, хуже её отсутствия.

Активная определяется ОТПЕЧАТКОМ, а не запомненным ключом — правил состав
руками, и не активна ни одна.

### Выбор сбрасывает правки и говорит об этом

Ручная расстановка техники и варианты модулей сбрасываются: в новом
решении на этих местах стоит другая мебель. Это сказано словами, а рядом
живёт «Вернуть предыдущее» — до следующего выбора.

### Опции решения — это выбор человека

`requirementsFromTemplate` проставляет `lockedOptions` по ключам, которые
задал шаблон. Без этого карточка «До потолка» собиралась ровно тем же
рядом, что «Прямая стандартная»: стратегия комплектации перекрывала опцию
своей, и два разных решения давали одну мебель и одну цену.

### Ловушки слоя 19

164. **Макет считается тем же `buildRun`, что и чертёж.** Отдельной
    картинки решения не существует — она разойдётся на первой правке.
165. **Решение, не помещающееся в стену, не показывается.**
166. **Опции шаблона — это выбор человека** (`lockedOptions`), иначе
    комплектация тихо вернёт своё, и две карточки дадут одну мебель.
167. **Разбор решения компании принимает и секции.** Раньше требовалась
    техника — и своё решение для спальни молча пропадало при сохранении.
168. **Своё решение хранит НАБОР, а не собранный ряд.** На другой стене
    оно обязано собраться заново по её длине.
169. **Два решения с одинаковым составом — это одна карточка дважды.**
    Ловится приёмкой отпечатков: `wardrobe-mezzanine` пришлось развести
    с `wardrobe-hinged` системой дверей.

## Слой 18: выбор варианта прямо на чертеже

На чертеже можно было двигать технику, тянуть полки и менять ширину, но
**сам модуль всегда был один и тот же**: внизу дверца, наверху глухой
фасад. В цеху на каждом месте есть выбор, и замерщик ждёт, что платформа
о нём знает.

Клик по модулю — рядом появляется список вариантов, подходящих **именно
этому месту**. Никаких выпадающих списков в стороне: выбор там, где палец
уже стоит.

### Вариант — это начинка места, а не новый тип модуля

Ширину, позицию и раскладку по-прежнему считает `buildRun`.
[lib/millwork/moduleVariants.ts](lib/millwork/moduleVariants.ts) отвечает
на один вопрос: что физически бывает в этом месте.

| Условие | Что отсекает |
|---|---|
| ширина места | карго шире 400 и стекло шире 900 не бывает |
| зона | в спальне кухонных вариантов нет вовсе |
| место в ряду | сушилка только над мойкой, вытяжка над варочной, карусель в углу |

Неподходящие **не показываются вовсе**, а не серыми: серая кнопка — это
вопрос «почему нельзя», а задавать его на встрече с клиентом некому.

У обычной дверцы и глухого фасада верхней границы ширины НЕТ (`anyWidth`):
раскладка выдаёт и 1225 мм, мебель делают на заказ. Ограничение проверяется
там, где оно физическое.

### Разница в цене, а не сумма

У варианта показана разница: «Подъёмник · +25 920 ₸». Клиент на встрече
решает, стоит ли эта дверца лишних денег, а не сравнивает два шестизначных
числа. Разница считается НАСТОЯЩИМ пересчётом — тот же `applyOps`, та же
`buildEstimate`; прикидка по прайсу разошлась бы с итогом внизу экрана,
а клиент видит оба числа.

### Узкое место — это карго, а не заглушка

Остаток 150–400 мм закрывался узкой дверцей, за которой ничего нет:
клиент платил за мёртвое место. Теперь там **выдвижная бутылочница** —
модуль, который продаётся. Уже 150 мм карго не бывает: механизм не влезает,
и такой огрызок по-прежнему прирастает к соседу.

### Верхний ряд выравнивается по мойке

Шкаф над мойкой обязан совпадать с ней по ширине — в него ставят сушилку.
Раньше верхний ряд заполнялся широкими стандартами, накрывал мойку модулем
на 1025 мм, и сушилку было некуда поставить: вариант существовал, а места
под него не было.

### Ловушки слоя 18

158. **Вариант не меняет габарит.** Меняется начинка; ширину и позицию
    считает раскладка, иначе ряд перестанет сходиться со стеной.
159. **Неподходящий вариант не показывается вовсе.** Серая кнопка — это
    вопрос, который некому задать.
160. **Разница в цене считается пересчётом, а не прикидкой по прайсу.**
    Иначе цифра на чертеже разойдётся с итогом внизу.
161. **Верхний ряд пересобирается из нижнего**, поэтому выбранные наверху
    варианты возвращаются по идентификатору модуля. Сдвинули низ — модуль
    другой, и выбор честно теряется.
162. **У модуля мойки нет дна ВСЕГДА**, по факту прибора, а не по выбору
    варианта: раньше эта деталь уезжала в раскрой, и цех распиливал лист,
    чтобы его выбросить.
163. **Выделение переживает выбор варианта.** Замерщик перебирает их
    подряд при клиенте: «а если стекло? а если подъёмник?».

## Слой 17: угловые и П-образные кухни

Угловая кухня — половина заказов. До этого слоя `Run` был одним прямым
рядом, а шаблоны «Угловая» и «П-образная» собирали ту же прямую.

**`Run` остался одним прямым рядом.** Угол — это ДВА таких ряда,
соединённых `Composition`; П — три. Вторая ветка раскладки разошлась бы
с первой на первой же правке, поэтому каждый сегмент по-прежнему считает
`buildRun`.

```
Composition { kind, segments: RunSegment[], corners: CornerJoin[], fingerprint }
```

### Главный инвариант угла

```
полезная длина Б = длина стены Б − то, что занял ряд А в углу
```

Занял он либо **900 мм** (угловой модуль — квадрат 900 × 900, он съедает
900 и вдоль своей стены, и вдоль соседней), либо **глубину ряда плюс
фальш-панель** (мёртвый угол). Считать здесь глубину при угловом модуле —
это налезть на него на 340 мм; вскрывается такое на монтаже, когда мебель
уже распилена, поэтому нарушение — исключение `CornerOverlapError`,
а не предупреждение.

### Два решения угла

| Решение | Когда | Что в смете |
|---|---|---|
| Угловой модуль 900×900 | нужен доступ в угол | корпус + карусель, дорого |
| Фальш-панель 100 мм | угол отдаётся под мёртвую зону | панель + угловые петли, дёшево |

Фальш-панель нужна не для красоты: без неё фасад при открывании упирается
в перпендикулярный. Петли **155° или 175°**, зазор фасада у угла **12 мм**
вместо обычных 3–4. Числа лежат в `CORNER` рядом с `GEOMETRY` — компания
их подтверждает, но из интерфейса не меняет. По умолчанию фальш-панель:
она дешевле, а угловой модуль замерщик выбирает осознанно.

### Приборы распределяются, а не дублируются

Мойка одна на всю кухню, а не по одной на стену. Пеналы уходят на
короткую стену, мокрая группа и варочная — на длинную: это рабочий
треугольник, а не предпочтение. Вытяжка едет за варочной сама.

### Ловушки слоя 17

153. **Второй ряд короче своей стены.** На угловой модуль — 900, на
    фальш-панель — глубина ряда плюс 100. Ошибка здесь вскрывается
    на монтаже.
154. **Приборы между рядами не дублируются.** Две мойки — это лишние
    деньги в смете и кухня, которой не бывает.
155. **Отпечаток композиции считается и от решения угла.** Фальш-панель
    вместо углового модуля — другая мебель и другие деньги.
156. **Угол по одной стене не собирается вовсе.** Вторая половина была бы
    выдуманной.
157. **Проход П-образной меньше 1200 мм — предупреждение по последствию:**
    «не разойтись вдвоём и не открыть ящик напротив».

## Слой 15: две-три компоновки одной кухни

Мебельщик показывает клиенту не одну расстановку, а две-три: мойка у окна
или у вывода воды, холодильник слева или справа, колонна с духовкой.
Больше трёх — «клиент теряется», это его слова.

Это НЕ бюджеты: три цены убраны намеренно (`SINGLE_VARIANT`) и не
возвращаются. Компоновка — это другая РАССТАНОВКА той же кухни.

```
buildArrangements → кандидаты из замера → отсев → mostDifferent(3)
```

Кандидаты собираются из замера, а не из списка в коде: «мойка у окна»
предлагается там, где окно есть. Каждый кандидат — это ДРУГИЕ ТРЕБОВАНИЯ,
а раскладку по-прежнему считает `buildRun`: своей разбивки у варианта нет,
иначе карточка разошлась бы с чертежом и сметой.

Отсев жёсткий: вариант, который не собрался или потерял прибор, не
показывается вовсе — клиент выбрал бы кухню без посудомойки, не заметив
этого. Одинаковые расстановки схлопываются по отпечатку.

### Ловушки слоя 15

112. **Компоновки считаются от состава БЕЗ того, чем они отличаются** —
    без стороны пеналов и без ручных позиций (`arrangementBase`). Иначе
    выбрал «холодильник справа» — и карточка «как считает расчёт»
    пересобирается с пеналами справа, схлопывается с выбранной, а
    подсветка начинает врать.
113. **Больше трёх не показываем никогда.** Лишние отбираются по различию
    расстановки (`mostDifferent`), а не по порядку в списке: три карточки,
    отличающиеся на пять сантиметров, — это не выбор.
114. **Вариант, теряющий технику, не показывается.**
115. **Комплектация на карточке — та же, что в итоге внизу** (`withStrategy`).
    Стратегия `optimal` меняет столешницу и фурнитуру; посчитай карточку
    без неё — и клиент увидит на карточке одну сумму, а в смете другую.
116. **Смена компоновки сбрасывает ручную расстановку и говорит об этом.**
    Так же называется и добавленный прибор: карточка «колонна» добавляет
    микроволновку в состав и после этого исчезает из списка — потому что
    колонна теперь есть во всех вариантах.
117. **Активная карточка определяется отпечатком, а не запомненным ключом.**
    Правил состав руками — не активна ни одна, и это честно.

## Слой 14: то, что мебельщик ставит каждый день

Микроволновка была в `APPLIANCE_SLOTS`, но в ряд не попадала никогда:
её не было ни в умолчаниях, ни в раскладке. Колонны «духовка + СВЧ»
конфигуратор не знал вовсе, хотя это самая частая высокая секция.

### Колонна — один пенал, два прибора

Заказаны духовка и микроволновка — они встают в ОДИН модуль 600 мм.
Двумя пеналами это лишние 600 мм стены, и мебельщик так не делает.
`Module.column` (`{ top, bottom }`) едет с модулем до чертежа, 3D и сметы;
по умолчанию микроволновка сверху — так ей пользуются, не приседая, —
а кнопка «Поменять местами» на выбранной колонне меняет порядок.

Ниши считает `columnNiches` — ОДНА функция на чертёж, 3D и наполнение.
Высоты паспортные (духовка 595, микроволновка 380–450), но опоры ниш
садятся на систему 32 и округляются ВВЕРХ: ниша может быть выше
паспортной, ниже — нет, иначе прибор не влезет и поедет обратно в магазин.

### Холодильник: встроенный или отдельностоящий

Разница — фасад заподлицо и петли для встройки, десятки тысяч в смете,
поэтому это выбор на модуле, а не косметика. Встроенный даёт `front_panel`,
петли и детали «Фасад встройки» в детализировке; отдельностоящий не даёт
ничего и в 3D виден целиком. По умолчанию встроенный.

### Витрина

Секция `glass_display`: стеклянные полки, стеклянная дверь в раме
(`glass_front`, м²) и лента по контуру (`led_display`, погонные метры —
`displayLedMeters`, а не «комплект»). Ширина 300–600 мм, встаёт в свободный
торец — напротив пеналов. Место под неё резервируется ДО раскладки техники,
и если после неё технике не хватает стены, отказывается ВИТРИНА: холодильник
важнее подсветки, и отказ называется словами.

Подсветка гаснет перед захватом кадра (`displayLit` в сторе,
[lib/millwork/capture.ts](lib/millwork/capture.ts)) — та же ловушка, что
с открытым ящиком: светящаяся полоса в clay-кадре становится частью мебели.

### Верхний ряд до потолка — переключатель на виду

`upperToCeiling` существовал, но был спрятан, а просит его каждый второй
клиент. Теперь это выбор рядом с составом. И он работает: стратегия
комплектации больше не перекрывает то, что человек выбрал руками —
`RunRequirements.lockedOptions`.

### Ловушки слоя 14

102. **Духовка и микроволновка — один модуль.** Два пенала по 600 мм
    съедают лишний метр стены, которого в квартире нет.
103. **Опоры ниш округляются ВВЕРХ по системе 32.** Ниша выше паспортной —

104. **`columnNiches` считается один раз на чертёж, 3D и наполнение.**
    Второй расчёт разведёт эскиз с присадкой.
105. **Порядок приборов в колонне входит в отпечаток.** Микроволновка над
    духовкой и духовка над микроволновкой — разная мебель.
106. **В колонне приборов ДВА, и смета обязана видеть оба.** `moduleAppliances`,
    а не `unit.appliance`: потерянный второй — это неоплаченный прибор.
107. **Встройка и отдельностоящий — разные строки, а не наценка.**
108. **Стратегия комплектации не перекрывает выбор человека**
    (`lockedOptions`). Переключатель, который ничего не меняет, читается

109. **Витрина отказывается первой.** Место под неё резервируется до
    раскладки, но при нехватке длины уходит она, а не техника.
110. **Подсветка гаснет перед захватом кадра.**
111. **Подпись колонны в ленте — из `label`, а не из имени прибора.**

## Слой 13: замерщик двигает технику руками

Алгоритм ставит мойку к воде, варочную не у края, холодильник в торец —
верные умолчания. Но на объекте замерщик видит то, чего алгоритм не знает:
газовый вывод в другом месте, у хозяйки своё представление о том, где стоять
плите. Пока поправить это нельзя, он доверяет расстановке только тогда,
когда она совпала с его планом, а в остальных случаях платформа мешает.

### Ручная позиция сильнее умолчаний

`RunRequirements.manualAnchors` — прибор → центр от левого края, мм. В
`planAnchors` такая позиция перебивает расчёт и получает наивысший приоритет:
при нехватке длины отбрасываются ДРУГИЕ приборы, но не этот.

Раскладка идёт в два прохода: **сначала ручные позиции**, потом остальное
вокруг них. Одним проходом слева направо ручной прибор упирается в то, что
уже стоит слева, и правка «не работает» при полностью верном коде.

**Вытяжка не перетаскивается** — она висит над варочной и едет за ней сама.
Отдельная вытяжка это ошибка монтажа, а не свобода выбора.

### Предупреждать, но не запрещать

| ситуация | реакция |
|---|---|
| варочная ближе 400 мм к краю | жёлтое: «некуда ставить горячую посуду» |
| варочная ближе 300 мм к мойке | жёлтое: «меньше рабочего зазора» |
| мойка далеко от вывода воды | жёлтое, **если расстановку трогали руками** |
| варочная под окном | жёлтое: «вытяжку туда не повесить» |
| прибор перестаёт помещаться | правка НЕ применяется, дефицит назван в мм |

Мойка дальше 600 мм от воды остаётся красным флажком, пока расстановка
автоматическая: там ошибся алгоритм. Как только замерщик взял расстановку в
свои руки, это предупреждение — он видел вывод своими глазами.

### Ловушки слоя 13

98. **Ручные позиции раскладываются первыми, остальное — вокруг них.**
99. **Хвостовой огрызок не подращивает модуль ЛЕВЕЕ ручного прибора.**
    Рост сдвигает всё правее себя, и прибор, поставленный на 1200 мм,
    уезжает на 1250. Полсантиметра замерщик не заметит, а доверие потеряет.
100. **Вытяжка не считается выпавшим прибором.** Она не занимает места
    в ряду, и отказывать из-за неё в переносе нельзя — только предупредить.
101. **Фигура с `fill="none"` ловит указатель только по обводке.** Модуль
    на чертеже тянется за прозрачный прямоугольник, а не за рамку.

## Слой 12: форма композиции и вид мебели

### Модель дорисовывала угол

Композиция прямая — один ряд вдоль одной стены, семь модулей, — а на
рендере кухня выходила угловой: слева пеналы на перпендикулярной стене.
Та же история, что с раскладкой и микроволновкой в пенале: **пустоту модель
заполняет по-своему, пока запрет не назван прямо**.

[lib/millwork/composition.ts](lib/millwork/composition.ts) собирает блок
`ФОРМА ГАРНИТУРА` с числами из состава и ставит его ПЕРВЫМ в `GEOMETRY_LOCK`,
до описания стиля: стиль модель читает как пожелание, а `GEOMETRY_LOCK` —
как ограничение, и порядок здесь имеет значение.

Форма считается из состава: угловой ряд — тот, в котором есть угловой
модуль. Перед отправкой `assertShapeMatches` сверяет текст промпта с формой
и бросает исключение, если в прямой композиции всплыло слово про угол.
Отпечаток конфигурации это не ловит: форма живёт в тексте, а не в модулях.

### 3D показывает конструкцию

Модуль был плоской коробкой. Мебель читается мебелью по шести признакам, и
все они геометрические:

| деталь | размер |
|---|---|
| зазор между фасадами | 3–4 мм из настроек цеха |
| фасад впереди корпуса | на свою толщину, 16–18 мм |
| цоколь утоплен | 50 мм вглубь, высота 100 |
| свес столешницы | 25 мм вперёд, торец 38 мм |
| ниша под верхним рядом | тёмная полоса на 1450 |
| ручки | профиль по кромке или накладная скоба |

Текстур дерева и мрамора в 3D нет намеренно: материалы показывает рендер,
а 3D показывает **конструкцию**. Все поверхности матовые и нейтральные.

**Встроенная техника закрыта фасадом.** Холодильник, посудомойка и мойка
получают обычную дверцу — тёмными остаются только духовка, варочная и
вытяжка. Без этого ряд из семи модулей читался как стена чёрных плит.

### Три ракурса

`sceneCamera` в [lib/cameraFraming.ts](lib/cameraFraming.ts): «Спереди»,
«Три четверти» (по умолчанию) и «Сверху». Фронтальный вид плоский — из него
не видно ни глубины, ни свеса столешницы, а мебель продаётся объёмом.
Камера ставится ОДИН раз на смену вида, дальше клиент крутит её сам.

### Ловушки слоя 12

93. **Форма композиции называется явным запретом.** «Углов нет. Второго
    ряда нет. На перпендикулярных стенах мебели нет вовсе.»
94. **Правило формы стоит до описания стиля.** Стиль — пожелание,
    `GEOMETRY_LOCK` — ограничение.
95. **Ось двери — на передней плоскости корпуса (`z = 0`).** Модуль
    нарисован от нуля вглубь; смещение на полглубины отрывает дверь от шкафа.
96. **Встроенная техника рисуется фасадом, а не чёрным блоком.**
97. **Кадров в секунду в headless мерить нельзя.** Там нет GPU, и
    софтверный растеризатор упирается в заливку пикселей: без единой тени
    сцена даёт те же 1–2 кадра/с, что и с тенями.

## Слой 11: интерактивный 3D-шкаф

Клиент не умеет читать чертёж, но открытый ящик понимает без объяснений.
Тык в ящик — ящик выезжает на 300 мм, тык в дверь — дверь распахивается на
90°, видно полки и штангу. Всё это **чистая геометрия, без единого запроса
к модели**: рендер стоит денег за каждую картинку, а эта сцена может
крутиться на встрече хоть час.

Данные уже есть: `Module.fill` из слоя 10. Полки берутся оттуда КАК ЕСТЬ —
второй расчёт развёл бы 3D с чертежом и детализировкой.

### Анимация своя, на useFrame

`frameloop="demand"` — это лечение мерцания, менять его нельзя. Любая
библиотека анимации двигает объекты вне цикла R3F, и кадр просто не
перерисовывается: анимация «не работает» при полностью верном коде.
Поэтому доводка в [useSlide.ts](components/millwork/cabinet3d/useSlide.ts):
доля пути за кадр, остановка при разнице меньше полумиллиметра и
`invalidate()` — **один на кадр**, а не по одному из каждого меша.

Там же счётчик движущихся элементов: `settled()` ждёт два кадра подряд без
движения, а не спит по таймеру.

### Зона касания меряется в пикселях

Дверца 200 мм в ряду 3200 мм на телефоне — это **восемь пикселей**
(замерено: 8×39 px). Увеличенный коллайдер «в миллиметрах» не помогает, он
сжимается вместе с кадром. `useTouchTarget` считает, сколько метров
приходится на пиксель на этом расстоянии, и раздувает невидимый меш до
44 px на экране: стало 71×67 px, тап попадает с первого раза.

### Перед захватом кадра всё закрывается

`captureForRender` ([lib/millwork/capture.ts](lib/millwork/capture.ts))
закрывает ящики и двери, снимает разрез и ждёт `settled()`. Это та же
ловушка, что была с гизмо: всё, что видно в кадре, модель считает частью
мебели — открытый ящик приедет в рендер выдвинутым.

### Ловушки слоя 11

87. **Анимация только через `useFrame` + `invalidate()`.** Сторонняя
    библиотека при `frameloop="demand"` не перерисует кадр.
88. **`invalidate()` — один раз за кадр.** При «Открыть всё» едут десятки
    элементов сразу.
89. **Зона касания считается в экранных пикселях, а не в миллиметрах.**
90. **Перед захватом кадра мебель закрывается и сцена ждёт `settled()`.**
91. **Интерактивный объект не рисует `KitchenUnit`.** Иначе в сцене стоят
    две кухни одна в другой: меш строит `Cabinet3D` прямо из `Run`.
92. **`offsetMm` у верхних модулей уже абсолютный.** Прибавленное начало
    сегмента уводит верхний ряд за стену — ловилось только глазами.

## Слой 9: один вариант и большое сравнение

### Экран результата — это сравнение

«До и после» занимает не меньше 70% экрана и стоит ПЕРВЫМ; чертёж, план,
3D и смета — ниже. Шторка в 3 px, ручка 56 px: экран смотрят вдвоём, и
клиент должен понять, что её можно тянуть, без объяснений. Кнопка «На весь
экран» разворачивает сравнение поверх всего, Esc закрывает. Тот же блок и
той же высоты стоит в кабинете клиента.

Вида «Рендер» больше нет: рендер и есть правая половина сравнения.

### Пять зон квартиры

[lib/millwork/zones.ts](lib/millwork/zones.ts) — профили: глубина, высота,
состав секций, статьи сметы и описание сцены для рендера.

| зона | глубина | высота | чем закрыт | своё в смете |
|---|---|---|---|---|
| Кухня | 560 | до потолка | распашные | столешница, фартук, техника |
| Спальня | 600 | до потолка | **купе** | двери-купе м², система купе, штанга, полки, ящики |
| Прихожая | 400 | до потолка | распашные | зеркало, крючки, обувница, скамья, пантограф |
| Зал | 400 | 2000 | распашные | кабель-канал, подсветка ниши, подвесной крепёж |
| Санузел | 450 | 850 | распашные | влагостойкий корпус, вырез под раковину |

**Секция — это начинка модуля** ([lib/millwork/sections.ts](lib/millwork/sections.ts)).
У кухни роль модуля задаёт прибор, в шкафу приборов нет: штанга под пальто
требует 1500 мм чистой высоты, полки идут шагом 350 мм, одна дверь-купе шире
1200 мм провисает. Эти числа из интерфейса не меняются — правило то же, что
и для `GEOMETRY`.

`buildRun` для зон без техники уходит в `buildSectionRun`: секции садятся на
свои ширины, лишнее ужимается до минимума, остаток раздаётся шагами по 50 мм,
хвост закрывается доборной планкой. Инвариант тот же — сумма сходится с длиной
до миллиметра, `assertRunFits` работает одинаково для всех зон.

Столешницы и фартука в спальне, прихожей и зале нет вовсе, поэтому в смете
этих строк тоже нет: `zoneProfile(run.zone)` решает, какие статьи вообще
появляются. В санузле корпус влагостойкий — это **другой ключ ставки**
(`ldsp_moisture`), а не наценка к обычному.

### Что зона решает в рендере

`ZoneProfile.scene` описывает, что должно быть в кадре: в спальне шкаф во всю
стену и край кровати, в зале выключенный чёрный экран и подсветка ниши, в
санузле влажный блик на плитке и полотенце для масштаба. Без этого модель
рисует кухню везде, где видит корпусный ряд. Четыре приёма из кухни остаются
во всех зонах: два материала, подсветка, чёрные акценты, потолочный свет.

### Готовность зоны считается, а не проставляется

`zoneReadiness(zone)` в [lib/millwork/templates.ts](lib/millwork/templates.ts):
пометка «в разработке» снимается, только когда у зоны есть свои секции и хотя
бы два шаблона. Флаг в профиле легко забыть переключить — и продукт начнёт
обещать посчитанный шкаф-купе, которого нет.

### Стиль выбирает человек

Стиль был жёстко привязан к комплектации: «премиум» — только премиум-модерн.
Но бюджет и вкус — разные вещи. Теперь три стиля выбираются рядом с кнопкой
отрисовки (`RENDER_CHOICES` в [lib/millwork/render.ts](lib/millwork/render.ts)),
по умолчанию премиум-модерн, выбор лежит в состоянии объекта
(`millwork.renderStyle`). Кабинет клиента берёт картинку по сохранённому
стилю; у старых объектов его нет, и там остаётся `VARIANT_STYLE`.

### Съёмка отдельно от стиля

Стиль отвечает за материалы и настроение, а «плоско» или «дорого» решает
СЪЁМКА: объектив, три источника света, тени и отражения. Раньше об этом
была одна строка — «естественный свет из окна», — и рендеры выходили
плоскими. Блок `PHOTOGRAPHY` в [lib/renderStyles.ts](lib/renderStyles.ts)
один на все стили; `optionsBlock` добавляет то, что видно в кадре из
комплектации: фасады без ручек при `integratedHandles`, верхний ряд до
потолка при `upperToCeiling`. Опции приезжают в промпт через
`meta.runOptions` сцены.

### Три поверхности кухни выбираются отдельно

Фасады, столешница и фартук — разные товары, разные строки сметы и разные
строки BINDING TABLE. Одним списком с одним выбором клиент видел своей
только одну поверхность из трёх, а две остальные модель придумывала.

| поверхность | откуда товары | ключ в `selections` |
|---|---|---|
| Фасады кухни | `applies_to = 'zone'` | `zone:kitchen` |
| Столешница | ключ сметы `countertop_*` | `zone:countertop` |
| Фартук | ключ сметы `wall_panel` | `zone:backsplash` |

Невыбранная поверхность не блокирует остальные: про каждую пишется своя
строка состояния — «столешница пойдёт по описанию комплектации». Запил и
плинтус в список столешниц не попадают: это работы, а не поверхность.

Шаг «Материалы» показывает ровно те поверхности, которые в зоне есть:
в спальне, прихожей и зале остаётся один блок — фасады, и называется он
по зоне («Фасады шкафа», «Фасады тумбы»). Пустой блок «Столешница» в
спальне предлагал бы выбрать то, чего там не бывает, — а в смете и на
чертеже этой строки уже нет. Строка итога тоже называет зону: «Ваша
спальня», «Ваш санузел». Подписи живут в `ZoneProfile`, чтобы не
расходиться между экранами.

**Ни один ключ не зависит от сцены.** Фасады сначала писались под id объекта
сцены — и не писались вовсе: на шаге «Материалы» сцена не смонтирована, id
нет, выбор молча уходил в никуда, а кнопки стояли выключенными. Теперь у
фасадов свой ключ, как у столешницы и фартука.

Комплект кухни по-прежнему может дать столешницу и фартук своими
референсами — но только если СВОЙ товар для них не выбран: у объектов,
собранных до разделения, материалы не должны пропасть. Там же выбор под
id гарнитура остаётся читаемым, но новый ключ главнее — иначе в промпт
уехали бы два разных артикула фасадов.

### Ловушки слоя 9

73. **Вариант один, но ключ варианта остался.** На нём держатся снятые
    галочки сметы, стиль рендера и сохранённое состояние объекта. Убрать
    ключ — значит переписать сохранённые проекты.
74. **Выключенный шаблон обязан объяснять, почему он выключен.** Тап, на
    который ничего не отвечает, читается как «выбор шаблона ничего не меняет».
75. **Зона, которая не просчитана, говорит об этом на своей карточке.**
    Не в документации и не в разговоре — на экране, который видит клиент.
    Готовность СЧИТАЕТСЯ по составу секций и числу шаблонов.
79. **Шкаф-купе не платит за распашные фасады.** Внутренние секции открыты,
    ряд закрыт полотнами: иначе смета берёт и двери-купе, и фасады с петлями.
80. **Тумба под раковину привязана к воде жёстче мойки:** 300 мм против 600.
    Раковина висит над сифоном, сдвинуть её подводкой нельзя — расхождение
    это перенос стояка, поэтому предупреждение блокирующее.
81. **Шаблон обязан вмещать свой состав.** Для кухни минимум считает техника,
    для остальных зон — сумма минимальных ширин секций.
76. **Ключ выбора не может зависеть от смонтированной сцены.** Сцена живёт
    только на шаге результата; на шаге материалов писать было бы некуда.
77. **Ключи `zone:kitchen`, `zone:countertop`, `zone:backsplash` попадают
    в сохранённые проекты.** Переименование потеряет выбранный товар
    у старых объектов.
78. **Кнопка отрисовки живёт В сравнении, а не под ним.** Сравнение занимает
    70% экрана: кнопка ниже не видна без прокрутки, и рендер выглядит
    сломанным. Состояние отрисовки одно (`useMillworkRender`) — иначе две
    кнопки показывали бы разное «сейчас рисуем».

## Слой 8: продукт, который выглядит дорого

### Палитра — язык производства, а не чертежа

Синька отменена. Инструмент мебельной компании взял цвета того, что она
делает: тёплый почти-чёрный вместо серого, костяной текст вместо белого,
латунь вместо неона.

```
--bg #16150F   --surface #1E1D16   --surface-2 #272519   --line-warm #34322A
--text #F2EFE6 --text-dim #9C978A  --accent #C08B3E      --alert #B5533F
```

Один акцентный цвет на весь продукт: он значит «основное действие» и
«выбрано», больше ничего. Градиентов, стеклянных панелей и цветных теней
нет. Тень одна: `0 1px 2px rgba(0,0,0,.28)`.

**Имена переменных остались прежними** (`--navy`, `--cyan`, `--sheet`):
на них завязаны чертёжные компоненты и полсотни классов Tailwind. Менять
значения дешевле, чем переписывать разметку; новые имена (`--bg`,
`--surface`, `--accent`) заведены рядом и используются в новом коде.

### Светлая тема живёт в куке, а не в localStorage

Тему обязан знать СЕРВЕР. Из `localStorage` её читает только браузер, и
светлая страница успевает мигнуть тёмной на каждом открытии. Кука
`mw-theme` читается в `app/layout.tsx` и превращается в `data-theme` прямо
в HTML — мигать нечему. Инлайновый скрипт в `<head>` для этого не годится
вовсе: App Router его не доносит до документа.

### Ровно три движения

1. Нажатие кнопки — `scale(0.985)`, 90 мс (`transform`, не цвет).
2. Появление карточки рендера — `.mw-appear`, 180 мс, по одной по готовности.
3. Смена числа в смете — `.mw-value-flash`, 300 мс; перезапуск через `key`.

Больше в продукте анимаций нет. `prefers-reduced-motion` выключает все три.

### Технические подписи — по запросу

Секунды рендера, число модулей и отпечаток конфигурации нужны нам, а не
клиенту, который сидит рядом и смотрит в тот же планшет. Они включаются
адресом `?debug=1` ([lib/debug.ts](lib/debug.ts)).

### Ловушки слоя 8

68. **Тема — кука, читаемая сервером.** `localStorage` даёт мигание,
    инлайновый скрипт в `<head>` App Router не доносит.
69. **Константу, нужную серверу, нельзя держать в модуле с `'use client'`.**
    Сервер получит ссылку на клиентский модуль, а не значение: подстановка
    молча вернёт `undefined`. Так уехала таблица `VARIANT_STYLE` —
    её пришлось вынести в [lib/millwork/styles.ts](lib/millwork/styles.ts).
70. **Картинка рендера не живёт в состоянии.** Три base64 по полтора
    мегабайта таскает каждая перерисовка; после ответа модели картинка
    уезжает в Storage, а в состоянии остаётся ссылка. Кабинет клиента при
    этом выбирает строку ПО СТИЛЮ выбранной комплектации, а не «последнюю».
71. **Кадр кодируется в JPEG вне главного потока.** `toDataURL` кодирует
    синхронно; замер показал 7 289 мс на beauty и 1 748 мс на clay. Кадр
    копируется в 2D-канвас сразу после `gl.render` (позже буфер WebGL уже
    очищен), а кодирует `toBlob` — после восстановления сцены.
72. **Плотность чертежа и замерного листа не трогать.** Мелкий шрифт там
    норма отрасли; правило «не мельче 13 px» на документы не распространяется
    (`.mw-sheet`, `data-doc`).

## Мерцание при движении мыши

Диагностика — [scripts/check-paint.mjs](scripts/check-paint.mjs): трасса
`devtools.timeline` за три секунды движения, с разбором площадей отрисовок
и A/B в одном прогоне.

Что показала трасса: перекрашивание происходит **только когда указатель
пересекает кнопки**. По пустому месту — ноль отрисовок, на `/login` — ноль
на любом маршруте, то есть общий макет ни при чём. Виноваты были два
свойства кнопок:

| | было | стало |
|---|---|---|
| отрисовок за 3 с | 126 | 56 |
| медиана площади | 967 600 px² (весь вьюпорт) | 4 830 px² (сама кнопка) |
| пересчётов стилей | 81 | 24 |

1. `transition: background-color/border-color` на `.mw-btn` растягивал
   каждое наведение на 120 мс: сплошной поток кадров при проведении мышью
   вдоль ряда кнопок. Переход убран — наведение мгновенное.
2. `contain: paint` на `.mw-btn` и `.mw-panel-flat` ограничил отрисовку
   их собственными границами. Без него любое наведение помечало грязным
   весь кадр. Рамка выделения и фокус ушли ВНУТРЬ (`ring-inset`,
   `outline-offset: -2px`) — наружные обрезал бы тот же `contain`.

`backdrop-filter`, крупных теней на липких панелях, `transition` на
свойствах раскладки и `:hover` на больших контейнерах не нашлось —
проверено тем же скриптом.

## Один dev-сервер на проект

`npm run dev` идёт через [scripts/dev.mjs](scripts/dev.mjs): он освобождает
порт и запускает `next dev` с жёстко заданным номером.

Причина в том, что `next dev` при занятом порте молча переезжает на соседний.
Два процесса начинают писать чанки в ОДНУ папку `.next` и подчищают чужие:
маршрут, который компилировал первый сервер, отваливается с `ChunkLoadError`,
хотя код исправен и `npm run build` зелёный. Симптом обманчив — на одной
странице всё работает, на другой нет, будто дело в самой странице.

## Проверка

```bash
npm run typecheck      # tsc --noEmit
npm run test:spatial   # пространственное соглашение (слой 1)
npm run test:catalog   # CSV из 1С, спецификация, фото → комната (слой 3)
npm run test:millwork  # раскладка, смета, варианты, коммуникации (слой 4)
npm run test:survey    # состояния величин, отпечаток, предупреждения (слой 6)
npm run build
npm run test:capture   # захват кадра в реальном браузере (нужен build)
npm run test:demo      # прогон демонстрации: пять шагов сценария продажи
npm run test:rls       # мультиарендность (нужны ключи Supabase)
npm run test:render    # живой рендер (тратит запросы к модели, нужен ключ)
npm run verify         # всё, кроме test:rls и test:render
```

`test:rls` и `test:render` не входят в `verify`: первый требует живого
Supabase, второй тратит настоящие запросы к image-модели. Без ключей — и при
заглушке из `.env.local.example` — оба честно пишут «не проверено» и выходят
с нулём. `test:rls` перед работой стучится в `/auth/v1/health`: падение с
«fetch failed» по несуществующему проекту выглядело бы как поломка RLS.

Инструменты глазной проверки (в `verify` не входят):
`node scripts/check-design.mjs` — снимки всех экранов в двух темах на 1440
и 390 px плюс отчёт о шкале и целях касания; `node scripts/check-paint.mjs` —
отрисовки при движении мыши; `node scripts/check-render-perf.mjs` — сколько
блокирован главный поток, пока рисуются три комплектации;
`ROOM_PHOTO=… node scripts/live-millwork-render.mjs` — живой прогон
комплектации по фотографии помещения (тратит запросы к модели);
`node scripts/check-unified-view.mjs` — три вида одной модели: совпадение
размеров с мебелью до пикселя, отсутствие наклона у ортокамеры, факт
переезда камеры;
`node scripts/check-scene-edit.mjs` — правка в сцене: выделение модуля,
варианты места, ручка ширины и смета в пять групп;
`node scripts/check-sheet.mjs` — чертёжный лист: состав видов, подписи с
масштабом, настоящий масштаб в режиме печати, номер листа в штампе;
`node scripts/check-variants.mjs` — лента превью: карточки-мини-чертежи,
разница в цене, перестроение чертежа на месте и время отклика;
`RUNS=1 node scripts/check-render-fronts.mjs` — ЖИВОЙ прогон визуализации
(тратит запросы к модели): состав с витриной и ящиками, картинка и мета
складываются в `.capture-check/render-fronts/`;
`node scripts/check-cabinet3d.mjs` — интерактивная сцена: клик по мебели,
число мешей и материалов, кадры в секунду, зона касания на 390 px;
`node scripts/check-cad-frames.mjs` — кадры САПР-сцены: ноль в покое и
число за минуту настоящей работы.

`test:capture` и `test:demo` перед стартом освобождают свой порт: сервер,
оставшийся от прошлого прогона, отдаёт СТАРУЮ сборку — страница открывается,
чанки 404, React не оживает, и падают проверки, к правкам отношения не имеющие.
Кадры после изменения сцены снимаются не по таймеру, а до фактической смены
картинки: на загруженной машине софтверный WebGL рисует дольше секунды.

`test:capture` поднимает `next start`, гоняет Playwright с WebGL и проверяет,
что в кадре нет служебных элементов, clay обесцвечен, вьюпорт восстановился,
кадр весит меньше 800 КБ и сломанный вариант не мешает остальным.
`HERO=1 npm run test:capture` дополнительно кладёт кадр ракурса по умолчанию
в `.capture-check/` для глазной проверки.
